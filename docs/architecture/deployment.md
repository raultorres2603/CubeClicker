# Deployment

CubeClicker deploys to three managed platforms: **Vercel** serves the React/Vite SPA as a static build, **Render** runs the Fastify + `@fastify/websocket` backend container as one free Docker web service, and **Neon** provides PostgreSQL for accounts, sessions, verification tokens, economy and customization. **GitHub Actions** is the single CI/CD pipeline, with the `development` and `production` GitHub Environments holding every per-environment secret and variable. The backend host moved from Fly.io to Render on 2026-11-16 after Fly's credit-card gate blocked the free development app (§ Superseded Fly.io backend); Vercel and Neon were retained, and the earlier AWS (ECS/ALB/RDS/ECR + Terraform) target remains historical (§ Superseded AWS deployment).

The application itself is unchanged: game logic, server authority, in-memory rooms, the WebSocket protocol, the auth model and the database schema are the same as local. The local `podman compose up` path is unchanged too (see `../../README.md` § Quickstart). The container images remain provider-neutral deployables (see `containerization.md`); Vercel hosts the static frontend build, not the backend.

- Canonical reference: `vercel-render-neon.md` — architecture, exact environment catalog, runbook, rollback, local-vs-cloud, cost and limits.
- Superseded reference: `vercel-fly-neon.md` — retained for history, marked SUPERSEDED.
- Application stack: `stack.md`. Container conventions: `containerization.md`. Feature record: `../features/render-backend-migration/status.md`.

## Platform split and state ownership

| Surface | Platform | What it owns |
| --- | --- | --- |
| Static SPA (`src/frontend`) | Vercel CDN | Nothing but the built HTML/JS/CSS; no functions, no serverless backend |
| HTTP API + WebSocket (`/auth/*`, `/healthz`, `/ws`) | Render free Docker web service, one instance | All live game/room state (in memory, one process) and auth sessions |
| PostgreSQL | Neon | Durable accounts, sessions, verification tokens, economy and customization rows only |
| CI/CD and configuration | GitHub Environments (source of truth) + Render service variables (runtime copy) | Pipeline ordering, per-environment secrets/variables and the committed runtime defaults; no runtime application state |

- **Game state stays on Render.** Rooms are in-memory, server-authoritative and per process. One instance is the pinned topology; two or more instances would split the room registry. See § Single-instance trade-off. Neon is never used for game/room state, and Vercel owns no application state.
- **Data flow.** Browser → Vercel for HTML/JS/CSS; browser → Render for `/auth/*` (`fetch`, `credentials: 'include'`) and `/ws` (`wss://`). The session cookie is host-only for the Render API host and is attached on both requests and the WebSocket upgrade; the backend resolves the account from the upgrade cookie exactly as locally.
- **Diagnostics `/metrics`.** The backend also serves `GET /metrics` (Prometheus text) on its existing port 8080. Render serves the whole backend on one public host with no path filter, so the committed configuration is the control: `render.yaml` sets `METRICS_ENABLED: 'false'` for the service and the live service carries the same value, making the public host return `404`. Local compose keeps `true` on the loopback only. The CORS hook excludes `/metrics`, so the frontend origin receives no allow-origin or credentials on `GET` or `OPTIONS` and cannot read it. Temporary internal scraping sets `METRICS_ENABLED=true` on the service (dashboard) and restarts it, which also resets the per-process metrics; because there is no path filter, that short window is reachable by a non-browser client and is an audited exception. The historical ALB routing table is not the current boundary (see § Superseded AWS deployment (historical) and `observability.md` § Exposure and retention).
- **Verification email and its assets.** Development and production deliver verification email through the Brevo HTTPS API on port 443; SMTP remains the local/off-Render transport. Delivery is an HTTP request from the backend (`POST https://api.brevo.com/v3/smtp/email` on `443`), not a service, and the fixed `BREVO_API_KEY` header value is read only from the environment. The two branded PNGs are static files under `src/frontend/public/email/`, served by the existing frontend origin at `/email/*.png` (Vite locally, nginx in the `prod` image, Vercel when deployed): no new service, port, image or backend route, and no attachments on the message. `APP_BASE_URL` supplies the origin for the verification link and the image URLs.
- **Deploy flow.** A push to `main` runs **CI once**; a successful CI run triggers the **deploy** job (`development` environment) via `workflow_run` (it does not re-run CI). A manual dispatch first resolves and guards the selected build (`Resolve selected build` → `Verify CI succeeded for target commit`) and checks out that SHA (`Confirm selected build checkout`, `Check selected build deploy contract`); the automatic path uses `workflow_run.head_sha` and skips those steps. The fixed order is `Check deployment Brevo configuration` (eleven values, `--check-only`, no network) → `Check selected build schema compatibility` (manual dispatch only) → Neon migration (direct URL) → `Sync Brevo SMTP settings to Render` (nine deployed names: the seven SMTP names plus `EMAIL_TRANSPORT` and `BREVO_API_KEY`) → `Deploy Render backend` (manual dispatch: Render deploy-by-commit API with `commitId`; automatic: deploy hook) → `Wait for Render deploy to complete` (manual: poll to `status: live` and require the service's current deploy ID/commit; automatic: 45 s head start) → health poll → Vercel pull/build/deploy `--prod` from the same checkout with `--meta githubCommitSha` → deployed smoke. Backend before frontend, because the frontend build bakes the API/WS URLs and should only point at a live, migrated backend.

- The effective environment is `github.event.inputs.environment || 'development'`, used identically by the concurrency group and the deploy job's `environment:`. A dispatch chooses `development` or `production` explicitly and reads only the selected environment's secrets and variables. The `production` Environment holds 23 names (15 variables, 8 secrets): the eleven-name guarded deploy catalog (7 variables, 4 secrets), the nine workflow-read names and the three inert parity names. In provider naming, the GitHub Environment `production` and the Neon branch `production` are environment identifiers, not resource-name suffixes; the production Render service and Vercel project are named `cubeclicker` with no environment token. The `main`-only deployment branch policy and required reviewers pause a production dispatch until the owner approves; development has no protection. A production dispatch selects the build with the optional `build_sha` (§ Build SHA selection (production)); a development dispatch requires an empty `build_sha`.
- There is no third environment. Development and production are fully isolated (separate GitHub Environment secrets/variables, separate Render services, separate Neon branches and separate frontend hostnames). Each environment deploys only to its own provider resources; no development value points at production and no production value points at development.
- There is no `develop` branch. `main` is both the integration branch and the development deployment branch: CI runs on pull requests and `main` pushes, and a `main` push deploys development after CI succeeds; production is manual (`workflow_dispatch`) and provisioned behind the `production` Environment's protection. The branch model is recorded in `../../AGENTS.md` § Conventions.

The live production dispatch validated all eleven names and synced nine (`eleven validated, nine synced`).
- `VITE_*` values are public client configuration baked into the Vercel build; they are not secrets. `VITE_WS_URL` is optional: the resolver derives `wss://<api-host>/ws` from `VITE_API_URL` when it is empty.
- **Brevo HTTPS API (deployed).** Development and production deliver verification email through the Brevo HTTPS API on port 443; SMTP remains the local/off-Render transport. The backend sends `POST https://api.brevo.com/v3/smtp/email` with the `api-key` header, the branded `htmlContent`/`textContent` template and a fixed `10000` ms `AbortSignal.timeout`; no SDK, body parse or provider template is added. `EMAIL_TRANSPORT=brevo-api` selects it, `BREVO_API_KEY` is the Brevo **REST API key** from **Settings → SMTP & API → API Keys** (not the SMTP key), and `SMTP_FROM` must be a Brevo-verified sender that parses as an address or `Display Name <address>` and is not the local Mailpit default. The deploy CLI validates all eleven names and syncs nine (`eleven validated, nine synced`); `RENDER_API_KEY` and `RENDER_SERVICE_ID` are never written to the Render service. A transport rejection maps to HTTP `502` with code `verification_email_failed`; the account stays persisted and unverified, the just-issued token is invalidated, and one `warn` `verification_email_delivery_failed` line carries `route`, `transport`, `errorType`, optional `transportCode` (`HTTP_<status>` for API failures), `host` and `port`; the non-blocking startup probe logs `brevo_api_transport_verify_ok` or `brevo_api_transport_verify_failed`.
- **Render runtime configuration** is committed for the non-secret values in `render.yaml` (`NODE_ENV=production`, `HOST=0.0.0.0`, `PORT=8080`, `METRICS_ENABLED=false`, `MAX_USERS_PER_SERVER=10`, `DB_SCHEMA_BOOTSTRAP_ENABLED=true`, `DB_EXPIRED_TOKEN_CLEANUP_ENABLED=true`, `DB_EXPIRED_TOKEN_CLEANUP_INTERVAL_MS=3600000`) and set in the Render dashboard for the remaining `sync: false` names (`DATABASE_URL`, `DIRECT_DATABASE_URL`, `CORS_ORIGIN`, `ALLOWED_ORIGIN`, `APP_BASE_URL`, `SESSION_COOKIE_SECURE`, `SESSION_COOKIE_SAMESITE`); `render.yaml` keeps `sync: false` and no value for every name. The nine deployed names (`SMTP_*` plus `EMAIL_TRANSPORT` and `BREVO_API_KEY`) are synced from the GitHub Environment, while those remaining `sync: false` names `stay dashboard-owned` and are `never synced`. `DATABASE_URL` (pooled) serves application queries and `DIRECT_DATABASE_URL` (direct) serves the startup phase (advisory lock, migrations and schema bootstrap). Secrets are never baked into the image or echoed in logs.
- `CORS_ORIGIN`, `ALLOWED_ORIGIN` and `APP_BASE_URL` are static Render service variables set to the exact `FRONTEND_ORIGIN`; the workflow no longer derives or stages them, so changing the frontend origin is a Render variable change plus a workflow variable change.
- Tokens are read through `env:`/`secrets.*` only: `RENDER_DEPLOY_HOOK_URL` is passed as `env:` to `curl` and never echoed, `RENDER_API_KEY` is read from the step `env:` and used only as the Render authorization header, and the Vercel commands read `VERCEL_TOKEN`, `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` from the environment.

## Deploy pipeline

- `../../.github/workflows/ci.yml` runs on pull requests and pushes to `main`: `verify-app` (`npm ci` → lint → typecheck → test → coverage → build), `smoke-e2e` (Mailpit-primed containerized smoke) and `verify-workflows` (`npm ci` on Node 24 → pinned `rhysd/actionlint:1.7.12` over both workflows → `src/frontend/vercel.json` JSON parse → `render.yaml` YAML parse that checks the service name/runtime/plan and that no platform health check is declared → a `deploy.yml` dispatch parse that pins the dispatch inputs/defaults, the `production` default, the input→environment mapping and the automatic path → a guard that `deploy.yml` never mentions Fly → `Guard rejects placeholder values` (credential-free `--check-only` fixture that must exit non-zero and print the exact `'production'` block header) → `Guard accepts a complete value set` (the same CLI with the complete `development` fixture, asserting the exact success line)). Workflow-level `permissions: contents: read`; every third-party action is pinned to a full commit SHA.
- `../../.github/workflows/deploy.yml` triggers on `workflow_run` of `CI` completing on `main`, plus `workflow_dispatch` for `development` or `production`. It runs one `deploy` job in the environment selected by the event (`development` after CI or a development dispatch, `production` for a production dispatch). A manual dispatch runs `Resolve selected build` (production: empty `build_sha` resolves the latest successful `CI` push build on `main`, a set value is used exactly; a development dispatch uses the dispatch SHA and rejects a non-empty `build_sha`), `Verify CI succeeded for target commit` on the resolved SHA (one `gh run list --repo "$GITHUB_REPOSITORY" --event push --branch main` plus the compare API `ahead`/`identical`), the selected-SHA `Checkout`, `Confirm selected build checkout` and `Check selected build deploy contract` (guard/sync, migration runner and deployed smoke identical to the dispatch ref; `pg` present); the automatic path skips those steps and checks out `workflow_run.head_sha`. The fixed order then continues: `Check deployment Brevo configuration` (eleven values, no network) → `Check selected build schema compatibility` (manual dispatch only) → Neon migration (`DIRECT_DATABASE_URL`) → `Sync Brevo SMTP settings to Render` (nine deployed names via the Render API) → `Deploy Render backend` (manual dispatch: Render deploy-by-commit API with `commitId`; automatic: the deploy hook) → `Wait for Render deploy to complete` (manual: poll to `status: live` and prove the current deploy/SHA; automatic: 45 s head start) → `/healthz` poll (180 s) → Vercel pull/build/deploy `--prod` from the same checkout with `--meta githubCommitSha` → warm `/healthz` → deployed smoke (`../../tests/e2e/deployed-smoke.mjs`). A production dispatch is manual only, resolves to the `production` Environment, is gated by its `main`-only deployment branch policy and required reviewers, and runs the same fixed order with the production values. The T6a one-line preflight fix remains: `--repo "$GITHUB_REPOSITORY"` in the pre-checkout `gh run list` of `Verify CI succeeded for target commit`; the guard condition, permissions, triggers and concurrency are unchanged, and the automatic `workflow_run` path still resolves to `development`.
- **No duplicate CI.** The deploy job does not call `ci.yml` and does not run lint/typecheck/test/coverage/build again; those gates run once in the CI workflow that triggered it. The manual path (either environment) checks the CI conclusion for the target SHA (`gh run list`) before deploying.
- **No alias step.** `vercel deploy --prebuilt --prod` updates the project's production domain (`cubeclicker-development.vercel.app` for development, `cubeclicker.vercel.app` for production), so the workflow has no separate `vercel alias` command and no duplicate host mapping.
- Every Vercel command runs from the repository root (the project Root Directory is `src/frontend`, applied once by the project settings). The project's `vercel.json`, build command, output directory, SPA rewrite and cache headers are the ones used.
- The Vercel build receives `VITE_CLOUD_DEPLOY=true`, `VITE_API_URL` and the optional `VITE_WS_URL`. Cloud mode fails the build when the API URL is missing/relative or the resolved WS URL is not `wss://`.
- The preflight fails closed: a missing or `CHANGEME` value stops the job before any provider is touched, and the sync runs after the Neon migration and before `Deploy Render backend`. `deploy.yml` contains only Neon, Render and Vercel steps.

### Build SHA selection (production)

Production dispatches accept the optional `build_sha` string in addition to `environment`; it is production-only.

- The `build_sha` input is optional; empty selects the newest successful `CI` push build on `main`, and a set value selects that exact 40-character lowercase commit SHA. The `build_sha` value may name a commit that is not the latest on `main`. The run prints `Resolved build: <sha> (<source>)` (`latest` when empty, `pinned` when set, or `dispatch-ref` on a manual development dispatch) and, for the latest resolution, `CI run: <id> <createdAt>`.
- `build_sha` must be a full 40-character lowercase commit SHA. It is rejected before checkout when malformed (`build_sha must be a full 40-character lowercase commit SHA.`), and a manual development dispatch with a non-empty value fails with `Build SHA selection is available for environment=production only; clear build_sha for a development dispatch.`
- The deploy-contract gate requires the selected build's guard/sync, migration runner and deployed smoke to match the dispatch ref. The schema gate requires the selected build's migration set to contain every migration already applied. Applied migration files are immutable; new schema changes are new numbered files. Comparing names is sufficient under that policy; relaxing it requires content hashes. A selected build that predates the current contract or an applied migration fails closed before the migration and before any provider call.
- The dispatch ref must be `main`, and the selected SHA must be on `main`. The `production` Environment's `main`-only deployment branch policy enforces the first; `Verify CI succeeded for target commit` enforces the second with a successful `CI` push run on `main` (`--event push --branch main`) plus the compare API `ahead`/`identical` for the resolved SHA; a dispatch from another ref fails the guard.
- The same SHA reaches both providers: `Deploy Render backend` calls the Render deploy-by-commit API (`POST /v1/services/{id}/deploys` with `commitId` and `clearCache: do_not_clear`) and a `202` fails closed because it carries no deploy ID; `Wait for Render deploy to complete` polls the selected deploy to `status: live` (default 10 s interval, 900 s timeout), then requires `GET /v1/services/{id}/deploys?limit=1` to return the selected deploy ID and SHA and prints `Render deploy live: <deploy-id> for <sha>`. The Vercel deploy runs from the same checkout and records the SHA with `--meta githubCommitSha`. The automatic `workflow_run` path keeps the deploy hook and its existing 45 s head start; the API/completion proof is for manual dispatches.
- Select the known-good build with `build_sha`: dispatch the known-good full SHA (for example `-f build_sha=<40-hex-sha>`) through the same guarded pipeline; this is the coordinated rollback because it re-runs the guard, contract, schema, migration, Render completion proof and smoke. To return to the newest successful build, omit `-f build_sha`. Per-provider rollback remains emergency-only (§ Rollback).

```bash
gh workflow run deploy.yml --ref main -f environment=production -f build_sha=<40-hex-sha>
```

Provider runbook: [`vercel-render-neon.md`](vercel-render-neon.md) § Production deploy with build SHA selection.

## Neon migrations

- One Neon project with the `production` branch (the pre-existing project default `br-floral-dream-zarerhtw`, migrated with the seven numbered migrations and zero application rows at provisioning) and the `development` branch `br-ancient-smoke-za1pdv7w` created from it. Application and migration URLs always carry `sslmode=require`.
- `DATABASE_URL` is the pooled `-pooler` URL for the Render service's runtime queries. `DIRECT_DATABASE_URL` is the direct URL for the CI migration job and the Render startup phase (advisory lock, migrations and schema bootstrap), which runs on a dedicated `pg.Client` so `BEGIN`, every statement and `COMMIT` share one connection (PgBouncer transaction pooling is not used for migrations).
- Ordering is fixed: **migrate (CI) → schema bootstrap → listen → backend deploy → frontend deploy**. CI runs `npx --no-install tsx src/backend/src/db/migrate-cli.ts` with `DIRECT_DATABASE_URL` before triggering Render; the image also packages `dist/db/migrations`, so the startup phase's migration step is an idempotent safety net and a no-op after CI. `node dist/db/migrate-cli.js --list` lists migration names without opening a connection. The startup schema bootstrap then verifies the five required tables before the process accepts traffic.
- With neither URL set (local host-only runs), the startup phase is skipped and the backend uses in-memory repositories; no cleanup scheduler is created. This preserves the no-database mode.
- Migrations are forward-only and add-only. Applied migration files are immutable; new schema changes are new numbered files. The production build SHA selection schema gate compares migration names under this policy. The Neon `production` branch is not protected on the free plan — an accepted deviation recorded in the feature spec. See § Rollback for the database recovery path.

## Database startup phase and schema bootstrap

The backend runs the database lifecycle phase itself at every boot, before it accepts traffic: build the app (logger + pool) → one dedicated direct-URL `pg.Client` → acquire a session-level Postgres advisory lock (retrying every 250 ms for at most 30 s) → apply pending migrations → run the schema bootstrap → best-effort unlock and end the client → `listen`. The bootstrap checks the five required tables (`users`, `sessions`, `verification_tokens`, `user_economy`, `schema_migrations`), creates any missing table and its indexes with idempotent `CREATE ... IF NOT EXISTS` DDL in one transaction per table, and reports required columns missing from an existing table without altering it. The numbered migrations remain the only schema-evolution authority; a table recreated by the bootstrap uses the final consolidated shape.

- **URL requirement: direct/session-capable.** The phase prefers `DIRECT_DATABASE_URL` and falls back to `DATABASE_URL`. The fallback must be a direct/session-capable URL: the advisory lock is session-scoped and DDL must not cross PgBouncer transaction boundaries. On Neon both URLs are set and the direct one wins; local compose points directly at the compose Postgres, so the fallback works there. A deployment that sets only the pooled `-pooler` URL cannot use the lock/DDL phase (the runner does not sniff provider hostnames): provide the direct URL or set `DB_SCHEMA_BOOTSTRAP_ENABLED=false` and rely on the CI migration.
- **Fail-fast vs warn-and-continue.** Connect, lock, migration and table-creation failures log `db_startup_failed` / `db_schema_bootstrap_failed` with `stage` (`connect`, `lock`, `migrations` or `bootstrap`), `errorType` and an optional SQLSTATE `code`, then close the app and exit `1` without `listen`; the deploy workflow's `/healthz` poll fails the deploy. A connect failure, a 30 s advisory-lock timeout, a failed migration and a denied `CREATE` are all fatal. An outdated table (missing required columns) logs `db_schema_table_outdated` at `warn` and startup continues; the migrations are the repair path.
- **Cleanup is in-process and best-effort.** After `listen`, the same process deletes expired `verification_tokens` rows (`expires_at <= now`) once immediately and then `DB_EXPIRED_TOKEN_CLEANUP_INTERVAL_MS` after each run settles (default one hour; 60,000–86,400,000 ms), with an in-flight guard, `unref()`ed timers and non-fatal failures (`db_verification_cleanup_failed`; the next run is still scheduled). `SIGTERM`/`SIGINT` stops the scheduler through the shutdown `beforeClose` hook before the pool closes. The Render free instance spins down after 15 idle minutes, so the schedule is best-effort and the immediate run on the next start catches up. No cron service, worker, pre-deploy command or second Render service is added.
- **Advisory-lock safety under Render's old/new overlap.** On a deploy Render builds first and then starts the new instance before the old one is fully retired (see `vercel-render-neon.md` § Architecture). Both processes may therefore run the startup phase concurrently; the session advisory lock serializes them, so the second instance waits (bounded at 30 s) until the first releases the lock and then finds the schema complete. That provider-level overlap is **not** application-level zero-downtime for clients: when traffic switches, the old instance's WebSockets close, clients follow the bounded reconnect policy and rejoin, and the new instance starts with empty in-memory rooms (§ Single-instance trade-off). The advisory lock makes the DDL phase safe under either provider behavior; it does not make a deploy invisible to connected clients.
- **Configuration.** `DB_SCHEMA_BOOTSTRAP_ENABLED` (default `true`), `DB_EXPIRED_TOKEN_CLEANUP_ENABLED` (default `true`) and `DB_EXPIRED_TOKEN_CLEANUP_INTERVAL_MS` (default `3600000`) are non-secret values committed in `render.yaml` and defaulted in `compose.yaml`; invalid or empty values fail startup naming the variable.

## Rollback

Manual, immediate and routing-only where possible; the full runbook is in `vercel-render-neon.md` § Rollback.

- **Frontend:** `vercel rollback <previous-deployment-url-or-id>` (production target) or `vercel promote <deployment-url>`; re-point the development host manually with `vercel alias set <deployment> <host>` only if a routing mistake needs correcting.
- **Backend:** redeploy the last known-good commit (revert on `main` and let CI → Deploy rebuild, or redeploy the previous deploy from the Render dashboard). `render deploys list srv-dbtcvv9srm7s73au5bag` lists deploys; the free plan has no release-image registry, so the git commit is the release identity.
- **Order:** roll back the backend first when the API/WebSocket is broken, then the frontend when only the UI is broken. API changes are additive, so the previous frontend stays compatible during the window.
- **Database:** no automatic down migrations. If a schema change must be undone, create a Neon branch from the pre-migration point in time (PITR), validate it, then repoint `DATABASE_URL`/`DIRECT_DATABASE_URL` (GitHub Environment secrets and Render service variables) to the restored branch. The pre-existing Neon `production` branch is never dropped, re-created or rolled back to a development branch.
- **Production:** select the known-good build with `build_sha` in a production dispatch (§ Build SHA selection (production)); because it re-runs the guard, contract, schema, migration, Render completion proof, Vercel same-SHA build and smoke, it is the coordinated rollback across both providers. Per-provider `vercel rollback`/`promote` on the production Vercel project and a Render dashboard rollback or known-good redeploy of `cubeclicker` are emergency tools only: they are immediate but one provider at a time, skip the guard/sync/migrations/smoke and can mix revisions; use them with same-SHA artifacts and re-run the deployed smoke afterwards. Neon stays forward-only. **No rollback to development**: production's `FRONTEND_ORIGIN`, `VITE_API_URL`, `DATABASE_URL` and `DIRECT_DATABASE_URL` are never pointed at development, and development is never used as a production fallback. After the live deploy is green, no production resource is deleted; failures are fixed forward.
- **After any rollback:** re-run the deployed smoke and check `/healthz`; a Render rollback restarts the instance, so clients reconnect and in-memory rooms reset (expected).

## DNS and cookies

- `FRONTEND_ORIGIN` is the single stable public frontend origin per environment (the Vercel production domain or a custom domain); unique per-deployment preview URLs are never used as a CORS/CSRF origin. `VITE_API_URL` is the stable Render (or custom `api.`) origin. Both environments use platform-default hosts: development `cubeclicker-development.vercel.app` / `cubeclicker-development.onrender.com`; production `https://cubeclicker.vercel.app` / `https://cubeclicker.onrender.com`.
- Recommended production topology: first-party subdomains under one registrable domain (`app.<domain>` on Vercel, `api.<domain>` on Render), so the session cookie is first-party and `SameSite=Lax` remains viable.
- Default `*.vercel.app` → `*.onrender.com` hosts are cross-site: production uses `SESSION_COOKIE_SECURE=true` and `SESSION_COOKIE_SAMESITE=none`, the same cross-site pair development carries, and Safari/iOS ITP or Chrome third-party cookie blocking can still drop the session cookie. That is a documented product risk, not a code bug.
- `CORS_ORIGIN`/`ALLOWED_ORIGIN`/`APP_BASE_URL` are set on the Render service to the exact `FRONTEND_ORIGIN`, so they cannot drift from the frontend host without a visible configuration change. CORS is an exact-origin allowlist with credentials, `Vary: Origin`, and no wildcard; the WebSocket upgrade checks a present `Origin` against the same allowlist (HTTP `403` before the upgrade, no `hello`) while allowing non-browser clients that omit `Origin`.
- The browser opens `wss://<api-host>/ws`; an `https://` page cannot use `ws://`, and the resolver rejects it in cloud builds. Render terminates TLS and proxies WebSocket upgrades without extra configuration; the existing 30 s heartbeat and reconnect policy are unchanged.
- HTTPS is provided by Render and Vercel. No certificate or DNS asset is created by this repository's pipeline; domains are user-owned.

## Single-instance trade-off

- The backend runs as exactly one free Render instance (`plan: free`, Frankfurt, `512 MB` / `0.1 CPU`). In-memory rooms are the reason: a second instance would serve a different room registry and clients would stop seeing each other.
- A deploy or cold start restarts the process and closes every WebSocket. Clients reconnect automatically (10 attempts, 500 ms → 5 s backoff) and in-memory rooms reset; there is no zero-downtime deploy, by design and by the room model. Render's brief old/new instance overlap during a deploy does not change this: the provider may run both processes for a moment, but clients still lose and re-establish their sockets and the new instance starts with empty rooms (§ Database startup phase and schema bootstrap records the advisory-lock safety of that overlap).
- Free instances **spin down after 15 minutes without traffic** and cold-start in roughly 30–60 s on the next request or WebSocket connection. The client's ~38 s retry budget can be exhausted by a cold start, in which case the connection banner shows `Connection lost` with a `Retry` button. Both free services (development and production) have this behavior; the two free Render services share the workspace's **750** instance hours per month, so a busy production service can starve development and the owner may move production to a paid plan (Q-1).
- Health is `GET /healthz` → `200` `{"status":"ok"}`, asserted by the deploy job (`200` within 180 s) before the frontend step. Render has **no platform health check** configured for the service (`healthCheckPath` is empty) and `render.yaml` declares none, so the deploy job's poll is the health gate. The deployed smoke then proves health, CORS (allowed and disallowed), SPA fallback, a real `/assets/*` 404 and a WebSocket hello/join/click plus the disallowed-Origin `403`.

## Security and credential posture

- No secret value is committed, baked into an image, or logged; GitHub masks registered secrets and the workflows never enable shell tracing. `.env*` files remain user-owned and off-limits.
- The canonical scoped credential audit is retained verbatim from `workflow-hygiene`. Its AWS patterns cover credentials from the superseded deployment era and its Fly pattern covers the abandoned backend; neither may reappear in any tracked non-doc file:

  ```sh
  git grep -nE "AKIA|aws_secret_access_key|AWS_SESSION_TOKEN" -- . ':(exclude)docs/'
  ```

  The connection-string audit is scoped to runtime/config trees and excludes colocated test fixtures: `git grep -nE "postgres(ql)?://[^\"' ]+:[^\"' ]+@" -- .github infra src ':(exclude,glob)**/*.test.ts' ':(exclude,glob)**/*.test.tsx'`. The token audit uses the credential-shaped pattern `(VERCEL_TOKEN|RENDER_API_KEY|RENDER_DEPLOY_HOOK_URL|FLY_API_TOKEN|BREVO_API_KEY|SMTP_PASS|SMTP_USER)=["']?[A-Za-z0-9+/_-]{12,}` plus the key shape `FlyV1 [A-Za-z0-9_-]{20,}` over the tracked tree, untracked files, branch diff and branch history, with the documented `docs/` prose and colocated `*.test.ts`/`*.spec.ts` synthetic-fixture exclusions; it returns no matches on the current tree. The Fly/Vercel/Render coverage is retained verbatim from `workflow-hygiene`, while the credential-shaped alternation adds the Brevo/SMTP names.
- CORS never uses `*` with credentials; `SameSite=None` requires `Secure`; the WebSocket `Origin` guard is always on for present origins. The `development` and `production` secrets are separate and both are live. Production's values are set in the `production` Environment and synced to the production Render service; the credential posture (owner-held credentials, builder never reading values, no secret in git, images or logs) is unchanged.
