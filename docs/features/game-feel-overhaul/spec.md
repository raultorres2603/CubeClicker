# Spec — Game-Feel Overhaul (3D Lootbox Reveal + Neon Forge Game Shell)

## Summary

Two user-requested presentation workstreams, specified as one feature: **(A) a 3D lootbox reveal** that stages the won part on the player's own spaceship in the existing customization visualizer, synced to the accepted 1290 ms reveal timeline, with rarity and duplicate presentation, explicit dismiss/equip controls, and reduced-motion and WebGL-unavailable fallbacks; and **(B) a cohesive "Neon Forge" game-shell overhaul** — chamfered graphite-glass panels, cyan energy rims, warm amber reward accents, a violet epic channel, a HUD resource strip, panel headings, rank medals, a crew chip, a status chip and a procedural CSS ambience layer — applied to the HUD, upgrades, customization, activity feed, leaderboard, users panel, connection banner and auth menu. Raw request: *"Also, when openning a lootbox, it should have an animation of showing the item you won, in 3D, like customization visualizer with the space ship itself"* and *"Also, I would like to improve UI to make it more \"game\" looking, it seems very simple."*

The reveal adds **no protocol, server, persistence, dependency or container change**. The already-shipped, server-authoritative, opener-only `lootboxOpened` message (plus the guest engine's local grant) is the sole grant carrier; the client reuses `lastLootboxGrant` and derives the staged look from the pinned part catalog. The shell overhaul is CSS/DOM-only: existing corner placements, responsive breakpoints, new-control 44 px targets (the existing 24 px HUD minimize is retained), focus visibility, contrast gates and the adaptive render/bundle budgets are preserved. No external image, audio, font or model asset is added; the stage and fallback are procedural three.js and inline SVG/CSS.

**Scope note.** The request names two things; the brief frames them as one feature with two deliverables. They share the shell and the customization panel, so one spec is the default; Q-16 records the split alternative.

## Context and decisions already accepted

- The grant carrier already exists: `openLootbox` → server-side `applyLootboxOpenV2` → opener-only `lootboxOpened { partId, slot, rarity, duplicate, lootboxes, keys, parts, appearance }` and an account-wide `customizationUpdate`; a guest open sets the same `lastLootboxGrant` locally (`spaceship-cursor-loot-animations` AC-18/AC-24/AC-27/AC-32). The current panel renders a 2D charge-orb/card reveal from that state.
- The cursor model and the customization preview are the accepted visual source of truth: `createCursorShipModel()` (21 meshes, 10 slot groups, `applyAppearance`) and `appearanceToCursorShipParams()` (10-slot mapping). The preview (`render/preview.ts`) already builds a single-context 30 fps scene.
- The customization panel is a deferred chunk (`DeferredSpaceshipCustomizationPanel`), so any three.js import it makes stays out of the entry graph; the bundle gate is `initial ≤ 150,000 B`, `three ≤ 165,000 B`, `total ≤ 300,000 B` gzip.
- The adaptive high/medium/low tier and the frame loop are untouched; the reveal runs in its own small context while the panel is open, capped at 30 fps.
- The shell's occupied bands and responsive rules are pinned: HUD top-left, connection banner top-centre, activity feed below it, leaderboard left rail, users top-right, customization toggle bottom-left, upgrades bottom-right, phase announcement bottom-centre; the `max-width: 720px` bottom-band stacking and the `main[data-customization-open='true'] .upgrades-panel { display: none; }` rule are retained.

## User stories

- As a player, when I open a lootbox I see the won part applied to my own ship in 3D — not an instant text result — so the unlock feels earned and memorable.
- As a player, I can tell at a glance whether the part is rare or epic, new or a duplicate, which slot it belongs to, and how many copies I own.
- As a player, I can equip the won part straight from the reveal, or dismiss it and keep playing; Escape, the button and Equip all behave predictably.
- As a guest, I get the same reveal locally with no account and no persistence.
- As a player with reduced motion, the reveal settles instantly to a static 3D result; as a player without WebGL, I still get a coherent fallback and the full card.
- As a player, the whole shell — HUD, panels, buttons, feed, leaderboard, crew, connection state and auth menu — reads as one game interface rather than a plain web page.
- As a keyboard/screen-reader player, every new control is reachable, 44 px, visibly focused and announced; nothing relies on colour alone.
- As a maintainer, the reveal is one pure pose function, one small stage module and one component with a single context; no server, protocol, persistence or container path changes.

## Deliverable A — 3D lootbox reveal

### Reveal flow (pinned)

1. The player presses `Open lootbox` in the customization panel. An account sends `{ type: 'openLootbox' }`; a guest calls `engine.openLootbox()`.
2. The server (account) or engine (guest) performs the existing weighted draw and produces the existing `lastLootboxGrant` with `{ partId, slot, rarity, duplicate, sequence }`; the account path also adopts the absolute inventory from `lootboxOpened`.
3. The panel's reveal branch mounts `LootboxReveal` for that `sequence`; the normal panel content (header, counts, open button, slot list, preview) is replaced, not merely overlaid.
4. The reveal panel becomes a non-modal centred spotlight while `customizationOpen && lastLootboxGrant !== null`; there is no full-screen pointer-blocking scrim, the game and the customization toggle remain interactive, and on mobile the panel stays the bottom sheet.
5. `LootboxReveal` builds the stage with the **staged try-on appearance** — the player's current appearance with only the catalog slot of `grant.partId` replaced by `grant.partId` — and plays the pinned 1290 ms timeline. The player's real appearance is **not** mutated.
6. The card shows `Rare`/`Epic`, the part name, the slot name, `New`/`Duplicate`, `Owned ×N`, and the `Equip`/`Dismiss` controls.
7. `Equip` calls the existing `onEquip(partId)` and then dismisses the reveal; `Dismiss` (or Escape) dismisses without equipping. Closing the customization panel while revealing also dismisses (the toggle remains clickable). A `welcome`, a non-connected transport status, or a new grant replaces the old reveal; there is no replay from persisted state.

### Why `lootboxOpened` and not diffing `customizationUpdate`

`lootboxOpened` is the accepted, opener-only, server-authoritative grant and carries exactly the identity the reveal needs. Diffing `customizationUpdate` would be ambiguous (two tabs opening concurrently produce two inventory deltas on the same connection; a reconnect or coalesced update can merge changes; a duplicate changes only a count, not a part id), would deliver a reveal to tabs that did not open the box (violating the accepted opener-only rule) and would require a new client-side correlation scheme. The desktop and mobile paths are identical because both already consume `lastLootboxGrant`. **No additive message is needed and no version bump is made.**

### Stage design (pinned)

- New pure module `game/reveal-motion.ts`: `REVEAL_SLOT_YAW_RAD`, `REVEAL_START_YAW_RAD`, `REVEAL_RARITY_HEX`, `createRevealStagePose()` and `revealStagePose(elapsedMs, slot, reducedMotion, out)`.
- New render module `render/lootbox-reveal.ts`: `createRevealStage(appearance, grant)` returns one scene, one camera, the cursor model, the staged appearance and one rarity ring. It reuses `createCursorShipModel()` and `appearanceToCursorShipParams()`; it does not create a second visual mapping.
- New UI component `ui/LootboxReveal.tsx`: owns exactly one `WebGLRenderer` and one `requestAnimationFrame` loop, renders at most 30 fps, pauses while `document.hidden`, renders exactly one frame and stops under reduced motion, and disposes the stage and renderer on unmount. If renderer or stage construction throws, it renders the inline-SVG fallback and the full card.
- The reveal is deliberately non-modal: there is no `aria-modal`, no focus trap and no full-screen pointer-blocking scrim. It is a `role="group" aria-live="off"` region labelled `Lootbox reveal: <part name>`, moves focus to `Equip`, restores focus to `Open lootbox` after an in-panel dismissal, closes on Escape, and leaves the customization toggle and the game clickable. Q-6 offers a true-dialog alternative.

### Pose timeline (pinned)

All times in ms; `easeOutCubic`, `easeInOutCubic` and `sin` are the accepted easing implementations. The accepted DOM phases are retained: charge 420, orb 250, flash 120, reveal 360, settle 140, total 1290.

| Phase | Window | `yawRad` | `scale` | `slotPulse` | `ringScale` | `ringOpacity` | `flashOpacity` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| charge | 0–419 | `REVEAL_START_YAW_RAD` → slot yaw, `easeInOutCubic` | `1 → 1.04` | 1 | 0.4 | 0 | 0 |
| orb | 420–669 | slot yaw | `1.04 → MOTION.revealStageOrbScale` (`1.10`), `easeOutCubic` | 1 | 0.4 | 0 | 0 |
| flash | 670–789 | slot yaw | 1.10 | 1 | 0.4 | 0 | `0.85 · sin(πt)` |
| reveal | 790–1149 | slot yaw | `1.10 → 1`, `easeOutCubic` | `1 + 0.10 · sin(πt)` (peak 1.10) | `0.4 → 2.4`, `easeOutCubic` | `0.9 · sin(πt)` | 0 |
| settle | 1150–1289 | slot yaw | 1 | 1 | 2.4 | 0 | 0 |
| rest | ≥ 1290 | slot yaw | 1 | 1 | 1 | 0 | 0 |

`REVEAL_SLOT_YAW_RAD` is exactly: `hull 0.35`, `nose 0.15`, `cockpit 0.45`, `wing-left 0.85`, `wing-right −0.85`, `engine-left 0.7`, `engine-right −0.7`, `ignition-left 1.0`, `ignition-right −1.0`, `tail-fin 1.2`. `REVEAL_START_YAW_RAD === 0.55` (the preview rest yaw). Reduced motion always returns the rest row for any elapsed time. The ring is fully faded by 1150, so settle and rest keep `ringOpacity === 0`.

## Security considerations

- **User-controlled data.** No new client input. The only dynamic reveal values are the server-issued `partId`, `slot`, `rarity` and `duplicate`; `partId` is validated with `isValidPartId`, and the catalog slot is derived with `partDefinition(partId).slot` (the wire `slot` is not trusted). An invalid part renders the fixed text `Unknown part` with `data-part-id="unknown"`, `data-slot=""`, `data-owned-count="0"`, no stage and no raw server string in any attribute or text. The part name and slot name come from the pinned catalog. The appearance map is normalized through `normalizeAppearance` before staging.
- **Persistence integrity.** No persistence, schema or storage is added; guest state stays ephemeral; the reveal is never replayed from `welcome` or any stored value. Reconnect clears it.
- **No secrets or dependencies.** No package, lockfile, environment variable or secret is added; no external URL, font, image or model is fetched; all geometry/materials are procedural and all CSS is gradients/inline SVG.
- **Resource bounds.** One reveal/panel WebGL context in addition to the main scene's own context; one cursor model (≤ 2500 triangles), one ring (96 triangles), ≤ 24 draw calls, 30 fps, paused while hidden, disposed on unmount; no unbounded arrays or timers (the reveal phase timers are cleared on unmount; the panel dismisses on unmount).
- **Rendering safety.** No `innerHTML`, `eval`, `fetch`, loader or `Texture`; the fallback SVG is a static React element; the stage uses named three.js imports only.
- **Test integrity.** Concrete values, exact DOM/CSS contracts and unchanged coverage thresholds; superseded CSS assertions are rewritten to the new pinned declarations, not deleted without replacement.

## Real-time impact

- **New shared/cross-client state:** none. The reveal, staged appearance, ring, pose and ambience are client-local presentation. The grant and inventory remain server-authoritative and opener-scoped exactly as accepted (`spaceship-cursor-loot-animations` AC-18/AC-26).
- **Connection lifecycle:** `lootboxOpened` stays opener-only; `customizationUpdate` stays account-scoped; guests stay local. A `welcome` (fresh join or rejoin) clears a present reveal, and any non-connected transport status clears it, so a reconnect never replays a stale animation. Grace, heartbeat, capacity and rebalance are unchanged.
- **Reconnection:** the persisted inventory arrives in `welcome`; the reveal is one-shot and is not reconstructed from persisted state. A dropped `lootboxOpened` leaves the inventory correct via `customizationUpdate`/`welcome` and loses only the animation, as before.
- **Multi-client:** a second tab of the same account receives `customizationUpdate` and no grant; it never renders the reveal. One connection remains one member for the leaderboard/roster. Last-write-wins per slot via `setSlotAppearance` is unchanged.
- **Server authority:** the server still chooses the part, rarity, duplicate flag and absolute inventory; the client never sends counts, rarity, odds or a staged appearance. Equip/unequip remain validated server-side.
- **Identity vs. "no accounts":** guests get the same catalog, odds, reveal and local equip with no persistence; no account is required. No identity conflict is introduced.

## Protocol, metrics and privacy evaluation

- **Protocol additivity:** no message is added; the existing `lootboxOpened` is reused. No version bump. The client catalog is unchanged. A decoder that drops an unknown field is unaffected, and no field is repurposed.
- **Metrics allow-lists:** `cubeclicker_ws_messages_encoded_total{type}` and `cubeclicker_ws_frames_sent_total{type}` already include `lootboxOpened`; no new metric or label value is added. `customizationUpdate` is unchanged.

## Assumptions

- The existing `lootboxOpened` grant and `lastLootboxGrant` are sufficient for the 3D reveal; no additional server field is needed.
- `createCursorShipModel`/`appearanceToCursorShipParams` are reusable with the staged appearance, and the slot-group base transforms are read after `applyAppearance` so the pulse multiplies rather than replaces them.
- The customization panel is the only reachable surface for opening a lootbox, so a reveal inside it is reachable whenever a grant exists; closing the panel is therefore a dismissal.
- The panel's `backdrop-filter` creates a containing block for fixed descendants, so the spotlight uses absolute centring rather than `position: fixed`; the panel has no transform in the normal state.
- The reveal can mount while the quality tier is high/medium/low; it uses its own small scene and does not read or change the tier.
- One WebGL context is enough: the panel unmounts the preview while the reveal is active and remounts it after dismissal.
- `requestAnimationFrame`, `ResizeObserver`, `document.hidden` and `WebGLRenderer` are available in production; tests inject/stub them and the fallback covers construction failure.
- The user's "improve UI" means the play shell (HUD, panels, feed, leaderboard, users, banner, auth, resources, ambience), not gameplay rules or economy balance.
- No external asset is needed: all new visuals are three.js geometry, inline SVG or CSS gradients; the system font stack remains.
- The accepted nine `--panel-*` tokens and `theme.ts` constants remain unchanged; the Neon Forge palette is additive, so existing contrast gates remain valid and are extended.
- Manual screenshots, keyboard passes and frame traces are acceptable evidence under the project's no-browser-automation convention.
- Stack, container, auth and real-time conventions are unchanged (DECIDED); this is a frontend source-only presentation change.
