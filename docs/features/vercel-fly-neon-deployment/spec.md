# Spec — Vercel + Fly.io + Neon Deployment Migration

## Summary

Migrate CubeClicker's cloud deployment from AWS (ECS Fargate + ALB + RDS + ECR, defined in Terraform and driven by GitHub Actions) to a split platform: **Vercel** hosts the React/Vite SPA as a static build, **Fly.io** hosts the existing Fastify + `@fastify/websocket` backend container (persistent process, `${PORT}` 8080, `GET /healthz`, `GET /ws`), and **Neon** provides PostgreSQL for accounts, sessions, verification tokens, economy and customization only. GitHub Actions becomes the single CI/CD pipeline with two GitHub Environments — `development` (auto-deployed from `develop`) and `production` (protected by required reviewers, deployed from `main`) — holding per-environment secrets and variables. The AWS Terraform tree and AWS workflows are superseded: AWS resources are not provisioned or deleted by this feature, and `infra/terraform/` is retained in place as archived, non-deployed infrastructure pending a user-owned delete-or-archive decision.

The migration is not a rewrite. Game logic, server authority, in-memory rooms, the WebSocket protocol, the auth model, the database schema and the local `podman compose up` path stay unchanged. The application surfaces that must change are the ones that assumed a same-origin, single-host deployment: the frontend must resolve `VITE_API_URL`/`VITE_WS_URL` per environment and send credentialed cross-origin requests; the backend must answer CORS preflights with an exact allowlist, emit the session cookie with configurable `SameSite` (`None; Secure` for cross-site default domains, `Lax` for same-site custom domains), and validate the WebSocket `Origin`; the deployment artifacts must describe a single always-on Fly machine (in-memory rooms cannot be horizontally scaled), a Vercel SPA build with a real `/assets/*` 404 and correct cache headers, and direct-vs-pooled Neon connection strings. Raw request: *"We'll use Vercel to deploy all the stack by using GitHub Actions as the CI/CD Pipeline. Also, we'll use Github environments and environment variables to create development and production environments. I need you to adapt infraestructure to deploy on Vercel. Also Github Action's to point to vercel instead of AWS"* — clarified by the user to: Vercel frontend, Fly.io backend, Neon Postgres, GitHub Actions CI/CD with `development`/`production` environments.

## Scope

### In scope

1. **Vercel frontend delivery.** A committed `src/frontend/vercel.json` and a Vercel project whose Root Directory is `src/frontend`; monorepo install from the root `package-lock.json`; build command `npm run build` (which runs `vite build` plus the existing bundle-budget gate); SPA fallback that leaves `/assets/*` as a real 404; long-lived immutable caching for hashed assets; `no-cache` for the app shell; no Vercel Functions and no serverless backend.
2. **Frontend runtime configuration.** A single resolver for `VITE_API_URL` and `VITE_WS_URL`, wired into the auth client, the WebSocket transport and the Vite build bridge. Development defaults stay same-origin (`''` for `/auth/*`, `ws://localhost:8080/ws`); cloud builds require absolute `https://` / `wss://` values, derive `wss` from the API URL when the WS URL is omitted, and fail the build/startup on mixed content.
3. **Backend cross-origin compatibility.** An in-repo CORS hook driven by `CORS_ORIGIN` (defaulting to `ALLOWED_ORIGIN`): exact-origin `Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials: true`, `Vary: Origin`, `OPTIONS` preflights, and no wildcard. A configurable `SESSION_COOKIE_SAMESITE` (`lax` default; `strict`; `none` requires `SESSION_COOKIE_SECURE=true`) applied to both setting and clearing the session cookie. A WebSocket `Origin` allowlist check that rejects a present, non-allowlisted origin with close code `1008` before `hello`, while still allowing non-browser clients that omit `Origin`.
4. **Fly.io backend delivery.** One parameterized root `fly.config.toml` (no committed app name; app and region come from GitHub variables) building `src/backend/Dockerfile` target `prod`; internal port `8080`; `force_https = true`; `auto_stop_machines = "off"`, `auto_start_machines = false`, `min_machines_running = 1`; `connections`-based concurrency; `GET /healthz` check; 512 MB shared-CPU machine; `fly secrets set --stage` for per-environment runtime configuration. Single-machine semantics are deliberate and documented: in-memory rooms are not shared across machines.
5. **Neon PostgreSQL.** One Neon project, two branches (`development`, `production`); application traffic uses the pooled `-pooler` connection string (`DATABASE_URL`, `sslmode=require`); migrations use the direct connection string (`DIRECT_DATABASE_URL`). A `db:migrate` CLI entry point runs the existing `runMigrations` runner before the backend deploy; startup migration remains an idempotent safety net. No game/session state moves into new tables; the existing accounts/economy/customization schema is unchanged.
6. **GitHub Actions CI/CD.** `ci.yml` keeps lint/typecheck/test/coverage/build plus the containerized smoke gate and adds a workflow-lint gate; the Terraform verify job is removed. `deploy.yml` selects the target environment from the ref (`develop` → `development`, `main` → `production`) or a `workflow_dispatch` choice, runs `verify` first, then a single environment-gated `deploy` job in the order: Neon migration → Fly backend deploy + health check → Vercel frontend build/deploy + alias → deployed smoke. Per-environment concurrency; no AWS actions, OIDC, ECR, ECS or Terraform.
7. **GitHub Environments and secrets/variables.** Exact catalog (see § Environment catalog): `VERCEL_TOKEN`, `FLY_API_TOKEN`, `DATABASE_URL`, `DIRECT_DATABASE_URL`, `SMTP_PASS` as environment secrets; `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`, `FLY_APP_NAME`, `FLY_REGION`, `FRONTEND_ORIGIN`, `VITE_API_URL`, `VITE_WS_URL`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_FROM`, `SESSION_COOKIE_SECURE`, `SESSION_COOKIE_SAMESITE`, `MAX_USERS_PER_SERVER` as environment variables. `development` has no required reviewers; `production` requires reviewers and restricts deployments to `main`.
8. **AWS supersession and documentation.** Rewrite `docs/architecture/deployment.md` for the new platform; add `docs/architecture/vercel-fly-neon.md` (architecture diagram, env catalog, runbook, rollback, local-vs-cloud, cost/limits); update `README.md`, `docs/architecture/stack.md`, `docs/architecture/containerization.md`, `AGENTS.md`, and add a superseded banner to `infra/README.md`; record a supersession ledger for `aws-deploy-pipeline`, `manual-deploy-trigger`, `workflow-hygiene`, `frontend-delivery-hardening` and `runtime-observability`. `infra/terraform/**` is retained, not deleted.
9. **Proof.** Unit/integration tests and coverage for every behavior change; containerized smoke unchanged; a new zero-dependency `tests/e2e/deployed-smoke.mjs`; CI evidence for the Vercel build and Fly deploy; a recorded development-environment deploy with health, WebSocket hello/join/click, CORS preflight and Neon migration evidence; no secret values in logs.

### Explicitly out of scope

- Any rewrite of the real-time backend, protocol, game loop, room model, server authority, auth model, identity model, database schema or frontend UI behavior.
- Vercel Functions, Vercel serverless WebSockets, Ably/Pusher/another realtime vendor, Redis, queues, microservices, or a second backend process.
- Horizontal scaling of the backend. The in-memory room model is single-process; more than one Fly machine is a different feature (shared room state) and is rejected here.
- Deleting AWS resources, deleting `infra/terraform/**`, or running `terraform destroy/apply`. Deletion requires explicit user approval per `AGENTS.md`.
- Migrating existing production data from AWS RDS to Neon. This is a separate operational feature if such data exists; the accepted AWS pipeline was never proven against a live account.
- Changing the local development path, the compose topology, the frontend nginx image contract, or the existing `tests/e2e/smoke.mjs` checks.
- Adding a new npm dependency. The CORS behavior is implemented in-repo; `@fastify/cors` is the flagged alternative, not the default.
- New Vercel-hosted API routes, custom domains/DNS/certificates (user-owned assets), provider cost commitments, or SMTP provider changes.
- Editing `runtime-observability` artifacts (paused at T1/T2; commits `b5d5869`, `c0796f3`). Its ALB/CloudWatch assumptions are flagged as stale for its later T3–T5.

## User stories

- As a player, I want the game to load from Vercel and connect over `wss://` to the Fly backend, so real-time play works from any network without mixed-content or CORS failures.
- As a returning account holder, I want my session cookie to survive cross-origin requests (or same-site custom domains) so login, verification and logout work without weakening CSRF/SameSite protections.
- As the project owner, I want one CI/CD pipeline that verifies the whole monorepo, migrates Neon, deploys Fly and Vercel in a deterministic order, and proves the deployed game with a WebSocket click.
- As the project owner, I want `development` and `production` isolated by GitHub Environments with different secrets/variables, so a development deploy can never touch production data.
- As the project owner, I want the local `podman compose up` workflow untouched, so contributors keep the same single-command environment.
- As the reviewer, I want AWS artifacts clearly superseded (not silently half-removed) and every environment value documented by name, so the migration is auditable and reversible.

## Acceptance criteria

Verification conventions: commands run from the repository root unless stated. "Tests" means the colocated Vitest file named in the AC. "Grep evidence" means the exact command's raw output is recorded in the build log. Operational ACs (AC-19) require the user-owned assets in § User-owned prerequisites; if those are absent the feature is `blocked`, not accepted.

### Frontend runtime configuration

- **AC-1 — Per-environment resolver.** `src/frontend/src/config.ts` exports `resolveFrontendConfig(env, options)` returning `{ apiBaseUrl, wsUrl }`; cloud mode is `options.cloud === true` (driven by the build-time `VITE_CLOUD_DEPLOY=true` flag, set only by the Vercel build — it is not a runtime secret and keeps the provider-neutral Docker image on its same-origin default). In local mode: `{}` → `{ apiBaseUrl: '', wsUrl: 'ws://localhost:8080/ws' }`; `{ VITE_API_URL: 'https://api.example.test/' }` → `{ apiBaseUrl: 'https://api.example.test', wsUrl: 'wss://api.example.test/ws' }`; `{ VITE_API_URL: 'https://api.example.test//' }` → the same values (all trailing slashes removed, including repeated slashes); `{ VITE_WS_URL: 'wss://mp.example.test/ws' }` → that exact `wsUrl`. In cloud mode: `VITE_API_URL` must be present and absolute `https://` (missing/relative throws an `Error` naming `VITE_API_URL`); `VITE_WS_URL` is optional and is derived as `wss://<api-host>/ws` when omitted; the **resolved** `wsUrl` must start with `wss://`, so an explicit `VITE_WS_URL=ws://…` throws an `Error` naming `VITE_WS_URL` and `wss://`. `config.test.ts` asserts these exact values, the double-slash case, the API-only cloud case, and both error messages.
- **AC-2 — Auth client uses the API origin.** `createAuthApi()` without an explicit `baseUrl` resolves the configured API base. With `VITE_API_URL=https://api.example.test`, `login()` calls `fetch('https://api.example.test/auth/login', { credentials: 'include', ... })`; with no env it calls `'/auth/login'` with `credentials: 'include'` exactly as today. `src/frontend/src/auth/api.test.ts` contains both exact assertions; the existing relative-path tests remain unchanged.
- **AC-3 — Transport uses the same resolver.** `createTransport()` uses `resolveFrontendConfig` for its default URL. `transport.test.ts` asserts the exact sequence `['ws://localhost:8080/ws', 'wss://mp.example.test/ws', 'ws://localhost:8080/ws']` for `VITE_WS_URL` undefined, set, and `''`; a cloud case with only `VITE_API_URL=https://api.example.test` opens `wss://api.example.test/ws`.
- **AC-4 — Build bridge bakes the URLs and gates the resolved config.** `src/frontend/vite.config.ts` defines `import.meta.env.VITE_API_URL` from `process.env.VITE_API_URL ?? ''`, `import.meta.env.VITE_WS_URL` from `process.env.VITE_WS_URL ?? ''`, and `import.meta.env.VITE_CLOUD_DEPLOY` from `process.env.VITE_CLOUD_DEPLOY ?? 'false'`; when `VITE_CLOUD_DEPLOY=true` it validates the **resolved** config via `resolveFrontendConfig` — an absolute `https://` API URL and a resolved `wsUrl` starting `wss://` — throwing before the build otherwise. `VITE_CLOUD_DEPLOY=true VITE_API_URL=https://api.example.test npm run build -w @cubeclicker/frontend` (no `VITE_WS_URL`) exits 0 (bundle budget included) and the resolver/transport tests assert the effective `wss://api.example.test/ws`; the same build with `VITE_WS_URL=wss://api.example.test/ws` also exits 0 and `grep -R "https://api.example.test" src/frontend/dist/assets` matches at least once. The local fallback literal `ws://localhost:8080/ws` may remain in the bundle; effective-URL correctness is asserted by `config.test.ts`/`transport.test.ts`, **not** by a literal-absence grep. The same build with `VITE_API_URL` unset exits non-zero and names `VITE_API_URL`; with `VITE_WS_URL=ws://api.example.test/ws` it exits non-zero and names `VITE_WS_URL` and `wss://`. The `src/build/vite-config.test.ts` assertions for the bridge are updated with concrete values.

### Backend cross-origin compatibility

- **AC-5 — CORS allowlist and preflight.** With `CORS_ORIGIN=https://app.example.test`, a Fastify `OPTIONS /auth/login` carrying `Origin: https://app.example.test`, `Access-Control-Request-Method: POST` and `Access-Control-Request-Headers: content-type` returns `204` and exactly: `access-control-allow-origin: https://app.example.test`, `access-control-allow-credentials: true`, an `access-control-allow-methods` value containing `POST`, an `access-control-allow-headers` value containing `content-type`, and `vary` containing `Origin`. A `POST /auth/login` with `Origin: https://evil.example` returns `403` with no `access-control-allow-origin`. A `GET /healthz` with no `Origin` returns `200` with no `access-control-allow-origin`. A comma-separated `CORS_ORIGIN` allows each listed origin and no others. `src/backend/src/cors.test.ts` asserts all of these.
- **AC-6 — Configurable session cookie.** `SESSION_COOKIE_SAMESITE` accepts `lax`, `strict`, `none` (case-insensitive) and defaults to `lax`; an unknown value throws naming the variable. `SESSION_COOKIE_SAMESITE=none` without `SESSION_COOKIE_SECURE=true` throws the exact message `SESSION_COOKIE_SAMESITE=none requires SESSION_COOKIE_SECURE=true`. With `SESSION_COOKIE_SAMESITE=none` and `SESSION_COOKIE_SECURE=true`, a successful `POST /auth/login` sets a `Set-Cookie` containing `HttpOnly`, `Secure`, `SameSite=None`, `Path=/`, and logout clears it with the same `Secure`/`SameSite` attributes. The default config still produces `SameSite=Lax` and no `Secure`. `auth/config.test.ts` and `auth/auth-routes.test.ts` assert these values.
- **AC-7 — WebSocket Origin guard.** `isWebSocketOriginAllowed(origin, allowedOrigins)` returns `true` for `undefined`, `true` for an exact allowlisted origin, and `false` for `https://evil.example`. A `/ws` upgrade request carrying `Origin: https://evil.example` is closed with code `1008` and receives no `hello` frame; an upgrade with an allowlisted origin receives the pinned `{ "type": "hello", "serverTime": <ISO> }`; an upgrade with no `Origin` (Node/client smoke) receives `hello`. Evidence: unit tests for the predicate plus an integration test using a raw `node:http` upgrade with an `Origin` header (no new dependency), recorded in `app.test.ts`.

### Deployment artifacts

- **AC-8 — Fly configuration contract.** `fly.config.toml` exists at the repository root and parses as TOML; it contains `[build]` with `dockerfile = "src/backend/Dockerfile"`, `[http_service]` with `internal_port = 8080`, `force_https = true`, `auto_stop_machines = "off"`, `auto_start_machines = false`, `min_machines_running = 1`, `[http_service.concurrency]` with `type = "connections"` and `hard_limit = 200`, a `[[http_service.checks]]` with `path = "/healthz"`, `method = "GET"`, `interval = "15s"`, `timeout = "5s"`, `grace_period = "10s"`, and `[[vm]]` with `cpu_kind = "shared"`, `cpus = 1`, `memory = "512mb"`. It contains no `app =` key, no `primary_region` key and no `release_command`; the app name comes from `--app "$FLY_APP_NAME"` and the region exclusively from `--primary-region "$FLY_REGION"` (no second, potentially stale region source in the file). Evidence: `grep -n` anchors for each key, `grep -n 'primary_region' fly.config.toml` returning no match, and a TOML parse check.
- **AC-9 — Prod image carries migrations.** `src/backend/Dockerfile`'s `prod` stage copies `src/backend/src/db/migrations` into `/app/src/backend/dist/db/migrations`. `podman build --format docker --target prod -f src/backend/Dockerfile -t cubeclicker-backend:verify .` exits 0; `podman run --rm cubeclicker-backend:verify node dist/db/migrate-cli.js --list` exits 0 and prints `001_init.sql` through `007_economy_revision.sql` in lexicographic order (7 lines, no duplicates).
- **AC-10 — Migration runner and CLI on a dedicated connection, with a no-database skip.** `src/backend/src/db/migrate-runner.ts` exports `resolveMigrationUrl(env)`, `runMigrationsAgainst(connectionString, deps?)` and `runStartupMigrations(env, deps?)`; `src/backend/src/db/migrate-cli.ts` exports `migrateFromEnv(env, deps?)`. `resolveMigrationUrl` (CLI contract) prefers a non-empty `DIRECT_DATABASE_URL`, falls back to `DATABASE_URL`, and throws naming both when neither is set. `runMigrationsAgainst` creates a **dedicated `pg.Client`** (one connection), calls `connect()`, passes that client — never a `pg.Pool` — to the existing `runMigrations`, and always `end()`s it in `finally`; this pins `BEGIN`, every migration statement and `COMMIT` to the same connection. `runStartupMigrations` is the **conditional startup path**: it returns `null` without creating a client, throwing, or exiting when neither `DIRECT_DATABASE_URL` nor `DATABASE_URL` is set (preserving `buildApp`'s in-memory repositories and the existing host-only `npm run dev`/`node dist/server.js` startup); otherwise it calls `runMigrationsAgainst` with the direct URL when present (Fly gets `DIRECT_DATABASE_URL`) or `DATABASE_URL` locally, and a migration failure still exits `1`. `server.ts` calls `await runStartupMigrations(process.env)` before `buildApp`. `migrateFromEnv` uses the same runner and propagates failures; `--list` prints migration names without opening a database connection. `migrate-runner.test.ts` asserts URL precedence, the thrown CLI message, connect/query/end ordering, the single-client contract, failure propagation, and the **no-database regression** (`runStartupMigrations({})` → `null`, no client factory call, no throw); `migrate-cli.test.ts` asserts the CLI path and `--list`. `npm run coverage -w @cubeclicker/backend` includes both files at ≥ 80% on all four metrics.
- **AC-11 — Vercel configuration contract.** `src/frontend/vercel.json` parses as JSON and contains exactly: `"framework": "vite"`, `"buildCommand": "npm run build"`, `"outputDirectory": "dist"`, one SPA rewrite with source `/((?!assets/).*)` and destination `/index.html`, and headers for `/assets/(.*)` → `Cache-Control: public, max-age=31536000, immutable`, `/` and `/index.html` → `Cache-Control: no-cache`. It contains no `functions`, `builds`, `routes` with `handle: "filesystem"`, or serverless runtime key. Evidence: `node -e "JSON.parse(...)"` and exact `grep -F` anchors.

## Security considerations

- **Cross-site cookie and CSRF posture.** The session cookie is `HttpOnly`, `Secure` in cloud environments, `Path=/`, and `SameSite=None` only when the frontend and API are cross-site; `SameSite=None` requires `SESSION_COOKIE_SECURE=true` (enforced at startup). `SameSite=None` removes the browser's default cross-site protection, so the existing `Origin` check on every state-changing auth route is the CSRF control, and CORS is an exact-origin allowlist with `Access-Control-Allow-Credentials: true` and `Vary: Origin`. The implementation must not introduce a wildcard or reflect arbitrary origins. When the user chooses same-site custom domains (`app.<domain>` + `api.<domain>`), `SameSite=Lax` is recommended and remains supported.
- **Third-party cookie blocking.** Default `*.vercel.app` → `*.fly.dev` deployments are cross-site; Safari/iOS ITP and Chrome's third-party cookie restrictions can block the session cookie regardless of `SameSite=None`. This is a product risk, not a code bug: the recommended production topology is first-party subdomains under one registrable domain, which also keeps `SameSite=Lax` viable. Development may use default domains with `SameSite=None` for Chrome-based testing. See Q-2.
- **CORS surface.** Only the configured frontend origin(s) receive `Access-Control-Allow-Origin`; preflights are answered without cookies; disallowed origins receive `403` from the existing `Origin` check. The CORS hook is in-repo and unit-tested, avoiding a new supply-chain dependency.
- **WebSocket origin.** Browsers do not enforce CORS on WebSocket connections, so the upgrade route validates a present `Origin` against the same allowlist and closes `1008` before `hello`. Non-browser clients that omit `Origin` remain allowed (matching the existing CSRF decision); this is documented, not accidental.
- **Secrets.** `VERCEL_TOKEN`, `FLY_API_TOKEN`, `DATABASE_URL`, `DIRECT_DATABASE_URL` and `SMTP_PASS` live only in GitHub Environment secrets and, for runtime values, Fly app secrets. No secret is committed, baked into the Vite bundle (`VITE_*` values are public client configuration), or echoed in logs. Fly secrets are staged with `flyctl secrets set --stage`; Vercel tokens are passed through `env:`, never on a command line that GitHub does not mask. The credential audit is part of AC-23.
- **Database.** Neon requires TLS (`sslmode=require`); the app uses the pooled endpoint, migrations use the direct endpoint. The production branch is protected and restored via a separate branch for rollback. No game/room state is persisted; accounts/economy are the only durable data and keep the existing schema and validation.
- **Supply chain.** New third-party actions (`superfly/flyctl-actions/setup-flyctl`, Vercel CLI installation) are pinned to a full commit SHA or an exact CLI version; no floating `@master`/`@latest`. Existing `actions/*` pins are preserved. Dependabot continues to track `github-actions`.
- **AWS surface.** No AWS credentials, roles, OIDC trust, ECR pushes or Terraform applies remain in workflows. `infra/terraform/**` is archived in place and cannot be applied by CI after `verify-infra` is removed.

## Containerization impact (per `docs/architecture/containerization.md`)

- **Local path unchanged.** `compose.yaml` and the single-command `podman compose up` are untouched; backend/frontend dev containers remain; `npm run smoke` still runs the Mailpit-primed containerized suite.
- **Backend image.** Fly builds the existing `src/backend/Dockerfile` `prod` target from the repository root. The one image change is packaging `src/backend/src/db/migrations` into `dist/db/migrations` (the current image does not copy `.sql` files and would fail startup migrations against a real DB). Health signal stays `GET /healthz`; port stays 8080; config stays environment-based; no secret is baked in; the image remains provider-neutral.
- **Frontend image.** Vercel builds the SPA directly from `src/frontend`; the nginx `prod` image and its static-delivery contract remain for local/smoke/portability but are no longer the cloud frontend. No nginx change.
- **No new compose service, image, port or volume.** Fly and Neon are managed services outside compose. The backend still exposes WebSocket on 8080; Fly terminates TLS and proxies upgrades (Fly Proxy passes WebSocket upgrades without extra configuration; it keeps idle WebSockets open, and deploys restart machines).
- **Deployment neutrality.** The container image remains runnable on any platform; only the deploy target changes. The provider-choice statements in `docs/architecture/stack.md`, `docs/architecture/containerization.md` and `AGENTS.md` are amended by the documentation task; this user request is the amendment authority.

## Real-time impact

- **Connection lifecycle.** Browsers connect cross-origin over `wss://<fly-app>/ws`; the existing client retry policy (10 attempts, 500 ms → 5 s backoff) and 30 s heartbeat are unchanged. A Fly deploy restarts the machine, closing all sockets; clients reconnect automatically, and in-memory rooms reset. The 30 s heartbeat also keeps intermediate proxies from treating the socket as idle.
- **Multi-client behavior.** One Fly machine runs one backend process, so all clients share the same room registry and see each other's live activity. Scaling above one machine would split rooms; that is explicitly out of scope and is documented in the runbook.
- **Server authority.** Unchanged: clicks, economy and room state remain server-authoritative; the frontend only resolves URLs.
- **Cookie at upgrade.** The session cookie is sent on the WebSocket handshake to the API host. Cross-site deployments require `SameSite=None; Secure` for the cookie to be attached; same-site custom subdomains work with `Lax`. The WS route resolves the account from the upgrade cookie exactly as today.
- **Mixed content.** An `https://` Vercel page cannot open `ws://`; the production resolver rejects `ws://` and derives `wss://` from `https://VITE_API_URL`.
- **Grace/reconnect.** The existing reconnect grace window (30 s) and heartbeat/missed-pong rules are unchanged. Fly's proxy does not close idle WebSockets; deploys and proxy restarts do, hence the reconnect contract remains the recovery path.
- **Identity.** No identity change. The auth model remains cookie sessions; the only new risk is third-party cookie blocking on default cross-site domains (Q-2), flagged rather than silently assumed.

If you use default `*.vercel.app`/`*.fly.dev` hosts, they must still be stable aliases and you accept the cross-site cookie/ITP risk for production (Q-2).
5. **GitHub.** Create the `develop` branch; create Environments `development` (no reviewers, deployment branch `develop`) and `production` (required reviewers, deployment branch `main`, prevent self-review recommended); add the secrets/variables from § Environment catalog.
6. **SMTP.** Provide the production SMTP host/port/user/password/from values and a **reachable** SMTP host or test mailbox for the Fly development environment. Mailpit stays compose-only (`mailpit` does not resolve from Fly) and must not be used as the cloud `SMTP_HOST`.
7. **Terraform decision.** Confirm archive (default) or authorize deletion of `infra/terraform/**`; this feature performs neither deletion nor `terraform apply`.
