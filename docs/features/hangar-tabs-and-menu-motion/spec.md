# Spec — Hangar Tabs & Menu Motion

## Summary

Three presentation refinements to the shipped Neon Forge game shell, all frontend-only: **(A)** split the oversized spaceship customization panel into smaller in-panel **tabs** built from the actual part catalog (10 slots → 5 two-slot groups), keeping the live preview, lootbox/key chips, `Open lootbox`, the reveal branch, every owned/locked/equipped state, 44 px targets, ARIA/keyboard operation, reduced-motion behaviour and the mobile layout; **(B)** add a **glitch/futuristic boot animation** when a menu opens — a CSS-only sequence of **four menu beats** (opacity flicker, scan sweep on the panel's top edge, rail power-up, stepped chromatic title split) plus a fifth tab-swap fade, on exactly the two menus the player opens (the hangar and the crew list), open-only, replayed on every open, disabled by `prefers-reduced-motion` **and** by the session reduced-motion preference; and **(C)** a screenshot-driven polish pass on the 1920×1000 game view (themed scrollbars, the warm-red crew pill, the full-width grey HUD minimize bar, tab-strip density and the short-viewport preview). Raw request: *"Cool, now, it look awesome, BUT: - Leaderboard overlaps a little bit Pilot Status box - Spaceship customization is quite big, we should be able to split it into smaller menus inside it, like, different tabs. - I want you to add glitch animations and/or futuristic animations when we open a menu. Check if you can improve any other thing based on this screenshot, that is how is looking game now"*.

The leaderboard/HUD overlap named in the same message is **out of scope**: it is being fixed in `game-feel-overhaul` T12. This feature adds **no protocol, server, persistence, dependency, asset or container change**; every visual is CSS or existing React markup, and the panel chunk stays deferred so the Three-free entry graph and the 150,000 / 165,000 / 300,000 B gzip ceilings are untouched.

## Context and decisions already accepted

- **Base state — the game-feel review fixes (`544cce8`).** The base already contains: `<main data-customization-open=… data-reduced-motion="true|false">` on the game main (`App.tsx`), the matching SSR/jsdom assertions (`App.test.tsx`), and a top-level `main[data-reduced-motion='true']` block in `game-view.css` (session reduced motion). **This feature does not edit `App.tsx`**; it **extends the existing** `main[data-reduced-motion='true']` block's selector list (it does not add a second session block). Its only `App.test.tsx` edits are the two pre-tab panel assertions T3 owns (AC-29, r2a). Predecessor: `game-feel-overhaul` review-fix commit `544cce8`.
- **A pre-existing reduced-motion gap is fixed here.** `.customization-panel[data-reveal-active='true']` (specificity 0,2,0) declares `animation: reveal-spotlight …`, while the `prefers-reduced-motion: reduce` block's `.customization-panel` (0,1,0) declares `animation: none` — so the **OS** preference does not actually stop the reveal spotlight today (the session block works only because of its `main[…]` prefix). The new hangar boot would inherit the same trap (`.customization-panel:not([data-reveal-active='true'])` is 0,2,0). AC-17 therefore pins *scoped* reduced-motion selectors in both blocks and closes the existing reveal gap in the same change.
- **The hangar is one long scroll.** `SpaceshipCustomizationPanel` renders `<h2>Spaceship hangar</h2>`, two `gf-chip` counts, `Open lootbox`, then all **10** `li.customization-slot` rows (3 variants each) and the 12 rem `SpaceshipPreview`, inside `.customization-panel` with `max-width: min(22rem, calc(100vw - 2rem))`, `max-height: 60vh` (`45vh` under the 720 px block), `overflow-y: auto` (`app.css`). `spaceship-cursor-loot-animations` AC-29/AC-30/AC-31 and `game-feel-overhaul` AC-21 pin the rows, the states, the targets, the preview and the reveal branch.
- **The catalog fixes the grouping.** `game/parts-v2.ts` `SLOT_CATALOG` has exactly 10 slots in a fixed order (`hull`, `nose`, `cockpit`, `wing-left`, `wing-right`, `engine-left`, `engine-right`, `ignition-left`, `ignition-right`, `tail-fin`); each has 3 parts (standard always owned, rare + epic lootable). `normalizePartMap` expands a legacy bilateral id to **both** sides (`wings-silver` → `wing-left-silver` + `wing-right-silver`; `engine-blue` → both ignitions; `body-X` → `hull-X`).
- **The panel is a deferred chunk.** `DeferredSpaceshipCustomizationPanel` dynamically imports the panel only while the toggle is open (`frontend-delivery-hardening` AC-4), and the reveal branch replaces the normal content while a grant exists (`game-feel-overhaul` AC-21). Anything this feature adds to the panel stays inside that chunk.
- **The motion system is centralised.** `MOTION` (`game/motion.ts`) is the single source of presentation tokens; 17 are mirrored as `--motion-*` on `main` in `game-view.css` and asserted by `game-view.css.test.ts`. Panels are chamfered by `clip-path` and declare **no `filter` and no outer `box-shadow`** (`game-feel-overhaul` AC-18), so any new effect must not reintroduce either.
- **Occupied bands and layering are settled.** HUD top-left, connection banner top-centre, activity feed below it, leaderboard left rail, crew top-right, customization toggle bottom-left, upgrades bottom-right, phase announcement bottom-centre; layer table canvas 0 / ambience 2 / panels 3 / level 5 / reveal 20 / toggle 21 / auth 100. Neither changes.
- **The screenshot.** The 1920×1000 view shows: the leaderboard rail overlapping the bottom of the Pilot status HUD (handled by T12), a bright native scrollbar inside the hangar, the warm-red `Users on Server` pill as the only non-cyan/amber surface in the shell, a full-width grey bar under the Pilot status panel (the HUD minimize control stretched by the flex column), and a dense hangar column. § Deliverable C dispositions each item.

## User stories

- As a player, the hangar opens as a small set of named part groups instead of one long scroll, so I can find the wing or the ignition I want in one click.
- As a player, I can tell from the tab strip how much of each group I have collected, and after a lootbox reveal I land on the group that contains my new part without a flash of the wrong group.
- As a player, opening the hangar or the crew list feels like powering up a ship console rather than a web page swapping a div.
- As a player with reduced motion (system preference or the session preference), menus appear instantly with no flicker, scan or chroma, and remain fully readable.
- As a keyboard/screen-reader player, the tab strip follows the ARIA tabs pattern (roving tabindex, arrow/Home/End that select without scrolling the panel), announces the selected group with its owned count, and every control keeps a 44 px target and a visible focus ring.
- As a maintainer, the tab grouping is one pure module derived from `SLOT_CATALOG`, the motion is four tokens plus CSS keyframes, and no protocol, server, persistence, dependency or container path changes.

## Deliverable A — Hangar tabs

### Tab set (pinned)

Five tabs, in this order, each holding two slot rows in `SLOT_CATALOG` order:

| # | `data-tab` | Label | Slots | Lootable parts | Badge max |
| --- | --- | --- | --- | --- | --- |
| 1 | `frame` | `Frame` | `hull`, `tail-fin` | 4 | 4 |
| 2 | `front` | `Front` | `nose`, `cockpit` | 4 | 4 |
| 3 | `wings` | `Wings` | `wing-left`, `wing-right` | 4 | 4 |
| 4 | `engines` | `Engines` | `engine-left`, `engine-right` | 4 | 4 |
| 5 | `ignitions` | `Ignitions` | `ignition-left`, `ignition-right` | 4 | 4 |

Rationale: two rows per group is exactly one "smaller menu", the union is the whole catalog, and the five labels fit an auto-fit grid inside the 22 rem panel (three + two at the desktop width, three + two at 375 px and at 320 px). The tab is a UI grouping, **not** a domain term (the glossary keeps `part slot` authoritative). Q-1 records the one-tab-per-slot alternative.

### Panel structure (normal state, pinned order)

1. `h2.customization-title` — `Spaceship hangar` (unchanged).
2. `.customization-counts` with the two `gf-chip` counts — `Lootboxes: N` / `Keys: N` (unchanged).
3. `button.customization-open.gf-cta` — `Open lootbox` (unchanged enable/disable rules incl. `pendingOpen`).
4. **New** `.customization-tabs[role="tablist"]` — five `role="tab"` buttons with labels and a badge.
5. **New** `.customization-tabpanel[role="tabpanel"]` (stable `id="customization-tabpanel"`) — the active group's `<ul class="customization-slots">` with exactly two `li.customization-slot` rows.
6. `SpaceshipPreview` — one instance, below the tab panel, mounted once for the whole normal state (never remounted by a tab switch, so the panel keeps exactly one WebGL preview context).

The reveal branch is untouched: while a grant exists the section renders `LootboxReveal` only — no title, counts, open control, tablist, tabpanel or preview.

### Height, scroll and fit (pinned)

- `.customization-panel` keeps the accepted `max-width: min(22rem, calc(100vw - 2rem))`, `max-height: 60vh` (with the accepted 720 px override `45vh` retained), `overflow-x: hidden`, `overflow-y: auto` and bottom-left placement: **one** scroll container, no nested scrollbars.
- `.customization-tabs` is `position: sticky; top: 0; z-index: 1;` over an opaque Neon Forge gradient, so the strip stays reachable while the panel scrolls.
- `.customization-tabpanel` declares **no** `overflow` and no height; the panel scrolls as a whole.
- The preview shrinks on short viewports: `height: min(12rem, 26vh)` and `8rem` under `@media (max-height: 760px)` (a `game-view.css` override of the `app.css` 12 rem base; `app.css` is not edited).
- Target: with the default tab and no grant, the panel shows the title, the chips, `Open lootbox`, the tab strip, both rows and the preview **without scrolling at 1920×1000** (`scrollHeight <= clientHeight`), and at 1280×720 the recorded `scrollHeight - clientHeight` is **≤ 140 px** (the strip stays sticky, so the tabs remain reachable). Recorded in the manual matrix.

## Deliverable B — Menu-open motion

### Sequence (pinned)

One CSS-only "boot" applied to the two menus the player opens — `.customization-panel` (normal state) and `.user-panel .users-list` — replaying on every mount, 320 ms total, **four menu beats** plus the tab-swap fade:

| Beat | Selector | Keyframes | Pinned stops |
| --- | --- | --- | --- |
| boot flicker | the panel / the crew list root | `menu-boot` (`var(--motion-menu-boot-ms)`, `linear`, `both`) | `0% { opacity: 0; border-color: var(--gf-rim-strong) }` · `12% { opacity: 0.62 }` · `22% { opacity: 0.14 }` · `34% { opacity: 0.86 }` · `46% { opacity: 0.48 }` · `60% { opacity: 1; border-color: var(--gf-rim) }` · `100% { opacity: 1; border-color: var(--gf-rim) }` |
| scan sweep | `::before` (the existing top light edge) | `menu-scan` (`var(--motion-menu-boot-ms)`, `linear`, `both`) | `0% { right: 100%; opacity: 0.15 }` · `45% { right: 0; opacity: 1 }` · `70% { right: 0; opacity: 0.4 }` · `100% { right: 0; opacity: 1 }` |
| rail power-up | `::after` (the existing left status rail) | `menu-rail` (`var(--motion-menu-flicker-ms)`, `steps(2, end)`, `both`) | `0% { height: 8%; opacity: 0.1 }` · `100% { height: 40%; opacity: 1 }` |
| chroma split | the panel title / the crew title | `menu-chroma` (`var(--motion-menu-chroma-ms)`, `steps(3, end)`, `both`) | `0% { text-shadow: -1px 0 var(--gf-rare), 1px 0 var(--gf-rim-strong) }` · `50% { text-shadow: 1px 0 var(--gf-amber), -1px 0 var(--gf-rare) }` · `100% { text-shadow: none }` |
| tab swap | `.customization-tabpanel` | `tab-panel-in` (`var(--motion-tab-switch-ms)`, `ease-out`, `both`) | `0% { opacity: 0 }` · `100% { opacity: 1 }` |

**Open only.** There is no close animation: closing the hangar or the crew list unmounts it in one commit (Q-8). Re-open replays the whole sequence because the element mounts again; the reveal spotlight (`reveal-spotlight`, 260 ms) is unchanged and is never combined with `menu-boot` (the boot is gated to `:not([data-reveal-active='true'])`).

**Interaction during the sequence.** Nothing is disabled while it runs: no `pointer-events: none`, no `inert`, no `aria-hidden`, no focus move, no delayed handler; `Open lootbox`, the tabs, the equip/unequip controls and the crew rows are operable from the first frame, and the animation never changes layout (no `width`/`height`/`margin`/`transform` on the panel root).

**Cost profile.** The beats animate `opacity`, `border-color` and `text-shadow` (paint/composite) plus `right` and `height` on two 1–2 px pseudo-elements (layout on a tiny box, one per open). It is cheap and bounded — one 320 ms pass per open, no JS, no per-frame work — but it is **not** a compositor-only animation; the bounds are asserted by AC-24 and the manual matrix.

**Reduced motion.** Both variants disable every new animation and leave the static content: the `prefers-reduced-motion: reduce` block (the file's single block) and the existing `main[data-reduced-motion='true']` session block, each carrying the **scoped** selectors of § Reduced-motion selectors (AC-17).

### Reduced-motion selectors (pinned, specificity-safe)

The boot rules out-specify a bare `.customization-panel` (0,2,0 vs 0,1,0), so both reduced-motion blocks must repeat the **scoped** selectors and the animation rules must be declared **before** the blocks (equal specificity → later source wins):

| Block | Scoped selectors that must appear |
| --- | --- |
| `@media (prefers-reduced-motion: reduce)` | `.customization-panel:not([data-reveal-active='true'])`, `…::before`, `…::after`, `… .customization-title`, `.customization-panel[data-reveal-active='true']` (the existing reveal spotlight), `.customization-tabs`, `.customization-tab`, `.customization-tabpanel`, `.user-panel .users-list`, `.user-panel .users-list::before`, `.user-panel .users-list::after`, `.user-panel .users-list .users-list-title` |
| `main[data-reduced-motion='true']` (existing block, extended) | the same scoped list, each prefixed `main[data-reduced-motion='true'] ` (the block already carries `main[data-reduced-motion='true'] .customization-panel[data-reveal-active='true']`, so the reveal fix needs no new session selector) |

## Open questions

**Approval checkpoint.** The orchestrator must present Q-1…Q-15 with these proposed defaults; the user may approve the defaults or request changes to any one. These are user-visible design decisions, not builder choices.

- **Q-1 — Tab set, order and labels.** Default: five grouped tabs in this order — `Frame` (Hull, Tail Fin), `Front` (Nose, Cockpit), `Wings` (Port Wing, Starboard Wing), `Engines` (Port Engine, Starboard Engine), `Ignitions` (Port Ignition, Starboard Ignition), two rows each. Alternative: ten tabs, one per slot, labelled with the exact slot names (`Hull`, `Nose`, …).
- **Q-2 — Default tab and reopening.** Default: always opens on `Frame`; after a reveal is dismissed or equipped the panel lands on the tab containing the granted slot; reopening starts on `Frame` again. Alternative: remember the last tab for the session (module-level memory, no storage).
- **Q-3 — Preview placement.** Default: one live preview below the tab content, always visible in the normal state and never remounted by a tab switch. Alternative: a compact preview inside the active tab instead.
- **Q-4 — Badge meaning.** Default: `owned/4` lootable parts owned in the group, always visible, announced as `<Label>, <owned> of 4 parts owned`. Alternative: a dot only when the group holds an owned part that is not equipped.
- **Q-5 — Animation style.** Default: the four-beat glitch boot — opacity flicker + top-edge scan sweep + rail power-up + stepped chromatic title split, pure CSS, no new DOM. Alternative: a scan sweep only (no flicker, no chroma), or no menu animation at all.
- **Q-6 — Duration and intensity.** Default: 320 ms total (`menuBootMs`), flicker 120 ms, chroma 90 ms, stepped (no easing curves). Alternative: a calmer 220 ms fade-plus-scan, or a louder 520 ms double-flicker.
- **Q-7 — Which surfaces animate.** Default: only the two menus the player opens — the hangar panel and the crew list. Alternative: also the HUD, upgrades, feed, leaderboard and auth menu on first appearance.
- **Q-8 — Close animation.** Default: none — menus close instantly (unmount), no exit animation, no delayed teardown. Alternative: a 120 ms fade-out state before unmount.
- **Q-9 — Tab switch motion.** Default: a 140 ms opacity fade of the tabpanel (`tabSwitchMs`). Alternative: instant switch with no motion.
- **Q-10 — Crew pill colour.** Default: the pill becomes Neon Forge glass with a cyan rim and the warm-red gradient moves to the count badge only. Alternative: keep the warm-red pill exactly as it is.
- **Q-11 — Scrollbar treatment.** Default: thin themed scrollbars (6 px cyan thumb at 35 % alpha, transparent track) on the hangar, upgrades and crew list. Alternative: hide scrollbars entirely and rely on wheel/touch.
- **Q-12 — HUD minimize control.** Default: keep the 24 px target but render it as a compact right-aligned chevron button instead of a full-width bar. Alternative: leave the full-width bar.
- **Q-13 — Panel height and preview size.** Default: keep the accepted `max-height: 60vh` (`45vh` on mobile) panel scroll and shrink the preview to `min(12rem, 26vh)` (`8rem` under a 760 px viewport height). Alternative: keep the 12 rem preview and accept more panel scrolling.
- **Q-14 — Mobile tab strip.** Default: the same auto-fit grid at every width (three + two at 375 px and at 320 px), with the label stacked above the badge under 720 px. Alternative: a single-row horizontally scrolling strip.
- **Q-15 — Screenshot-polish scope.** Default: in scope = themed scrollbars, crew pill, HUD minimize bar, tab chrome, short-viewport preview; backlog = variant rarity chips, per-tab empty-state copy, feed/leaderboard empty placeholders, shell-wide boot on `welcome`, close animations, a sliding tab indicator. Alternative: pull the rarity chips and the empty-state copy into this feature.

## Assumptions

- The hangar is the only surface that needs tabbing: it is the only panel with ten repeated rows; the upgrades panel has three rows and needs none.
- Two rows per tab plus a header, the open control, the strip and a shrunken preview fit inside `max-height: 60vh` on a 1920×1000 viewport with no scroll and inside 1280×720 with ≤ 140 px of scroll; the manual matrix records the measured `scrollHeight`/`clientHeight`.
- `position: sticky` works inside the clipped, `overflow: auto` panel in the shipping browsers; if it does not, the strip falls back to a non-sticky block (no AC change, recorded in the build log).
- `scrollbar-width`/`scrollbar-color` (Firefox) and `::-webkit-scrollbar` (Chromium/WebKit) degrade to the platform default where unsupported.
- The "broad grey HUD minimize bar" in the screenshot is the empty `Toggle HUD` button stretching in the flex-column panel; if the screenshot shows a different control, the fix is re-scoped before build (recorded in Q-12).
- Tab selection is ephemeral UI state; nothing in the product vision requires remembering it.
- The panel is only rendered after `welcome` and only in the browser, so the default-tab `useState` initialiser never causes a hydration mismatch, and the render-phase landing adjustment cannot loop (it fires only on the `grant non-null → null` transition).
- The screenshot audit is of the 1920×1000 view; the other viewports are regression checks, not redesign targets.
- The reveal branch, the preview, the motion-token mirror, the session reduced-motion block and the bundle/deferred-chunk machinery stay as accepted (base `544cce8`); this feature only adds to them and corrects the reduced-motion specificity gap.
