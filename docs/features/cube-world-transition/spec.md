# Spec — Cube World Transition (directional travel, mini-cube-built surface, random mini-cube counts)

## Summary

Third visual/design pass, three changes all local to the frontend workspace: (1) **random mini-cube counts** — each cube level draws one random integer from the seeded, injectable RNG that determines its grid size N (pinned range 3–7), and all six faces of that level carry exactly N² mini-cubes with the same ids (`face:row:col`) and instancing/picking forms as today; (2) **mini-cube-built surface** — the cube reads as one giant cube made of mini-cubes: tiles sit flush, edge-to-edge, with no face plates or black surface showing between/around them, the cube body remains only as the dark interior behind removed tiles, and rotation/clicking/pops are unchanged; (3) **directional travel to a randomly placed next cube** — when the sixth face clears, the engine draws the next cube's direction (left / right / top / bottom), the camera departs in that direction while pulling back, the next cube comes into existence at the turn-around at its random world position (24 world units away in the drawn direction), and the camera flies in to land exactly at the rest pose over the new cube. Online occupancy/collision is explicitly future and out of scope (documented extension point only). Everything else in the three accepted features stays in force; the predecessor specs are authoritative for everything not superseded and are never edited.

## Scope

### In scope

- Frontend workspace only (`src/frontend`): `game/types.ts` (range constants, `TravelDirection`), `game/engine.ts` (per-level grid draw, travel-direction draw, two new snapshot fields, deterministic RNG fallback), `game/session.ts` (random/grid wiring), `render/cube-view.ts` (flush tiling, plates removed), `render/scene.ts` (world positions, directional travel path, snapshot-driven rebuild, face-removal countdown), plus their colocated tests, `render/picking.test.ts` (multi-size pick coverage — `picking.ts` unchanged), `App.test.tsx` (test-only snapshot fixture), and `docs/product/glossary.md` (updated terms + one new term).
- The three behaviors above with pinned constants, exact pose/progress tables, seeded determinism, reduced-motion collapses, and deterministic node tests.

### Explicitly out of scope

- Game rules: click/explosion stats, intent *kinds and ordering semantics*, the phase machine (`intro`/`travel`/`playing` unchanged — no new phase), style cycling, rotation settle values, auto-rotation, input mapping, HUD/live region — all unchanged (the engine's click and rotation paths are untouched).
- Online/multiplayer occupancy: no collision checks, no shared world state, no server authority, no identity/accounts, no reconnection handling; the spawn-selection seam is documented (§ 3) as the future hook — no implementation.
- Backend, WebSocket, persistence, economy, container assets, CI, configs, `main.tsx`, `index.html`, `ws/**` — unchanged.
- Audio, new dependencies, new drawable *types*, browser automation, pixel/perceptual tests.
- New UI: no mini-cube count display, no minimap, no new HUD elements, no new copy.

## UX behavior (pinned)

### 1. Random mini-cube count per level (supersedes the fixed 5×5 structure)

One random integer per level determines the per-face mini-cube count, identical on all six faces: the integer is the **grid edge N** — a random square grid (Q-1: the alternative arbitrary-count layout is listed and rejected). `N ∈ [3, 7]` (9–49 per face, 54–294 per cube level); N = 5 — the accepted predecessor size — sits mid-range.

- **Draw:** `N = MINI_CUBE_GRID_MIN + ⌊random() · (MINI_CUBE_GRID_MAX − MINI_CUBE_GRID_MIN + 1)⌋` = `3 + ⌊draw · 5⌋` from the injected RNG. `MINI_CUBE_GRID_MIN = 3`, `MINI_CUBE_GRID_MAX = 7` live in `game/types.ts` (the grid-domain constant home; `GRID_SIZE` 5 stays as the default/fallback value). With the constant draw `0.5`, N = 5 — the accepted engine tests' 25-per-face assertions stay valid.
- **Draw order (pinned):** (1) one grid draw at engine creation (level 0); (2) explosion bursts consume draws exactly as today (`createBurst`, default profile only); (3) one direction draw at travel start (§ 3); (4) one grid draw at each level advance. When `EngineOptions.gridSize` is injected, the grid draws are skipped and every level uses the injected size (tests' determinism seam).
- **Determinism:** no `Math.random` anywhere in `game/**` — the engine's omitted-`random` fallback is a pinned deterministic LCG (seed 1, multiplier 1664525, increment 1013904223, modulus 2³²), and the session injects `env.random` (the sanctioned `browser-env.ts` reader) at attach via `setRandomSource`. Seeded LCG sequences are pinned in tests (concrete per-level N values and directions).
- **Semantics kept:** 6 faces per board, ids `face:row:col`, immutable removal, repeat-click no-op, synchronous `clicks`/`facesDestroyed`, referentially stable snapshots, style cycling, level progression — all unchanged (the board functions were already parameterized by `gridSize`).

### 2. Mini-cube-built cube surface (no black face plates)

The cube looks like one giant cube made of mini-cubes: each face is **fully tiled by its mini-cubes, flush and edge-to-edge** — no plate, no black face, no gap shows between or around tiles.

- **Geometry:** one `InstancedMesh` per face with N² instances sized to fill the face exactly: `MINI_CUBE_TILE_RATIO = 1` (was 0.9), so `tileSize = CUBE_SIZE / N` on the face axes (thickness 0.25, proud of the body, unchanged). Adjacent tiles on a face meet edge-to-edge; the outermost tiles reach the cube edges exactly (N × `CUBE_SIZE/N` = 5); edge tiles of adjacent faces meet along the cube edges. Tile *centres* are unchanged (only the extent grows), so the pinned first/last instance positions hold.
- **Plates removed:** the per-face plane meshes, their materials, and `PLATE_OFFSET` are deleted from `cube-view.ts`; `CubeView` no longer exposes `plateMeshes`. The cube group's children are exactly: the body + one `InstancedMesh` per live face (7 at construction).
- **Interior appearance (defined):** the cube body (a `CUBE_SIZE` box in `style.cubeColor`) remains *behind* the tile layer as the **dark interior without a lit plate** — it is what a player sees where tiles have been removed (removed tile slots and cleared faces). It stays fully covered wherever tiles remain.
- **Rotation** is unchanged (the cube group rotation machine is untouched). The pop-then-shrink animation (§ ledger, polish AC-4) is unchanged in factor form — a shrinking flush tile exposes the dark interior around it, which is the intended "mini-cube removed" look.
- **Face clearing:** with no plate to fade, a `faceCleared` intent starts a removal **countdown** of the active profile's `faceFadeMs` (400 ms default / 100 ms reduced) — long enough for the face's last tile pop (160 ms) to finish — then the face's `InstancedMesh` is detached and its geometry/material disposed exactly once. No opacity animation exists anywhere on the cube. The engine-side `faceFadeMs` pacing before travel is unchanged.
- **Style system:** `applyStyle` re-colours the body and the live faces' tile materials exactly as today (minus the plates); per-level materials, refresh/destroy behavior, and disposal are retained.

### 3. Directional travel to a randomly placed next cube (supersedes the same-position swing)

**World model.** Cubes live in a flat world plane (z = 0). The camera rests above the *current* cube at `(cx, cy, 12)` looking at `(cx, cy, 0)` — level 0 at the origin keeps the accepted rest value `(0,0,12)`. The camera is always axis-aligned with the identity quaternion, so screen-right = world +x and screen-up = world +y — the four travel directions map directly to world offsets at `CUBE_SPACING` = 24: left `(−24, 0)`, right `(24, 0)`, top `(0, 24)`, bottom `(0, −24)`.

**Direction selection (engine, pure, seeded).** At travel start the engine consumes exactly one RNG draw: `TRAVEL_DIRECTIONS[⌊draw · 4⌋]` with `TRAVEL_DIRECTIONS = ['left', 'right', 'top', 'bottom']` (draw 0.5 → `top`). The drawn direction rides in `snapshot.travelDirection` (non-null exactly during `travel`; `null` in `intro`/`playing`) so the scene can steer the departure from the first travel frame. The scene captures the flight origin (`travelFrom` = the old cube's position) and the offset at the first travel snapshot; the direction is constant for the whole travel (engine contract, pinned in tests).

**Flight (scene, pure function of progress).** Over the old cube at `(ox, oy)` with offset `(dx, dy)`:

- position: `x(p) = ox + dx · easeInOutQuad(p)`, `y(p) = oy + dy · easeInOutQuad(p)`, `z(p) = 12 + 78 · travelSwing(p)` — the retained symmetric pull-back as the depth component;
- look target: `(x(p), y(p), 0)` — the camera looks straight down the view axis (identity quaternion at every p);
- segments: **departure** p ∈ [0, 0.5] — the camera pulls back (12 → 90) while drifting toward the new cube (lateral 0 → 12) — "going away" in the direction of the other cube, the finished cube fully framed the whole way; **midpoint** p = 0.5 — the turn-around (lateral 12, depth 90); the engine advances the level exactly once (retained midpoint advance) and the new cube comes into existence at its world position; **approach** p ∈ (0.5, 1] — the camera flies down into the rest pose over the new cube, the new cube fully framed the whole way; **rest** p = 1 — exactly `(ox + dx, oy + dy, 12)` looking at `(ox + dx, oy + dy, 0)`, which equals the `playing` rest pose (continuous landing, never a snap).

Pinned pose tables (all four directions; dyadic-exact doubles — derived from the formula above, which is **authoritative**, revision r2: z = `12 + 78 · travelSwing(p)`, lateral = `easeInOutQuad(p) · offset`):

| Direction | p = 0 | p = 0.25 | p = 0.5 | p = 0.75 | p = 1 |
| --- | --- | --- | --- | --- | --- |
| right | `(0, 0, 12)` → `(0,0,0)` | `(3, 0, 51)` → `(3,0,0)` | `(12, 0, 90)` → `(12,0,0)` | `(21, 0, 51)` → `(21,0,0)` | `(24, 0, 12)` → `(24,0,0)` |
| left | `(0, 0, 12)` | `(−3, 0, 51)` | `(−12, 0, 90)` | `(−21, 0, 51)` | `(−24, 0, 12)` |
| top | `(0, 0, 12)` | `(0, 3, 51)` | `(0, 12, 90)` | `(0, 21, 51)` | `(0, 24, 12)` |
| bottom | `(0, 0, 12)` | `(0, −3, 51)` | `(0, −12, 90)` | `(0, −21, 51)` | `(0, −24, 12)` |

(targets mirror the x/y components at z = 0; the table rows list `position → target` only where the target differs from the pattern — every row's target is `(x(p), y(p), 0)`. Every cell is recomputable from the pinned easings: `travelSwing(0.25) = 0.5` and `travelSwing(0.75) = 0.5`, so z is 51 at both; `easeInOutQuad(0.25) = 0.125` and `easeInOutQuad(0.75) = 0.875`, so the lateral is 3 and 21. At the followup's nine pinned progress values the z column is exactly the retained table `12/21.75/51/80.25/90/80.25/51/21.75/12` — the retention claim in the supersession ledger holds verbatim.)

**Spawn placement and the old cube's lifecycle.** The level advance's `levelChanged` intent marks the rebuild **pending**; the next `applySnapshot` (same frame, per the pinned session loop order `applyIntents → applySnapshot`) performs exactly one rebuild: the old cube view is disposed exactly once, the new view is built at the snapshot's grid size and style, and its group is placed at `old position + offset(direction)` (level 0 → level 1 with `right`: `(24, 0, 0)`; two consecutive `right` travels land at `(48, 0, 0)`). Exactly one cube view exists at any time — the old cube is **disposed at the midpoint**, so the world never grows and the accepted AC-16 drawable ceilings hold (fewer drawables than before: no plates). Reconciliation without an intent (style/grid change arriving in the snapshot) rebuilds in place with a zero offset.

**New cube's visibility during the path (framing gates).** With the real camera: the *old* cube's box (extent `CUBE_SIZE`, centred at the old position) is fully inside the frustum at p ∈ {0, 0.25}; the *new* cube's box is fully inside at p ∈ {0.5, 0.75, 1} — both at every supported aspect {2/3, 16/9, 7/3} (verified numerically: the binding corner stays well inside the smallest horizontal half-angle ≈ 17.27°).

**Backdrop.** The starfield anchor already copies the camera's live position and quaternion, so the anchored cone follows the lateral flight with zero change to `starfield.ts`; the expansion scale table (1 → 8 → 1 via `travelSwing`) is retained unchanged. The followup's corner-ray coverage gates keep passing at the retained level-0 poses and are **extended** to the directional poses — turn-around `(12, 0, 90)` and rest `(24, 0, 12)` — at aspects {2/3, 16/9, 7/3} × swirls {0, π/4} (translation-invariance: the camera stays axis-aligned, so the coverage argument transfers).

**Reduced motion (defined collapse — instant positional swap).** `travelMs` 150, no flight, no expansion: the camera stays at rest over the *current* cube at every p; at the midpoint the level advance rebuilds the cube at its new world position and the next snapshot puts the camera at rest over it — the swap is instant and positional, consistent with the accepted AC-12 collapse philosophy.

**Input stays gated** for the whole `travel` (engine contract unchanged). Stats and style carry-over, orientation reset, `travelStarted` once, `TRAVEL_LEVEL_ADVANCE_P` 0.5 — all retained.

**Future online hook (documented, no implementation).** The engine's direction draw and the scene's `CUBE_SPACING` offset mapping are the seams a future online feature replaces with server-assigned spawn positions plus occupancy checks ("must not be occupied by another cube" — only meaningful once other players' cubes exist; with one cube at a time there is nothing to collide with). Server authority, identity, and reconnection stay out of scope per `docs/product/realtime-backlog.md`.

## User stories

- As a player, I want every cube level to have a different, randomly generated number of mini-cubes, so each level feels fresh instead of always the same 5×5 grid.
- As a player, I want the cube to look like one giant cube built out of mini-cubes — no black plates or gaps between the tiles — so the object I click feels solid and tactile.
- As a player, I want the transition to the next cube to fly me toward it in the direction it actually spawned — left, right, above or below — and land me right in front of it, so level changes feel like exploring a world, not like a pop.
- As a player who prefers reduced motion, I want the same collapses as before — no flights, no expansion, an instant (positional) level swap.

## Open questions

- **Q-1 — Per-face count scheme (user checkpoint).** Pinned: **option (a)** — one random integer per level is the square grid edge N ∈ [3, 7] (N² per face, identical on all six faces). **Recommended: keep (a).** Option (b) — a random per-face count C laid out in a near-square grid with a partial last row — is rejected: a partial row leaves an uncovered strip (reintroducing exactly the "face showing between tiles" look this feature removes), breaks the flush edge-to-edge tiling argument, forces a picking-decode change (`√count` no longer decodes), and adds per-face layout state for no gameplay gain.
- **Q-2 — Grid range.** Pinned [3, 7] (9–49/face; 5 = the accepted size sits mid-range; the constant draw 0.5 → 5 keeps the accepted tests valid). **Recommended: keep.** Alternatives [4, 6] or [2, 8] are constant-only changes with a spec-revision note.
- **Q-3 — Surface vs volumetric cube.** Pinned: **surface tiling** — tiles sit proud of the body, which remains as the dark interior behind removed tiles. **Recommended: keep.** A full volumetric mini-cube lattice (N³ mini-cubes filling the volume) is rejected: it reworks board/picking/instancing wholesale and the request speaks about faces.
- **Q-4 — Direction set.** Pinned: four cardinal directions (left/right/top/bottom) as the request names. **Recommended: keep.** Eight directions (with diagonals) generalize the offset table but were not requested.
- **Q-5 — Spawn spacing and travel geometry.** Pinned: `CUBE_SPACING` 24; lateral `easeInOutQuad`, retained z swing 12→90→12, look target the lateral point. **Recommended: keep** — constant-only tuning otherwise (a spacing change is a one-constant edit with a spec-revision note).
- **Q-6 — Old-cube disposal.** Pinned: the finished cube is disposed at the travel midpoint (the retained rebuild-dispose path), so at most one cube view exists (AC-16 ceilings). **Recommended: keep.** Keeping the finished cube visible until arrival is rejected: two live cube views would break the accepted drawable ceilings and grow the world.
- **Q-7 — Level-advance timing.** Pinned: the followup's midpoint advance is retained (the new cube appears at the turn-around distance and the fly-in approaches it). **Recommended: keep.** Advancing at travel start would show the new cube during the whole departure (reads as "it was already there"); at the end, the approach half would fly toward empty space.
- **Q-8 — Future online occupancy (direction only).** Server-assigned spawn positions with occupancy checks will replace the engine's direction draw and the scene's offset mapping (the documented seams). Identity vs "no accounts" and server authority stay unresolved per `docs/product/realtime-backlog.md`. Not designed here.

## Assumptions

- "Going away … move camera to the left, right, bottom or top depending on where the other cube is" = directional world travel: the next cube spawns at a cardinal offset from the finished cube; the camera departs laterally toward it while pulling back, then flies in to rest over it (AC-3).
- Screen directions equal world axes because the camera is always axis-aligned with the identity quaternion (screen-right = +x, screen-up = +y) — pinned in § 3.
- "The mini-cubes generated for each face is a total random integer" = one random integer per level determines the per-face count, identical across all six faces (Q-1 option (a): the integer is the grid edge N; per-face count N²; cube total 6N²).
- "Giant cube made by mini-cubes" = flush, edge-to-edge tiling with no plates/gaps; the body stays as the dark interior behind removed tiles (Q-3).
- "Not occupied by another cube" is a future-online concern: single-player keeps at most one cube at a time (the old one is disposed at the midpoint), so no occupancy logic exists now (Q-8).
- The constant draw 0.5 maps to N = 5 and direction `top`, keeping the accepted engine tests' 25-per-face and travel assertions valid except the fixture re-pins named in the ACs.
- The per-level random walk is unbounded (positions drift from the origin over many levels); positions stay exact (integer multiples of 24) — acceptable single-player, no world bound.
- The followup's starfield coverage argument transfers to the lateral poses because the camera stays axis-aligned (translation only) and the anchor already copies the camera's full pose; the coverage gates are extended, not weakened.
- The engine's snapshot gains two required fields (`gridSize`, `travelDirection`); hand-built test fixtures in `session.test.ts` and `App.test.tsx` are updated in the same change (no optional fields — the engine always sets them, pinned by tests). The `levelChanged`/`travelStarted` intent shapes are unchanged: the spawn data travels on the snapshot and the rebuild trigger moves scene-side (implementation seam; the observable midpoint rebuild is unchanged).
- The session resolves `env.random` at attach (the engine exists from session creation for SSR/pre-attach snapshots; it runs on the deterministic LCG until attach injects `env.random` via the new `setRandomSource`) — production randomness is unchanged in effect (`browser-env.ts` remains the single browser-global reader).
- Mid-chain (after the game-layer task, before the render task) levels beyond 0 render at level 0's grid size and out-of-range picks no-op — documented in plan D-6 and resolved by the render task.
- Stack unchanged: `three@0.186.1` / `@types/three@0.186.0`, TypeScript strict, Vitest, ESLint; the project testing bar (concrete assertions, no banned matchers, ≥ 80 × 4 per workspace) governs.
- The accepted features' specs/plans/tasks stay authoritative for everything not superseded; this spec is read alongside them and never edits them.
