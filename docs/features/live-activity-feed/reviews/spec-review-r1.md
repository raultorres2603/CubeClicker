# Spec Review — r1

## Summary

❌ changes requested — 2 MAJOR, 8 MINOR, 2 INFO. The design is feasible and well grounded in the existing hub, protocol, reducer and single-live-region shell: the six server-derived events, the per-server 1/s ring, the additive `activityEvent`, the `welcome`/`worldEntered` snapshot, the `WorldState.activity` reducer, the non-live `ActivityFeed`, the privacy/isolation contract, the containerization no-change statement and the unit/integration/e2e strategy are all present. The blocking issues are internal contradictions, not security or architecture: the derivation ACs say "exactly one" event while the cadence drops candidates inside the 1 s window, and the move path records the move-in join first so the same move's completion is always dropped even though AC-7 says it is attributed to the new server. Six MINORs pin plan/test details (reconnect wording vs the 20-event ring, decoder parity, post-close inertness, move-in `except`, the leave predicate, and AC-10's newest-first order) plus the privacy-scan scope and the cross-server travel window. Q-1–Q-4 are genuine product-visible checkpoints and must be confirmed explicitly.

## Approval checkpoint

Q-1–Q-4 are **genuine** product-visible values and must be confirmed by the user, not inferred from the queue approval:

1. **Q-1 — Milestone cadence**: every 5th completed cube (first at Cube 5); alternatives 10th/25th.
2. **Q-2 — Cadence policy**: drop candidates inside the 1 s window (no queue/timer); one accepted event per server per second.
3. **Q-3 — Buffer and display**: 20 stored / 5 visible; alternatives 10/3 or 50/8.
4. **Q-4 — Placement**: top-center ticker below the connection banner, non-interactive, with a mobile offset.

Q-5 (completion precedence) and Q-6 (`worldEntered` snapshot) are user-visible defaults; Q-7–Q-14 are technical defaults. The orchestrator must present the four checkpoint values in `awaiting_approval` and record the confirmation in `status.md` before T1 starts.

## Notes / backlog (non-blocking)

- **Grounded derivation points are sound.** `handleCompletion` already captures `elapsedMs`/`bonus` before the cube reset (`hub.ts:1215-1230`), `broadcast` already supports `except` (`hub.ts:542`), and the move-in `memberJoined` broadcast already excludes the mover (`hub.ts:1277`); the plan can reuse these directly.
- **Metrics is exactly the two allow-list entries.** `metrics.ts:75-122` has the `type` allow-lists for `cubeclicker_ws_messages_encoded_total` and `cubeclicker_ws_frames_sent_total`; adding `activityEvent` there (and nowhere else) is the minimal correct change, and the 30-metric catalog count is unchanged.
- **Smoke predicate.** When adding the AC-27 check, match `event.type === 'memberLeft'` rather than assuming the next frame after `memberLeft`: if B's join event was accepted (joins more than 1 s apart), A's queue can hold a `memberJoined` activity frame before the leave. The existing `waitForMessage` already skips non-matching frames; use it with the type predicate and keep the existing 1 s grace.
- **UI keys.** `ActivityFeed` should use `key={event.id}` for the `<li>` list so a new event at the front mounts a new node and the 160 ms entry animation applies; the AC-21 CSS test alone does not prove the animation on insertion.
- **SSR test shape.** `App` renders from `useSyncExternalStore` with a server snapshot (`App.tsx:375-392`); the populated-feed SSR test should supply a fake session whose `getMultiplayerSnapshot().world` has `serverId > 0` and a non-empty `activity`, and whose `getSnapshot`/`getServerSnapshot` are pure.
- **Docs placement.** `docs/architecture/realtime.md` has `## Benchmark` at line 126; the new `## Activity feed` goes before it. `docs/product/glossary.md` uses `###` entries in alphabetical order; `### activity feed` belongs between `### account` and `### appearance`.
- **Ownership/scope checks pass.** The plan does not touch `docs/features/README.md`, `compose.yaml`, `compose.smoke.yaml`, either Dockerfile, `package.json`, `package-lock.json` or `.env*`; T5 proposes the index row only. The root `npm test`/`npm run test --workspace` scripts exist; coverage is per workspace with the 80% bar.
- **No new service/port.** The feed uses the existing `GET /ws` backend endpoint and the existing encode-once fan-out; the containerization contract is satisfied without a compose or Dockerfile change.
