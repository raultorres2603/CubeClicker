# Spec — Testing Acceptance Criteria

## Summary

Reflect the user's new testing acceptance criteria in the CubeClicker AI agent framework: when implementing code, the builder must ship **unit tests and integration tests**, keep **coverage at ≥ 80%**, write **no useless tests**, and assert with **concrete ("real") data** — never wildcard/loose matchers (`expect.anything()`, `expect.any()`, loose `objectContaining`/`arrayContaining`/`toMatchObject`, argument-unchecked `toHaveBeenCalled()`, snapshot-only or assertion-free tests). The criteria become checkable, not aspirational: `@vitest/coverage-v8` (the only sanctioned dependency addition — dev-only, official Vitest package, version-locked to the installed `vitest` 3.2.7) plus a `coverage` script in the root and both workspaces, and **thresholds of 80 for statements, branches, functions, and lines** in both workspace Vitest configs, scoped to `src/**/*.{ts,tsx}` with only justified exclusions (the two composition-root entrypoints). The frontend config's test discovery is extended to `.test.tsx` (component test files must actually be discovered and executed — F1 fix in r2), and the frontend gate is closed by named, DOM-free tests whose reachability is shown in § Testing strategy (F2 fix in r2). The framework files that govern planning, building, review, and orchestration are updated with pinned, additive contracts so every future feature is specced, built, and gated to this bar; `AGENTS.md` § Commands/§ Conventions/§ Boundaries and `README.md` § Commands carry the project-level statement. This feature is **self-consistent**: its own build measures the current baseline (unknown pre-build), closes the gap with meaningful tests within the existing tooling, and ends with `npm run coverage` green in both workspaces (policy in § Testing strategy). Per the 2026-10-16 framework-autonomy directive (quoted in `docs/features/online-realtime-workflow/spec.md` Q-1) there is **no user checkpoint**: the pipeline runs autonomously under reviewer oversight and genuinely open decisions are recorded in § Open questions with recommended resolutions.

## Scope

- `src/backend/vitest.config.ts`, `src/frontend/vitest.config.ts`: v8 coverage config — include/exclude (built-in defaults extended), thresholds 80 × four metrics, text-only reporter; the frontend config's test-discovery `include` is extended to `['src/**/*.test.ts', 'src/**/*.test.tsx']` so `.tsx` test files are actually discovered (backend discovery unchanged — F1).
- New/updated tests to close the baseline gap: `src/frontend/src/App.test.tsx` (new, SSR render path); `src/frontend/src/ws/connection.test.ts` — the **mandated** default-socket-factory top-up (stubbed global fake class, no real network — F2b); `src/backend/src/app.test.ts` only if the baseline reveals uncovered behavior.

Plus per-task build logs `build-log-T1.md … -T9.md` in this feature directory (evidence: baseline numbers, diffs, command transcripts, per-AC audit).

### Explicitly out of scope

- Any application behavior change: production modules (`src/backend/src/app.ts`, `server.ts`; `src/frontend/src/{App.tsx,main.tsx,ws/connection.ts}`) are not modified; tests/configs/docs only.
- Any dependency beyond `@vitest/coverage-v8` (no `jsdom`/`happy-dom`, no test frameworks, no reporters, no assertion libraries). No `.env*`.
- Coverage artifacts beyond console output: no HTML/JSON/clover reports, no badges, no CI upload; `reporter: ['text']` only.
- CI/pipeline enforcement machinery (no hooks, no workflows); no container/compose/Dockerfile changes; `npm run smoke` unchanged and not extended.
- Refactoring production code for testability; per-file coverage thresholds (`perFile`) and threshold auto-update (explicitly disallowed); adding tests solely to inflate numbers.
- Retrofitting other feature directories or `docs/features/README.md`; any `.opencode` permission change.
- Resolving the metrics-strictness or entrypoint-exclusion choices with the user: they are pinned here with recommendations and remain open for a future user-owned amendment (Q-1, Q-2).

## User stories

- As the project owner, I want the builder to deliver unit + integration tests at ≥ 80% coverage with real assertions, so regressions are caught instead of papered over.
- As the builder, I want an explicit, checkable bar (command, thresholds, assertion rules, no-useless-tests definition) so I know exactly when my task is done.
- As the reviewer, I want to rerun the coverage command and apply assertion-quality checks so weak tests cannot pass the code gate.
- As the planner, I want spec and task templates that force every feature to define its testing strategy to this bar.
- As the orchestrator, I want coverage evidence in the build gate and final summary so acceptance reflects the real state.

## Acceptance criteria

Verification notes: every AC states its evidence; **pre-build verification (spec gate) is inspection-only** — the coverage tooling does not exist yet. Post-build (code gate) commands are runnable: `npm run coverage` (and the workspace-scoped form `npm run coverage --workspace @cubeclicker/backend` / `…frontend`), `npm test`, `npm run lint`, `npm run typecheck`, plus `git diff`/`grep`/`npm ls`. "Baseline" = the coverage run recorded in `build-log-T1.md`. "Build-start baseline" = file content at a task's build start, recorded in its build log; diffs are checked against it. "Banned matchers" below means the Vitest forms of the request's "ItIsAny or something like that": `expect.anything()`, `expect.any(Constructor)`, `expect.objectContaining()`, `expect.arrayContaining()`, `expect.stringContaining()`/`expect.stringMatching()`, loose `toMatchObject()` (as a stand-in for pinning the full expected value), argument-unchecked `toHaveBeenCalled()`, snapshot-only assertions (`toMatchSnapshot`/`toMatchInlineSnapshot` as the sole assertion), assertion-free tests, and weak existentials used as stand-ins for a concrete expected value (`toBeTruthy()`/`toBeDefined()`/`not.toThrow()` where a concrete value can be asserted). The only escape is an exception meeting the exception rule: **≤ 1 per task**, justified in an in-test comment naming the concrete unavoidability reason (why no exact-value assertion is possible), reviewer-approved, and recorded in the review artifact. **Retroactivity:** the bar applies to new and changed test content; pre-existing tests are not retro-refactored by this feature (grep evidence covers the test diff). **Amendment trace:** in-place replacements are limited to the 16 pinned line replacements enumerated in `plan.md` § Pinned content contracts — contracts 3.C, 6.B, 6.C, 6.E, 11.A, 11.B, 12.A, 12.B, 14.A, 16.A, 19.A, 20.A, 21.A, 21.B, 22.B, 22.C; everything else is additive (additions include, e.g., 6.A, 6.D — the 🚫 append, 22.A — the stack.md table row).

## Non-goals

- No application behavior change, no production-source edits, no refactors for testability.
- No dependency beyond `@vitest/coverage-v8`; no DOM test environment, no additional frameworks/reporters/assertion libraries.
- No coverage report artifacts (HTML/JSON/clover), badges, or CI upload; console text only.
- No CI hooks/workflows; no container/compose/Dockerfile/smoke changes.
- No per-file thresholds, no threshold auto-update, no CI-level enforcement.
- No retrofitting of other feature artifacts; no `docs/features/README.md` changes beyond the orchestrator's own bookkeeping; no `.env*`; no permission changes.
- No mid-build carve-outs: if a metric cannot clear 80 with meaningful tests after the mandated close-path, the task reports `blocked` and options flow through the orchestrator (Q-5) — no in-feature threshold, exclusion, or include adjustments (F2c).
- No user checkpoint machinery: open decisions are recorded with recommendations (Q-1, Q-2), not escalated to the user.

## Boundaries

- ✅ Always: run lint, typecheck, tests, and the coverage command before reporting done; keep edits additive per the pinned contracts; record raw command evidence (baseline numbers, transcripts, greps) in `build-log-T<id>.md`; commit per task with a conventional message.
- ⚠️ Ask first: any exclusion beyond the two pinned entrypoints; any further dependency (the answer is no — report `blocked`; the single sanctioned dependency `@vitest/coverage-v8` and its sanction trace are in § Security considerations); lowering a threshold below 80 or widening the include set; touching any file outside the inventory.
- 🚫 Never: weaken assertions (banned matchers, snapshot-only, assertion-free tests) or exclude production code from coverage without a justified, reviewer-approved reason to make the gate pass; add dependencies; edit `.env*`; change permissions; push; rewrite pre-existing content beyond the pinned replacements; resolve Q-1/Q-2 unilaterally.

## Security considerations

- **Dependency addition (supply chain):** exactly one new dev-only dependency, `@vitest/coverage-v8` — official Vitest provider, MIT, version-locked to the installed `vitest` (peer requirement `vitest@3.2.7`); it pulls standard istanbul/test-exclude transitive dev packages. It is not part of production images or runtime artifacts and adds no runtime surface. Lockfile updated only via npm.
- **Sanction trace (F5):** the raw request requires ≥ 80% coverage, and Vitest — the decided test runner — has no coverage capability without a provider; the 2026-10-16 framework-autonomy directive (quoted verbatim in `docs/features/online-realtime-workflow/spec.md` § Open questions Q-1: *"I don't want you to ask for all. Please, update framework to work autonomsly without user's request. If needed because it's a blocker, ask user."*) requires the pipeline to apply the workflow-file operations this request mandates without a user checkpoint. Together they sanction exactly this one dependency — dev-only, official, version-locked — for this feature; any other dependency remains ask-first with the answer no (report `blocked`).
- **No secrets / no user data:** the feature touches no `.env*`, no credentials, no user-controlled data paths; the coverage command runs locally under existing shell permissions and produces console output only.
- **Framework self-editing:** the feature edits `.opencode/**` and `AGENTS.md` (content only, no permission entries); all edits are pinned, baseline-diffed (AC-22), reviewer-inspected, git-revertible, never pushed.
- **Test integrity as a security control:** the assertion-quality bar exists because weak assertions hide regressions (including in untrusted-input handling); the reviewer checks it, and new tests must not weaken existing coverage or introduce flaky/order-dependent patterns.
- **Containerization impact — explicitly none:** no services, images, ports, environment variables, health signals, or deployables are added or changed; coverage is host tooling (`npm`), like `npm test`; `compose.yaml`, both Dockerfiles, `compose.smoke.yaml`, and the containerized smoke test stay untouched. The entrypoint exclusions are compensated by the containerized smoke test, which exercises both composition roots through the container path (`npm run smoke`).
- **Real-time impact — explicitly none:** this feature changes no runtime behavior and no shared/cross-client state; connection lifecycle, reconnection, multi-client behavior, and server authority are out of scope here. The updated testing bar applies to future real-time features through the same skill/checklist edits (the existing `testing.md` real-time section is retained).

## Testing strategy

- **Baseline policy (cold start).** Current repo coverage is unknown; the planner cannot run npm. Policy: **T1 measures the baseline** (after tooling lands) and records per-workspace, per-metric numbers + exit codes in `build-log-T1.md`. The scaffold is tiny and the gap is small and bounded. **Frontend reachability (F2-corrected, r2):** the frontend production surface after exclusions is `ws/connection.ts` (10 functions), `App.tsx` (3 functions), and `main.tsx` (excluded as the entrypoint). Baseline: functions = 9/13 ≈ 69% — `defaultSocketFactory` (`connection.ts:33-35`) is unreached because the existing harness always injects `socketFactory`, and `App.tsx` is never imported. Close-path: (1) the SSR render test executes `App`'s render path but **not the effect callback or its cleanup (`App.tsx:17-23`) — SSR never runs effects, so those 2 functions remain uncovered without a DOM environment; this is accepted and stated honestly, not papered over**; (2) the **mandated** `connection.test.ts` top-up (stubbed global WebSocket class — no real network I/O) covers `defaultSocketFactory` and the `socketFactory ?? defaultSocketFactory` arm. Resulting functions = **11/13 ≈ 84.6% ≥ 80** — the gate clears only with the mandated top-up (without it: 10/13 ≈ 76.9%, red). Statements/lines: after both additions the only unexecuted statements/lines are the two effect-arrow bodies (2 of ~65) → ≈ 95%+; branches: the existing suite covers the state-machine sites and the top-up covers the factory fallback arm — a small number of defensive guard arms are unreachable by construction; the T1 transcript is the measured ground truth. **If** the measurement shows any metric that cannot clear 80 with meaningful tests, the builder reports it and the orchestrator surfaces the lawful options (a follow-up spec to sanction a DOM-environment dependency, or a user-owned threshold amendment) — no in-feature carve-out exists (Q-5); the accepted state must nonetheless leave the gate green and meaningful (AC-4, AC-5).
- **This feature's own tests:** unit-level where logic exists (the mandated `connection.test.ts` factory top-up — stubbed global, deterministic, no network I/O); integration-level where modules compose (`App.test.tsx` renders the component and asserts concrete output; backend route/WS behavior is already covered by real-socket tests). New tests follow the new bar (concrete assertions, no banned matchers, deterministic).
- **Verification commands (canonical, from `AGENTS.md` after AC-19):** `npm ci`; `npm run lint`; `npm run typecheck`; `npm test`; `npm run coverage` (the gate); `npm run coverage --workspace @cubeclicker/<workspace>` (per-task pre-gate form); `npm run smoke` (optional container regression check — the container path is untouched).
- **Inspection evidence:** per-file `git diff` vs. build-start baselines; grep anchors for the tokens named in each AC; `npm ls vitest @vitest/coverage-v8`; banned-matcher grep over test diffs; lockfile diff inspection; permission-block diff inspection.
- **Reviewer re-verification:** the reviewer reruns `npm run coverage` and the suite at the code gate, inspects exclusions/assertions, and treats anything unverifiable as unmet (AC-4, AC-9, AC-10, AC-23).

## Open questions

- **Q-1 — Metric strictness.** The bar is pinned as **all four metrics ≥ 80** (statements, branches, functions, lines, per workspace), which is strictly stronger than the request's single "80% of coverage" and closes metric-picking loopholes. **Recommended resolution: keep all four.** If the user prefers lines-only (or different thresholds), a one-line config amendment per workspace applies it; nothing in the framework structure changes.
- **Q-2 — Entrypoint exclusions.** `src/backend/src/server.ts` and `src/frontend/src/main.tsx` are the only excluded production files (composition roots whose behavior is exercised by the containerized smoke test). **Recommended resolution: keep.** Alternative considered and rejected: spawn-based entrypoint tests (disproportionate, flaky); leaving them in would drag the gate below 80 without adding meaningful assertions. Any additional exclusion requires a spec revision and reviewer approval (🚫 boundary).
- **Q-3 — Per-file thresholds.** Aggregate per-workspace thresholds are pinned; `perFile` is a possible future tightening (it would force each module ≥ 80). Not adopted now (tiny modules make per-file thresholds noisy); note for a future amendment.
