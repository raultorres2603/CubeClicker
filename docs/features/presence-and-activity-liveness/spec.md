# Spec — Presence & Activity Liveness

## Summary

Two user-facing bugs are fixed in one feature. **(1) Presence:** when a player closes the game, they currently stay listed on their game server — in the roster, the `Users on Server` panel, the live leaderboard entries/totals and the `members_active` gauge — for up to the 30 s reconnect grace window, and after a page reload they can appear twice (the old grace member plus the new one). The audit below shows this is not a broken grace timer: the hub applies `RECONNECT_GRACE_MS` to **every** socket close because there is no page-lifecycle signal that says "this was a deliberate close". When the new `leave` reaches the server before the reloaded page's `join` (the normal ordering), the old member is finalized and the reload produces one member; a lost/late frame or an already-disconnected socket falls back to the accepted grace and can still show the old member (and a second member/overflow) until expiry. The feature adds one additive client frame, `{ type: 'leave' }`, sent by the client on a non-bfcache `pagehide`; the hub finalizes that member immediately (the existing final-removal path: `memberLeft { reason: 'left' }`, destroy-if-empty, activity/leaderboard cleanup) while **abrupt** disconnects keep the accepted 30 s grace and token rejoin exactly as shipped. **(2) Activity liveness:** server activity currently never disappears; the ring keeps 20 events and the ticker shows the five newest until newer events push them out, and `welcome` replays the whole ring on reconnect. The feature makes activity temporal: `ACTIVITY_EVENT_TTL_MS = 5000`, the hub's `snapshot` (used by `welcome` and `worldEntered`) returns only events younger than 5000 ms and prunes the expired tail of the 20-event ring, and the frontend expires each displayed event 5000 ms after first receipt (current and pending-travel feeds), so an event is on screen for about five seconds and then disappears; expired events can never reappear on reconnect. No new service, dependency, persistence, database write, port, image or protocol version is added, and no existing wire shape changes.

## Context and root-cause audit

The audit was executed against the tree at planning time. The raw request is "When closing game, player remains on server, it's a bug." and "Also, server activity must be temporal, like 5 seconds message and then dissapears."

### What the user sees

1. Close the tab (or reload) → the other players still see the player's cube and name in `Users on Server`, in the roster-derived state, and in `Leaderboard` for a while; the leaver may be counted in `Server totals`.
2. Reopen/reload within that while → a second member with a new `Player N` name appears; on a full server the reloaded player can overflow to the next game server while the ghost still occupies a slot.
3. An activity line ("Player 2 joined", "Player 2 left", a clear, an epic) stays in the top-center ticker until five newer events push it out; reconnecting replays the whole 20-event ring.

### Conclusion

The grace expiry itself works: after `RECONNECT_GRACE_MS` the member is removed and `memberLeft (left)` is broadcast. The bug is the **missing distinction between a deliberate close and an abrupt disconnect**, so the grace path is applied to a deliberate close; the reload token loss then turns the retained ghost into a visible duplicate, and abnormal loss can stretch the window through the heartbeat budget. The fix must not remove or shorten the grace (that would break the accepted reconnect guarantee) — it must add an explicit, self-only leave signal and keep grace for the abrupt path.

## User stories

- As a player who closes the game, I want my name and cube to leave the server immediately, so other players do not keep seeing me.
- As a player who reloads, I want the old member gone and one new member, so I do not occupy two slots or overflow to another server.
- As a player with a flaky connection, I want my cube, identity and counters restored when I reconnect, so a blip does not cost my progress.
- As an account holder with multiple tabs, I want closing one tab to remove only that tab, so my other tab keeps playing.
- As a player, I want an activity line to stay on screen for about five seconds and then disappear, so the ticker reflects what is happening now.
- As a returning player, I want only recent activity in my `welcome`, so I do not rejoin into a wall of stale lines.
- As a screen-reader user, I want the ticker to remain a non-live landmark, so expiring lines never interrupt the game's announcements.
- As a maintainer, I want the presence and expiry rules to be server-authoritative, bounded, and provable by unit, integration and containerized tests.

## Presence contract

### Definitions

| Term | Definition |
| --- | --- |
| **Present on a server** | A member is present iff the hub's registry holds them in one of that server's occupied slots. Present has two sub-states: **connected** (a joined socket is attached) and **in grace** (the socket closed abruptly and `now < expiresAt`). Both are listed by the roster, the panel and the leaderboard, exactly as shipped. |
| **Explicit leave** | A joined connection sends `{ type: 'leave' }` (the client sends it on a non-bfcache `pagehide`). The member is finalized immediately on the existing final-removal path: no grace, removed from `members`, `tokens` and the registry; `memberLeft { playerId, reason: 'left' }` to the remaining members; the server is destroyed if it was the last member; the activity ring/leaderboard state is dropped (server destroyed) or marked for the next coalesced snapshot (server survives). The connection is then closed by the server. |
| **Abrupt close** | A socket close **without** an accepted `leave` (network drop, crash, killed tab, bfcache eviction with a closed socket, heartbeat termination). The accepted `RECONNECT_GRACE_MS` path is unchanged: the member stays in the roster/leaderboard for the window, the cube freezes, and `rejoin { token }` resumes the same member. |
| **Reconnect within grace** | `rejoin { token }` before the deadline resumes the same member, server, slot, cube and session counters, sends a fresh `welcome`, and cancels the grace timer. No duplicate member is created. |
| **Rejoin after leave** | Impossible by design: `leave` deletes the token, so `rejoin { token }` returns `error resume_failed`; the next `join` creates a fresh member (new `Player N`, new slot). |

### Lifecycle matrix

| Event | Grace timer | Roster / `Users on Server` | Leaderboard entries/totals | `members_active` | Reconnect |
| --- | --- | --- | --- | --- | --- |
| `join` | none | member appears (existing `memberJoined`) | next coalesced flush includes the member with zero counters; `welcome` includes them immediately | +1 | n/a |
| `rejoin` within grace | cancelled | member never disappeared | unchanged counters; `welcome` carries the current snapshot | unchanged | same member |
| Explicit `leave` | none created | member disappears with the immediate `memberLeft (left)` | dropped at the next coalesced flush (≤1000 ms) and absent from every later snapshot; a later `welcome` already excludes them | −1 immediately | `resume_failed`; a `join` creates a new member |
| Abrupt close | starts (`now + RECONNECT_GRACE_MS`) | member stays, cube frozen | member stays ranked with counters | unchanged | `rejoin { token }` resumes |
| Grace expiry without rejoin | expired | `memberLeft (left)`, server destroyed if empty | next flush drops the member and recomputes totals | −1 | token deleted; `resume_failed` |
| Cross-server move (completion) | n/a | existing `memberLeft (moved)` / `memberJoined` | counters travel with the member (accepted) | unchanged | unaffected |

### Derived views and timing

- The **immediate** surfaces after an explicit leave are the protocol `memberLeft` broadcast (next frame to every remaining member) and the reducer/roster/`Users on Server` panel built from it. The **leaderboard** is coalesced: the leaver drops at the next `leaderboardUpdate` (at most 1000 ms after the leave); a `welcome` built in that window is already correct because `snapshotFor` reads live members. This bounded transient is accepted and documented.
- `members_active` is `members.size`; it drops immediately on explicit leave and still includes grace members on the abrupt path (the metric's accepted meaning).
- No new presence field is added to `MemberState`, `welcome.roster`, `LeaderboardEntry` or `memberJoined`; grace members look identical to connected members (Q-2 proposes keeping this).
- Spectating is unchanged: when a spectated member leaves (explicit or grace expiry), the existing `memberLeft` handling auto-returns the spectator; a same-server `levelAdvanced` still keeps the spectator in place.

### Multi-tab, reload, and the last member

- One connection = one member (accepted). A `leave` removes only the sending connection's member; the account's other tabs, their sockets and their leaderboard rows are untouched. A multi-tab account may show two rows with the same username while both tabs are open (accepted `server-live-leaderboard` Q-8).
- A page reload (or tab close) sends `leave` on the non-bfcache `pagehide`. **When the leave reaches the server before the new page's `join` (the normal ordering), the old member is removed, so the reload produces one member and frees the slot for the new join.** If the frame is lost or late, or the socket was already disconnected, the old member remains in the accepted grace window and the new page can join as a second member — and, on a full server, overflow to the next server — until the grace expires. That is the accepted abrupt-close fallback, not a new bug; the normal ordering is what the feature adds.
- When the **last** member leaves explicitly, the server is destroyed immediately; there is no `memberLeft` recipient, no activity event for a destroyed server (accepted `live-activity-feed` AC-6) and no leaderboard state. An abrupt close keeps the server alive for the grace window, as shipped.
- A tab switch (`visibilitychange: hidden`), a backgrounded mobile browser that keeps the socket open, and a bfcache pagehide (`event.persisted === true`) **never** send `leave`: tab switching is not closing the game and entering bfcache may return to the same page/socket.

### Explicit leave is best-effort on unload

`pagehide` is the correct modern unload signal, and the frame is sent on the already-open socket; browsers do not guarantee delivery of any frame during teardown. If the frame is lost, the server sees a normal close and applies the accepted grace path, so the fix degrades to today's bounded behavior rather than corrupting state. The send is **exception-safe**: the session guards `transport.send` (a socket in `CLOSING`/`CLOSED` can throw from `WebSocket.send`), so a failed leave cannot throw out of the unload handler or skip the remaining cleanup (AC-7). `beforeunload`/`sendBeacon` alternatives are recorded in § Protocol and additivity; the chosen design adds no HTTP route, CSRF surface or storage.

## Temporal activity contract

### Constants and ownership

| Constant | Value | Home | Rule |
| --- | --- | --- | --- |
| `ACTIVITY_EVENT_TTL_MS` | `5000` | `src/backend/src/game/protocol.ts` and the frontend mirror `src/frontend/src/multiplayer/protocol.ts` | An event is **fresh** iff `serverNow - event.at < 5000`; at exactly 5000 ms it is expired. The client displays each event for 5000 ms from first local receipt. |
| `ACTIVITY_EXPIRY_TICK_MS` | `250` | `src/frontend/src/multiplayer/activity-lifetime.ts` | Fallback prune cadence: when no reduction occurs, an event is removed at the first tick at or after its display deadline (≤250 ms late). Every world reduction prunes synchronously before publishing, so a seeded/tombstoned event is never late. |
| `ACTIVITY_FEED_LIMIT` | `20` (unchanged) | both protocol mirrors | The in-memory ring still keeps at most 20 accepted events; TTL only filters what is delivered/displayed. |
| `ACTIVITY_MIN_INTERVAL_MS` | `1000` (unchanged) | backend `game/activity.ts` | Cadence is unchanged: at most one accepted event per server per trailing second. |

Because the cadence is 1/s and the TTL is 5 s, **at most five accepted events can be fresh at any instant**; the server snapshot therefore carries 0–5 events (still within the accepted ≤20 bound), and the ticker's five-visible cap aligns with the live window by construction.

### Server eligibility (authoritative)

- `activity.snapshot(serverId)` returns only fresh events, newest first, as fresh copies. Expired events are pruned from the tail of the ring before the copy; pruning changes neither `nextId` nor `lastAcceptedAt`, so ids keep advancing and the 1 s gate is unaffected.
- `record` continues to accept at most one event per trailing second, assign `id` on acceptance only, and keep 20 newest; it also prunes the expired tail so the ring never retains a stale suffix beyond the next access.
- `welcome` (fresh join **and** rejoin) and `worldEntered` (cross-server move) use `snapshot`, so an event that is 5000 ms or older at snapshot time can never travel. This is the guarantee behind "expired events must not reappear on reconnect"; the client expiry below is the display guarantee.
- The live `activityEvent` frame is unchanged: it is immediate, encode-once, and carries the accepted shape. The hub does not re-send or expire live frames.
- `dropServer` and `clear` keep their accepted terminal semantics; the ring count remains bounded by the live server count.

### Client display expiry

- `WorldState.activity` and `pendingWorldSwap.activity` hold accepted events until their display deadline passes; a removal is applied **synchronously on the reduction that seeds or changes the feed**, and the 250 ms interval is only the fallback for time passing between reductions (no interval tick is required for a tombstoned/expired seed to be rejected). A pure `pruneActivity(state, isExpired)` removes expired events from the current feed and the pending target feed, returning the same `WorldState` reference when nothing expired and preserving the untouched branch's identity.
- The session owns the lifetime bookkeeping: after **every** world reduction (`welcome`, `worldEntered`, `activityEvent`, `leaderboardUpdate`, any frame) and after `applyWorldSwap`, it observes the current and pending feeds with the local clock and records a display deadline (`receiptNow + 5000`) for each `serverId:id` **only if the key was not seen before**. The reduction then runs `pruneActivity` with the observed deadlines **synchronously, before any `publishMultiplayer()` call** — including the handler-specific publish inside `handleWelcome`/`handleWorldEntered`, not only the reduction's final publish — so a tombstoned or newly expired seed never enters the published feed, not even for one tick. Deadlines are keyed by `serverId:id` (server ids are never reused; ids restart at 1 per server), so a same-server rejoin that re-seeds the same event preserves the remaining lifetime instead of restarting it. A fresh join on a different server drops the old server's keys.
- A key that has expired locally is **tombstoned** for `ACTIVITY_EVENT_TTL_MS`: a later `welcome`/`worldEntered` seed of the same key is filtered out by the synchronous prune and cannot be published, even at a boundary where the server still considers it fresh. Tombstones and deadlines for servers that are neither current nor pending are dropped, so memory stays bounded.
- One session-owned interval (`ACTIVITY_EXPIRY_TICK_MS`) is the fallback that prunes both feeds while attached when no reduction occurs; becoming visible prunes immediately before the next frame, so a throttled background tab never returns with stale lines. The interval is cleared on `dispose()`; no callback, publish or state change occurs after dispose.
- The client never uses `event.at` for display expiry (the event clock is the server clock; the client clock may be skewed). Receipt-anchored deadlines make the five-second lifetime deterministic on the client; the server's `at`-based filter independently guarantees eligibility. No timestamp is displayed (accepted).

### Travel window

`worldEntered` seeds `pendingWorldSwap.activity` from the target `snapshot` and the session observes it, so target events received during the travel get deadlines; the reduction is synchronously pruned before it is published. The travel-midpoint `applyWorldSwap` makes the pending feed current with the same deadlines, then runs observe → synchronous `pruneActivity` → `publishMultiplayer`; old-server deadlines/tombstones are dropped. An old-server `activityEvent` is never applied to the new feed (accepted reducer guard), and an event that expired while travelling is pruned before/at the swap, never published for a tick.

### Reduced motion and accessibility

- Expiry is a state removal with **no exit animation**: no new keyframes, transition or motion token. The accepted 160 ms entry animation remains, disabled both by the session's `data-reduced-motion="true"` and by `@media (prefers-reduced-motion: reduce)`. Reduced motion changes nothing about content or lifetime.
- The feed remains a non-interactive complementary landmark (`<aside class="activity-feed" aria-label="Server activity" aria-live="off">`) with no `role="status"`/`alert`/`log`; `.phase-announcement` stays the shell's only polite/assertive live region. Removing a line after five seconds does not announce, move focus or change the accessibility tree's landmark structure; an empty feed renders `null`. The content is readable on demand within its lifetime; permanent history is a non-goal.

### Mixed versions

No wire field is added, so an old client against the new backend still decodes `activity` and live frames; it simply never expires them locally (it keeps up to the 20-event reducer cap until a new `welcome`). A new client against an old backend expires live events locally but may receive up to 20 snapshot events; the still-fresh ones are displayed for their local lifetime, the older ones are displayed once and expire (best effort). The deploy-together model is unchanged and no version bump is needed.

## Protocol and additivity

### Client `leave`

```ts
// Client → server, additive; no fields, no identity.
| { type: 'leave' }
```

- `parseClientMessage` accepts exactly `{ "type": "leave" }` (extra fields are dropped, like every catalog message) and returns `{ ok: true, message: { type: 'leave' } }`; both mirrors expose the same accepted fixture. A client frame with an unknown type is still `bad_message`.
- No server message is added: the existing `memberLeft { playerId, reason: 'left' }` carries the outcome. The server catalog, `welcome`/`worldEntered` shapes, `MemberState`, `LeaderboardSnapshot` and `ActivityEvent` are unchanged.
- The hub decodes `leave` only after a successful `join`/`rejoin`; before that it returns `error not_joined` (existing rule). The handler removes the connection's own member through the existing final-removal path, sets the connection's `closeReason` to `client`, and closes the peer; a later `close` event finds no member and starts no grace.
- No protocol version bump: an old client never sends `leave` and retains the old **presence** behavior (the grace path); it decodes the smaller `activity` snapshot described in § Mixed versions but does not expire live lines locally. A new client against an old backend gets `error bad_message` for `leave` (it is unloading, so the error is harmless) and the old grace behavior applies.

**Close-transport decision (not a user checkpoint).** The feature uses the WebSocket `leave` frame on non-bfcache `pagehide`; no HTTP route is added. This is a technical decision, not a product choice: the user-visible outcome (the member leaves when the page closes) is identical, and the alternative (`navigator.sendBeacon`/`fetch(..., {keepalive:true})` to a new backend endpoint) would be more reliable on unload but adds a route, a body-carried game token, origin/CSRF handling and a new failure surface for a best-effort action. The residual is explicit: a lost/late frame or an already-disconnected socket falls back to the accepted grace, and the user-visible consequence is the bounded second-member window described in § Multi-tab, reload, and the last member.

### Metrics

- `cubeclicker_ws_messages_received_total`'s closed `type` allow-list gains exactly one value: `leave`. This is required, not optional instrumentation: `inc` throws for an unlisted label value.
- No new metric; the encoded/frames allow-lists are unchanged because no server message type is added. `cubeclicker_members_active` and `cubeclicker_servers_active` keep their existing meaning and refresh points; an explicit leave drops them immediately, a grace close does not.

### Rollback

- **Presence rollback:** remove `leave` from both `ClientMessage` unions/decoders, the hub case/handler, the `pageLifecycle` source/subscription and the `leave` send, and the `leave` allow-list value. No stored data, flag, migration or operational state exists; rollback restores the unconditional grace path.
- **Activity rollback:** remove `ACTIVITY_EVENT_TTL_MS` and the snapshot filter/prune from `activity.ts`, and remove the frontend lifetime module, session interval/prune and `pruneActivity` helper. `WorldState` is unchanged either way; a restart clears everything.
- Both rollbacks are code-only and independent; deploy order is safe because no wire shape changed (the only additive frame is client → server and is self-only).

## Acceptance criteria

Verification notes: backend = `src/backend`, frontend = `src/frontend`. Evidence per AC is a test asserting concrete values or a command/transcript. All tests use concrete expected values (no wildcard matchers, no snapshot-only or assertion-free tests). Commands: `npm run lint`, `npm run typecheck`, `npm test --workspace …`, `npm run coverage --workspace @cubeclicker/backend|@cubeclicker/frontend` (pre-gate per task), and the full gates in the final task.

### Presence and explicit leave

- **AC-1 — Explicit leave removes presence immediately.** Given joined A (`p1`, slot 1) and B (`p2`, slot 2) on server 1 (capacity 2), when A sends `{"type":"leave"}` at hub time `t` and no timer is advanced, then: B receives exactly one `{"type":"memberLeft","playerId":"p1","reason":"left"}` and A receives none; A's fake peer records `close()`; immediately before the leave `vi.getTimerCount()` is 3 (A's heartbeat, B's heartbeat and the server's coalesced leaderboard timer) and immediately after the synchronous leave/close it is 2 (B's heartbeat and the leaderboard timer) — **no grace timer for `p1` remains**; and after advancing the clock by `RECONNECT_GRACE_MS`, B's received frames contain no second `memberLeft` for `p1` (final removal, no grace path). With a metrics-injected hub, `cubeclicker_members_active` is 1 and `cubeclicker_servers_active` is 1. Evidence: `hub.test.ts` (frames, fake-peer close, gauges, fake timers/`vi.getTimerCount()`), `metrics.test.ts`.

## Boundaries

- ✅ Always: keep the hub the only authority for presence; remove only the `leave` sender's member; preserve grace for every close without an accepted `leave`; send `leave` only on a non-bfcache `pagehide` while welcomed; key presence by the connection; use the injected hub clock and fake timers in tests; filter expired events server-side before any snapshot; expire displayed events client-side with one bounded scheduler; keep the shell's single live region; update docs in the same change; run the full gate.
- ⚠️ Ask first: changing `ACTIVITY_EVENT_TTL_MS`, `ACTIVITY_EXPIRY_TICK_MS`, the grace/heartbeat values, the 20-ring bound, the 5-item display or the 1 s cadence; adding a presence field, a quit button or an HTTP leave route; changing the `leave` wire shape; adding a dependency or npm script; touching container/package files; any coverage exclusion or threshold change.

## Security considerations

- **User-controlled data.** `leave` has no payload; the server removes the member attached to the sending connection. Extra fields (including a forged `playerId`) are dropped by the decoder and can never select another member. No free text, token, account id, email or IP enters the added path.
- **Authorization.** The connection's successful `join`/`rejoin` is the only authorization for `leave`; a non-joined connection gets `error not_joined`. Account identity remains server-resolved from the session cookie; guests and accounts use the same self-only path. A multi-tab account cannot remove another tab.
- **Abuse bounds.** A `leave` removes at most the sender and closes the socket; there is no fan-out amplification beyond the existing one-recipient-count `memberLeft` broadcast. No rate limiter is needed because the socket is closed by the server. The existing `MAX_MESSAGE_BYTES` (1024) and `MAX_CONNECTIONS` (200) are unchanged.
- **Page lifecycle.** `pagehide` is a browser event with no user data; the client sends a constant frame. No storage, beacon, URL or secret is involved; bfcache is respected (`persisted === true` sends nothing).
- **Temporal activity.** Expiry only removes server-issued events; no client value can extend an event's lifetime or create one. The server filter runs before copying; the client tombstone/deadline state is bounded by the feeds and cleared with the session.
- **Persistence integrity.** Not applicable: nothing is persisted, no database write is added, and a restart clears every member, ring and deadline.
- **Logging/metrics hygiene.** The `leave` frame content is never logged (the existing logging contract logs no message bodies); the metric label is the closed `type` value. No new PII or high-cardinality series is added.
- **Dependencies/secrets.** No new dependency, secret, environment variable or `.env*` change.

## Real-time contract

**Server authority.** The hub is the only authority for presence: a member is present iff the registry holds them; `leave` is a validated request from a joined connection that removes only that connection's member; no client-reported roster, presence flag or timestamp is trusted. Activity `at`/`id` remain hub-assigned, and only the hub decides whether an event is eligible for a snapshot.

**Connection lifecycle.** connect → `hello` → `join`/`rejoin` → `welcome`; an abrupt close starts the 30 s grace and a rejoin within it resumes the same member; an explicit `leave` finalizes immediately and closes the socket; a heartbeat timeout is an abrupt close. There is no other presence state.

**Reconnection.** An abrupt close within grace resumes identity, cube, slot and session counters exactly (accepted). An explicit leave deletes the token and is terminal; when the reload/close's `leave` reaches the server before the next `join`, the next connection creates a new member with the old member already gone. If the leave is lost or late, or the socket was already disconnected, the old member remains in the accepted grace window and the new page can join as a second member (and overflow on a full server) until expiry — the documented best-effort residual, not a new state. A rejoin `welcome` carries only unexpired activity, so a long disconnect cannot replay expired events. The hub keeps no per-client queue and never replays missed frames individually.

**Multi-client behavior.** Every remaining member receives the same encoded `memberLeft(left)` bytes after an explicit leave (the leaver is removed before the broadcast, so it receives none). Roster/`Users on Server` update on that frame; the leaderboard updates at its next coalesced flush (≤1 s) and every later `welcome` is already correct. A multi-tab account is multiple members: one tab's leave cannot remove another's. No member ever receives another server's presence or activity.

**Identity vs. "no accounts".** No conflict: `leave` is identity-agnostic and self-only; guests and accounts behave identically. Account identity, session cookies, token resume and the one-connection-one-member rule are unchanged. Multi-tab duplicate rows are the accepted membership model, not an account-merge feature.

**Latency.** Explicit removal and the `memberLeft` broadcast are synchronous on frame receipt; the leaderboard is bounded by its accepted 1 s coalescing; the activity `memberLeft` event is subject to the accepted 1 s per-server gate. Activity display expiry is 5000 ms from receipt; the fallback interval removes a line within 250 ms after the deadline when no reduction occurs, and every reduction prunes synchronously before publish. Abrupt presence is bounded by grace (and, for a half-open socket, by the heartbeat before it).

**No persistence.** Presence, rings and deadlines are process memory only; a backend restart clears them.

**Slow clients and shutdown.** No per-client queue is added; the transport owns buffering/backpressure. `hub.close()` remains terminal: no send, timer callback or membership mutation after close, and the new expiry scheduler is client-side only.

The explicit-leave reliability residual (WS best-effort vs an HTTP beacon) is documented in § Protocol and additivity and § Explicit leave is best-effort on unload; it is not asking the user to choose a transport.

## Open questions

Q-3 (close transport) is resolved in § Protocol and additivity as the WebSocket `leave` frame; it is not an open question and is not in the approval checkpoint. The remaining questions:

- **Q-1 — Activity lifetime.** Recommended **5000 ms** (`ACTIVITY_EVENT_TTL_MS = 5000`): the user's "about 5 seconds", visible enough to read, short enough that the ticker stays current. Alternatives: 3000 ms (calmer, harder to read) or 8000 ms (easier to read, slower to clear).
- **Q-2 — Grace presence display.** Recommended **no new field/marker**: a grace member is present and listed exactly as shipped, because the member may resume and the roster is the only presence list. Alternative: an additive `presence: 'connected' | 'grace'` on `MemberState` + a panel marker (more protocol/UI surface, a new product state).
- **Q-4 — Multi-tab.** Recommended **per-connection** presence/leave (the accepted one-connection-one-member rule). Alternative: account-merged presence, which needs account identity in the roster and a different identity model.
- **Q-5 — Client expiry anchor.** Recommended **receipt time** (`receivedAt + 5000`), never the server `at`, so client clock skew cannot hide or extend a line; a same-server rejoin preserves the remaining deadline via the `serverId:id` key. Alternative: derive from `event.at` + a `hello.serverTime` offset (more precise across long seeds, more clock machinery).
- **Q-6 — Expired re-seed guard.** Recommended **a bounded tombstone** for a locally expired key (`ACTIVITY_EVENT_TTL_MS`), so a boundary reconnect cannot re-display it. Alternative: rely only on the server filter (simpler, but a sub-second boundary can re-seed a locally expired key).
- **Q-7 — Ring size under TTL.** Recommended **keep 20** (`ACTIVITY_FEED_LIMIT`), even though at 1/s and 5 s at most five are fresh: it preserves the accepted bound, keeps the `ttlMs` seam test meaningful and has trivial cost. Alternative: reduce to 5 (less memory, a protocol-visible constant change).
- **Q-8 — Snapshot lifetime for a fresh join.** Recommended **full 5 s from display** for each event the server still considers fresh; an event accepted just before a join is shown for its local five seconds. Alternative: compute the remaining server age (needs clock-offset machinery; Q-5).
- **Q-9 — Leave socket close.** Recommended **the server closes the socket** after finalizing the member, so no orphan connection can `join` again. Alternative: keep it open for a re-join (extra state for no product benefit during unload).
- **Q-10 — Heartbeat/grace values.** Recommended **unchanged** (30 s/2 missed pongs, 30 s grace): the explicit close path bypasses them, and shortening either reopens accepted liveness timing and false-disconnect risk. Alternative: a shorter heartbeat (faster abnormal cleanup, more false disconnects).
- **Q-11 — Activity leave event.** Recommended **yes**, an explicit leave records the same `memberLeft` candidate as grace expiry (subject to the accepted 1 s gate), because "Player left" is meaningful presence information. Alternative: no activity line on explicit leave (quieter, but the ticker would omit a real leave).
- **Q-12 — bfcache.** Recommended **do not leave on `persisted === true`** (the page may return and the socket may survive); the transport's existing retry handles a socket that was closed. Alternative: always leave (no ghost on back/forward, but breaks a bfcache return).
- **Q-13 — Documentation home.** Recommended **`docs/architecture/realtime.md` + glossary + observability/admin docs**, with `frontend-rendering.md` for the session seam; no new document. Alternative: a new presence architecture doc (fragments the outbound contract).
- **Q-14 — Smoke proof.** Recommended **keep the existing `checkMultiplayerFlow` B abrupt-close grace check and add D's explicit leave + E's freed-slot join**, reusing the 1 s smoke grace and the existing `>= 900 ms` / `< 900 ms` bounds; no 5 s TTL wait in smoke. Alternative: unit/integration only (leaves the real wire presence path unproven).

## Assumptions

- One backend process with in-memory rooms; presence, rings and deadlines are process memory only; a restart clears everything. No Redis, queue, microservice or persistence is introduced.
- The hub's injected clock (`HubDeps.now`) is the only server time source; it is non-decreasing in production and controlled by tests. `activity.at` and the TTL comparison use it.
- `pagehide` is the browser lifecycle event the client uses; `event.persisted === true` means bfcache and sends nothing. The frame is best-effort; a lost/late frame or an already-disconnected socket falls back to the accepted grace behavior. Reload ordering is therefore best-effort: when the `leave` reaches the server before the new page's `join`, the reload produces one member; otherwise the old member remains in grace and a second member (and possible overflow) can coexist until expiry — the accepted abrupt-close fallback, not a new state.
- React StrictMode/remount `dispose()` is **not** a leave; only `pagehide` sends `leave`. `dispose()` closes the socket and the server applies grace, so a remount within grace reconnects.
- The **session** sends `leave` through the transport only while `welcomed` and connected; a page closed while disconnected cannot deliver it (grace expiry remains the fallback). The transport itself has no `welcomed` concept — it only writes while its send target is open.
- A `leave` is terminal for the member: the token is deleted and the socket is closed; the next connection uses `join`.
- The frontend and backend deploy together; no protocol version negotiation exists. The additive `leave` and the unchanged server catalog are safe in both deploy orders; the old-client mixed behavior is documented.
- The activity cadence remains 1/s, so at most five events are fresh under a 5 s TTL; the 20-event ring remains an upper bound, not a promised snapshot size.
- Client display deadlines are receipt-anchored; `event.at` is never used for client expiry. `serverId:id` is unique for the life of the process because server ids are never reused and per-server event ids are monotonic.
- An explicit leave is a final removal: it takes the same `removeMember` path as grace expiry, including the activity/leaderboard cleanup, so the accepted derived views need no new state.
- Existing suites (`ActivityFeed.test.tsx`, `App.test.tsx`, `game-view.css.test.ts`, `UserPanel.test.tsx`, `Leaderboard.test.tsx`) remain green without weakening; only TTL/leave expectations are added or re-pinned with the same concrete rigor.
