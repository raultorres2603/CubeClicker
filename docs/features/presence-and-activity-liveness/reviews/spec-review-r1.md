# Spec Review — r1

## Summary

❌ changes requested — 4 MAJOR, 7 MINOR, 4 INFO. The root-cause audit is verified against the tree and the core design is sound: a self-only `leave` on a non-bfcache `pagehide`, immediate finalisation through the existing `removeMember` path, retained abrupt-close grace/token rejoin, a server-side 5000 ms snapshot filter with tail pruning, receipt-anchored client expiry, and no wire-shape/version/dependency/service change. The AC set, dependency graph, `files_owned`, coverage and containerization contracts are otherwise strong.

Four concrete defects must be fixed before building:

1. **AC-3** expects the post-leave fresh join to be `p2` / `Player 2`, but AC-1 already assigned B = `p2` / `Player 2`; the hub's monotonic `playerCounter` yields **`p3` / `Player 3`** (`hub.ts:1089-1095`). The AC as written cannot pass.
2. **AC-5** expects C's `welcome.roster` to be `[B, C]`, but A's leave frees slot 1 and C fills the lowest free slot, so slot-ordered roster is **`[C, B]`** (`servers.ts:94-101,130-142`; `hub.ts:714-724`; the existing hub test at `hub.test.ts:717-726` pins the same shape).
3. **AC-15** mixes a same-server rejoin at 4000 with a pending travel seeded at 1000, but `reduceWorldState` clears `pendingWorldSwap` on every `welcome` (`server-state.ts:432-447`), so the 5000/6000/7000/8000 expectations cannot coexist with that rejoin in one chronology.
4. **AC-1/AC-2/AC-4** assert hub internals (`grace.expiresAt`, `rosterFor`, `collectLeaderboardMembers`, `registry.serverCount`, `members.size`) that the `GameHub` interface (`hub.ts:290-314`) does not expose; `hub.test.ts` can assert the outcomes only through frames, metrics, timers and rejoin failures, or through a new test seam the plan does not declare.

The seven MINORs cover the Q-3 technical checkpoint, the reload-ordering guarantee, the smoke's existing leave check, the old-client AC wording, the pagehide send's exception safety, the T8 false-positive grep, and the `user-authentication` AC-25 supersession wording.
