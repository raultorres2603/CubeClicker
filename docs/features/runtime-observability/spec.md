# Spec — Runtime Observability

## Summary

CubeClicker currently has no structured backend logging, no counters or metrics endpoint, and no way to prove production connection counts, room occupancy, message rates, rate-limit drops, heartbeat terminations, database latency, or the pending depth of the removal/economy flush queues added by `realtime-broadcast-batching`. `src/backend/src/app.ts:193` constructs `Fastify()` without a logger, so every request and connection is invisible unless it fails loudly; the only health signal is `GET /healthz`. This feature adds **runtime observability without new infrastructure**: Fastify/Pino structured JSON logs with strict redaction and request/connection correlation; an in-process metrics registry with a fixed, low-cardinality catalog covering connection lifecycle, rooms/capacity, messages and broadcast fan-out, removal/economy flush depth and cadence, rate-limit drops, database pool/query latency, economy/upgrade revision rejections and shutdown; a Prometheus-text `GET /metrics` endpoint on the existing backend port that the ALB does not route; and a dev-only frontend performance overlay behind `VITE_PERF_OVERLAY`. No server, image, port, dependency, observability stack or public exposure is added. Raw request: "Please, find any kind of performance optimizations we can do on project and, also, find new skills we added and provide some new features you think are good to have" followed by "Proceed with all of them, one by one"; this is the next approved feature in the audit queue.

## Context and audit evidence

Verified by the read-only audit at planning time:

- `src/backend/src/app.ts:193` — `Fastify()` is built with no logger configuration; `src/backend/src/server.ts` only has `console.log`/`console.error`; no request, connection or shutdown event is structured.
- `src/backend/src/app.ts:251` — the only observability endpoint is `GET /healthz` (`{"status":"ok"}`); no `/metrics` route, counters, gauges or histograms exist anywhere in `src/backend/src`.
- `src/backend/src/game/hub.ts:441-488` — broadcasts and account broadcasts are the hot outbound paths; `hub.ts:680-702` owns heartbeat termination; `hub.ts:922-928` and `hub.ts:1326-1329` drop rate-limited frames; `hub.ts:999-1042` rejects stale economy/upgrade revisions.
- `src/backend/src/game/broadcast.ts:41-65` — the removal batcher exposes `pendingGroups()` and the economy coalescer exposes `pendingAccounts()`; these depths are operationally important after batching but are not exposed.
- `src/backend/src/db/pool.ts:33-44` — the Postgres pool is created without any query latency or pool-gauge instrumentation.
- `docs/architecture/deployment.md` § WebSocket edge handling — the ALB routes only `/ws`, `/auth*` and `/healthz` to the backend; `/` (default) goes to the frontend. A backend `/metrics` path is therefore not publicly reachable by default, and this feature adds no ALB route.
- `infra/terraform/modules/ecs/main.tf:192-216` — the deployed backend already runs with `NODE_ENV=production` and the `awslogs` driver; its CloudWatch log group has `retention_in_days = 30`. No logging infrastructure change is needed.
- The stack is one backend process, Fastify + `@fastify/websocket`, Postgres only for accounts/economy; there is no Redis, queue, Prometheus, Grafana, Loki, OpenTelemetry SDK or external SaaS, and none is added.

## User stories

- As a maintainer, I want one place to see whether the backend is accepting connections, how many rooms and members exist, and whether message/fan-out rates are normal, so I can diagnose a production problem without attaching a debugger.
- As a maintainer, I want heartbeat terminations, rate-limit drops, stale economy/upgrade revisions and shutdown events counted, so silent degradation becomes visible.
- As a maintainer, I want removal/economy pending depths and flush cadence exposed, so a regression in the batching scheduler is detectable before it becomes a latency incident.
- As an operator, I want database pool saturation and query latency visible without SQL text or user data, so I can tune the pool safely.
- As a security reviewer, I want assurance that passwords, session cookies, authorization headers, emails and verification tokens never appear in logs or metrics labels.
- As a developer, I want a dev-only overlay showing frame time, renderer draw calls/triangles, quality tier and WebSocket RTT, so client performance can be inspected in a local build without shipping debug UI.

## Acceptance criteria

### Structured logging and privacy

- **AC-1 — Environment log levels.** `buildLoggerOptions(env)` resolves the level as: `NODE_ENV=production` → `info`; `NODE_ENV=development` → `debug`; `NODE_ENV=test` or an unset `NODE_ENV` with no `LOG_LEVEL` → logging disabled (`false`); `LOG_LEVEL` explicitly set overrides all of these and accepts exactly `fatal|error|warn|info|debug|trace|silent`. An invalid `LOG_LEVEL` (for example `verbose`) throws an `Error` whose message names `LOG_LEVEL`. Evidence: `logging.test.ts` table, and an `app.test.ts` assertion that `buildApp({ NODE_ENV: 'production' })` has a logger while `buildApp({})` does not.
- **AC-2 — Redaction and no request bodies.** The logger uses Pino redaction with censor `[REDACTED]` for the top-level paths `email`, `password`, `pass`, `token`, `sessionToken`, `verificationToken`, `cookie`, `authorization`; the request/response paths `req.headers.cookie`, `req.headers.authorization`, `req.headers['x-api-key']`, `res.headers['set-cookie']`, `req.body.email`, `req.body.password`, `req.body.pass`, `req.body.token`, `req.body.sessionToken`, `req.body.verificationToken`; and the wildcard forms `*.email`, `*.password`, `*.pass`, `*.token`, `*.sessionToken`, `*.verificationToken`, `*.cookie`, `*.authorization`. A log call that includes `{ email: 'alice@example.test', password: 'hunter2', token: 'tok-1', cookie: 'session-secret', authorization: 'Bearer secret', body: { password: 'nested-pass', email: 'nested@example.test' }, headers: { cookie: 'nested-cookie', authorization: 'Bearer nested' } }` emits `[REDACTED]` for every one of those values and none of the raw values. A real `POST /auth/login` request carrying an email and password emits no request body and no raw email/password/session-cookie value. Evidence: `logging.test.ts` captured-stream assertions for the top-level and nested fields, and `app.test.ts` for the login flow.
- **AC-3 — Request/connection correlation.** Every WebSocket connection log uses the Fastify request id as `connectionId` (`req.id`), so it correlates with the matching HTTP upgrade request log. The hub receives a `LogSink` whose `info(event, fields)`/`warn(event, fields)` methods are backed by a Pino adapter calling `logger.info(fields, event)`/`logger.warn(fields, event)`; the structured fields are emitted, not silently dropped. A connection open emits `ws_connection_opened { connectionId }`; a client close emits `ws_connection_closed { connectionId, reason: 'client', durationMs >= 0, wasJoined }`; a heartbeat termination emits `ws_heartbeat_timeout { connectionId, wasJoined }` and `ws_connection_closed { reason: 'heartbeat' }`; a capacity rejection emits `ws_connection_rejected { connectionId, reason: 'capacity' }`. No log field contains `playerId`, `accountId`, `username`, `email`, `remoteAddress` or query-string values. Evidence: `app.test.ts` (open/close over a real socket with a captured logger), `hub.test.ts` (heartbeat/rejection with an injected `LogSink` recorder).
- **AC-4 — Safe error serialization.** The logger's `err` serializer emits exactly `{ type, code? }` (`type` from `error.name`, `code` only when it is a string) and never `message`, `stack`, request/response bodies, SQL text or query parameters. Logging `new Error('alice@example.test')` emits an `err` object with no email and no `message`/`stack` keys; an error with `code: 'ECONNRESET'` includes that code. Evidence: `logging.test.ts`.
- **AC-5 — No PII in logs.** After a full account login + `/auth/me` + WebSocket join flow in one test app, no captured log line contains the test email, password, username, session cookie value, verification-token value, remote IP value, `playerId`, `accountId` or `serverId`. Evidence: `app.test.ts` exact `not.toContain` assertions over the concatenated captured stream.

### Metrics format, catalog and exposure

- **AC-6 — Prometheus text format.** A seeded registry renders deterministic Prometheus text: sorted `# HELP`/`# TYPE` blocks, `name value` samples, labels sorted by name, label values escaped by the exported `escapeLabelValue` helper, histogram `_bucket{le="…"}`/`_sum`/`_count` samples (the `le` label is renderer-reserved), a final newline, and no ANSI or JSON wrapper. `escapeLabelValue` escapes backslash as `\\`, double quote as `\"` and newline as `\n`; `escapeLabelValue('a"b\\c')` returns `a\"b\\c`, and the renderer emits that sample as `label="a\"b\\c"`. `GET /metrics` returns `200`, `content-type` exactly `text/plain; version=0.0.4; charset=utf-8`, `cache-control: no-store`, and the same body. Evidence: `metrics.test.ts` exact-string render plus `escapeLabelValue` cases and `metrics-route.test.ts` `app.inject`.
- **AC-7 — Fixed catalog and bounded labels.** The registry defines exactly the 30 metrics in § Metrics catalog, each with its type, help text, label names and allowed label values. `inc`/`set`/`observe` throw when a metric is unknown, a label name is undeclared, a declared label is missing, or a label value is outside its allow-list. Catalog-declared label names are only `reason`, `type`, `scope`, `result` and `signal`; histogram `_bucket` samples additionally carry the renderer-generated reserved `le` label, which is not part of any definition and is exempt from the catalog value allow-list. There is no catalog label whose name is `playerId`, `userId`, `accountId`, `email`, `token`, `ip`, `remoteAddress` or `serverId`. Evidence: `metrics.test.ts` (including a rejected `type: 'attacker-controlled'` label) and an `app.test.ts` scrape after two account joins.
- **AC-8 — Internal-only exposure on the existing port.** With `METRICS_ENABLED` unset or `true`, `GET /metrics` is served by the existing backend on port 8080; with `METRICS_ENABLED=false` the route is not registered and returns `404`. No new listen port, host mapping, compose service, Dockerfile, ALB listener rule or Terraform route is added: `infra/terraform` contains no `/metrics` path, and `docs/architecture/deployment.md` still lists only `/ws`, `/auth*`, `/healthz` as backend routes. The only compose changes are safe environment pass-throughs — backend `LOG_LEVEL: "${LOG_LEVEL:-debug}"` and `METRICS_ENABLED: "${METRICS_ENABLED:-true}"`, and frontend `VITE_PERF_OVERLAY: "${VITE_PERF_OVERLAY:-false}"` — so the documented local overrides reach the containers (AC-24/AC-25); `compose.smoke.yaml`, both Dockerfiles and `infra/terraform` are unchanged. Evidence: `metrics-route.test.ts`, `git diff --exit-code -- infra/terraform compose.smoke.yaml src/backend/Dockerfile src/frontend/Dockerfile`, `grep -F 'LOG_LEVEL' compose.yaml`, `grep -F 'METRICS_ENABLED' compose.yaml`, and a grep for `"/metrics"` under `infra/terraform` returning no match.
- **AC-9 — Containerized endpoint proof while joined.** `tests/e2e/smoke.mjs` adds a dedicated `checkMetrics` step that, after the multiplayer/auth checks, opens one WebSocket client, reads `hello`, sends `join`, waits for `welcome`, and **while that client is still joined** fetches `http://backend:8080/metrics`. It records a PASS line asserting: `200`, Prometheus content type, `# TYPE cubeclicker_ws_connections_open gauge`, `cubeclicker_ws_connections_open` with value `>= 1`, `cubeclicker_servers_active` with value `>= 1`, `cubeclicker_ws_connections_total` with value `>= 3`, `cubeclicker_ws_messages_received_total{type="join"}` with value `>= 3`, and `cubeclicker_ws_frames_sent_total{type="hello"}` with value `>= 3`. It then closes the client and waits the existing settle budget so the registry drains before exit. `npm run smoke` exits 0 and the existing checks stay green. Evidence: raw `npm run smoke` output in the T5 build log; frontend-prod is rebuilt first per AC-26.

### Counters and instrumentation

- **AC-10 — Connection lifecycle.** With a metrics-injected hub: two attaches set `cubeclicker_ws_connections_open` to `2` and `cubeclicker_ws_connections_total` to `2`; a client close sets the gauge to `1` and increments `cubeclicker_ws_connections_closed_total{reason="client"}` by `1`; a capacity rejection increments `cubeclicker_ws_connections_rejected_total{reason="capacity"}` by `1`; a heartbeat miss path increments `cubeclicker_ws_heartbeat_timeouts_total` by `1`, closes with `reason="heartbeat"`, and observes `cubeclicker_ws_connection_duration_seconds`. Evidence: `hub.test.ts` with fake peers, fake timers and an exact-render assertion.
- **AC-11 — Messages, encode-once and fan-out.** Two members join one server; after the second `welcome`/`memberJoined` settles, record the current counters as the baseline. One accepted explode then flushes one `miniCubeRemoved`: the deltas are `cubeclicker_ws_broadcasts_total +1`, `cubeclicker_ws_messages_encoded_total{type="miniCubeRemoved"} +1`, `cubeclicker_ws_frames_sent_total{type="miniCubeRemoved"} +2` (one per recipient, proving one encode and two deliveries), and `cubeclicker_ws_broadcast_fanout` count `+1` with sum `+2`; the cumulative join counter is `2` and the explode counter is `1`. The second join's `memberJoined` broadcast is therefore outside the removal measurement window. A malformed frame increments `{type="invalid"}` and an oversized frame increments `{type="oversized"}`. Evidence: `hub.test.ts` baseline/delta metric samples.
- **AC-12 — Rooms, members and capacity.** While the hub is open, after joins, a move/leave and a server destroy, `cubeclicker_servers_active`, `cubeclicker_members_active`, `cubeclicker_server_capacity` and `cubeclicker_ws_connections_capacity` equal `registry.serverCount()`, `members.size`, `config.maxUsersPerServer` and `config.maxConnections` respectively at every asserted step (including `0` servers after the last member leaves). These registry-equality assertions do not apply after `hub.close()`; AC-13 defines the post-close gauge values as a metrics-only shutdown reset. Evidence: `hub.test.ts`.
- **AC-13 — Removal/economy flush depth and cadence.** After `enqueue`, `cubeclicker_removal_batch_pending_groups` equals `1`; after a flush it returns to `0`, `cubeclicker_removal_flushes_total` increments by `1`, `cubeclicker_removal_ids_total` increments by the flushed ids, and `cubeclicker_removal_batch_size_count` increments by the flushed groups. After `queue`, `cubeclicker_economy_pending_accounts` equals `1`; after the cadence flush it returns to `0` and `cubeclicker_economy_flushes_total` increments by `1`. `hub.close()` sets the pending, open-connection, member and server gauges to `0` as a metrics-only shutdown reset even though the in-memory registry object is not cleared; the test does not assert registry equality after close. Evidence: `hub.test.ts` with fake timers.
- **AC-14 — Rate-limit drops.** Thirty admitted explodes in one trailing second followed by a 31st explode yields `rate_limit_drops_total{scope="explode"}` exactly `1` while `messages_received_total{type="explode"}` is `31`; the 21st rotate in one second yields `{scope="rotate"}` exactly `1`; a denied auth request through `createRateLimiter(now, onDenied)` calls `onDenied` once and a `scope="http"` counter increments by `1` in the app. No limiter key (IP/email) is logged or used as a label. Evidence: `hub.test.ts`, `rate-limit.test.ts`, `app.test.ts`.
- **AC-15 — Stale revision rejections.** A late economy result with `revision <= lastAppliedRevision` increments `cubeclicker_economy_revision_rejections_total` by `1` and leaves every member's economy unchanged; a late purchase with `revision <= lastAppliedUpgradeRevision` increments `cubeclicker_upgrade_revision_rejections_total` by `1` and leaves upgrades/`upgradesUpdate` unchanged. A result rejected only because the hub is closed is not counted. Evidence: `hub.test.ts` out-of-order cases.
- **AC-16 — Database pool and query latency.** `instrumentPool` wraps a promise-returning `query`; a resolved query increments `cubeclicker_db_queries_total{result="ok"}` by `1` and observes exactly `0.012` seconds into `cubeclicker_db_query_duration_seconds` for an injected 12 ms clock; a rejected query increments `{result="error"}` by `1` and rethrows the original error; a synchronous throw does the same. `collectPoolMetrics` sets `cubeclicker_db_pool_total`, `_idle` and `_waiting` from `totalCount`/`idleCount`/`waitingCount`, and all three to `0` when the pool is `null`. No SQL text or query parameters appear in any metric name, label or log. Evidence: `db-metrics.test.ts` and the `/metrics` integration scrape.
- **AC-17 — Shutdown events.** `installShutdownHandlers` registers `SIGTERM`/`SIGINT` once; the first signal logs `shutdown_started { signal: 'SIGTERM' }`, increments `cubeclicker_shutdown_total{signal="SIGTERM"}` by `1`, calls `app.close()` exactly once, logs `shutdown_complete`, and exits `0`; a second signal during shutdown is ignored; an `app.close()` rejection logs `shutdown_failed { signal, errorType }` and exits `1`. `server.ts` installs the handlers after `listen`. Evidence: `shutdown.test.ts` with a fake process event emitter and fake app.
- **AC-18 — Metrics contain no PII or unbounded values.** After two account logins, joins and a scrape, the rendered metrics body contains none of the test emails, usernames, passwords, session tokens, verification tokens, player ids, account ids, server ids or remote IPs. Every catalog-declared label name observed in the body is one of `reason`, `type`, `scope`, `result`, `signal` and its value belongs to the catalog allow-list; histogram `_bucket` samples additionally carry only the reserved `le` label whose bucket-bound values are exempt from the allow-list. Evidence: `app.test.ts` `not.toContain` assertions and a parser that validates catalog samples and skips/exempts `le` on `_bucket` samples.

### Frontend dev-only overlay

- **AC-19 — Flag off by default.** `isPerfOverlayEnabled(env)` is `true` only for `env.VITE_PERF_OVERLAY === 'true'`; `undefined`, `''`, `'1'`, `'TRUE'` and `'yes'` are `false`. With the flag false, `App` renders no `[data-testid="perf-overlay"]`, does not call `session.measureRtt` or `session.getPerfStats`, and therefore sends no diagnostic ping; the session's `measureRtt` itself stays flag-agnostic. Evidence: `overlay.test.ts` and `App.test.tsx` with a fake session spy.
- **AC-20 — Overlay content and refresh.** With the flag true and a fake session returning `{ frameMs: 16.7, tier: 'high', drawCalls: 42, triangles: 1000 }` and RTT `24`, the overlay renders the exact labels `Frame 16.7 ms`, `Quality high`, `Draw calls 42`, `Triangles 1000`, `WS RTT 24 ms` inside `<aside data-testid="perf-overlay" aria-live="off">`; the next 250 ms poll updates the stats, the next 1000 ms poll updates RTT, and `null` renders `WS RTT —` and `Frame —`. Evidence: `PerfOverlay.test.tsx` with fake timers.
- **AC-21 — Session frame stats.** With an injected environment whose renderer adapter has `stats()` returning `{ calls: 7, triangles: 700 }` (the adapter mirrors `renderer.info.render`), after one 16 ms frame `getPerfStats()` returns `{ frameMs: 16, tier: <current view tier>, drawCalls: 7, triangles: 700 }` — the session maps `calls` to `PerfStats.drawCalls`; a tier change is reflected on the next frame; `dispose()` makes `getPerfStats()` return `null`. Evidence: `session.test.ts`.
- **AC-22 — WebSocket RTT.** With a connected fake transport, `measureRtt()` sends exactly one `{ type: 'ping', t: <rounded env.now()> }`; a matching `{ type: 'pong', t }` resolves the elapsed milliseconds; no pong resolves `null` after exactly 2000 ms; a disconnected/no-transport session resolves `null` without sending; a transport status change away from `connected` resolves every pending call with `null`; `dispose()` clears every pending timer and resolves pending calls with `null`. The overlay flag gate is asserted at the App level in AC-19, not inside `measureRtt`. Evidence: `session.test.ts` with fake timers and `App.test.tsx` for the no-call case.
- **AC-23 — Diagnostic protocol mirrors.** The backend and frontend protocol mirrors both parse `{"type":"ping","t":123}` to `{ type: 'ping', t: 123 }` and both reject a missing, `NaN`, `Infinity`, string or boolean `t` with the existing `bad_message` result; both expose `pongMessage(t)` producing `{ type: 'pong', t }` and the exact encoded frame `{"type":"pong","t":123}`. The hub answers an accepted ping with the exact `pong` frame; a second ping within 1000 ms is dropped, increments `rate_limit_drops_total{scope="ping"}` by `1`, and sends no pong. Evidence: backend/frontend `protocol.test.ts` and `hub.test.ts`.
- **AC-24 — No production UI or bundle regression.** With `VITE_PERF_OVERLAY` unset, the built app renders no overlay and the overlay module performs no polling; `npm run build` still exits 0 within the pinned 150,000/165,000/300,000 B gzip budget. The overlay is a static small component (no new dependency, no Three.js import). `README.md` documents that the overlay is enabled with the exact command `VITE_PERF_OVERLAY=true podman compose up`, and `compose.yaml` passes `VITE_PERF_OVERLAY` to the frontend service with default `false`; the production frontend build leaves it unset. Evidence: `App.test.tsx`, `npm run build` output in the T4/T5 build log, a README exact-string grep, and `grep -F 'VITE_PERF_OVERLAY' compose.yaml`.

Every relative link resolves; `docs/features/README.md` is not edited by the builder. - No protocol version bump; the additive `ping`/`pong` diagnostic frames are used only by the dev overlay and change no game state.
- No log retention, rotation, shipping or alerting change in the repository; the existing stdout/`awslogs` path and 30-day CloudWatch retention are reused.
- No historical metric persistence, aggregation across restarts, dashboards or alert rules; metrics are per-process and reset on restart.
- No metrics authentication token; exposure relies on the network boundary (ALB does not route `/metrics`).
- No production frontend overlay and no user-facing performance setting.
- No new npm dependency and no `docs/features/README.md` edit by the builder.

## Boundaries

- ✅ Always: keep the single-process architecture; keep `/metrics` off the ALB and on the existing port 8080; use allow-listed metric labels and PII-free fields; keep request bodies, cookies, tokens and emails out of logs; keep existing auth, game, batching and protocol behavior unchanged; use injected clocks/timers and captured log streams in tests; record raw command output in build logs; update documentation in the same change as the behavior.
- ⚠️ Ask first: exposing `/metrics` publicly or adding an ALB/Terraform route; adding Prometheus/Grafana/Loki/OpenTelemetry or any external observability service; adding a new npm dependency; changing log retention or adding a log shipper; adding a metrics auth token; changing the diagnostic `ping`/`pong` shape, rate or purpose.
- 🚫 Never: log request/response bodies, cookies, authorization headers, passwords, emails, verification tokens, session tokens, SQL text, query parameters or remote IPs; add unbounded labels (user/server/player ids) or user input as a metric label; expose metrics publicly by default; weaken or delete existing tests; edit `.env*`; `git push`; edit outside the task's `files_owned`.

## Security considerations

- **Metrics exposure.** `/metrics` is served only by the backend on port 8080. The ALB routes only `/ws`, `/auth*` and `/healthz`; `/metrics` falls outside those rules and is therefore not publicly reachable by default. The endpoint has no credentials by design because it is a network-internal diagnostic surface; `METRICS_ENABLED=false` removes it entirely. Making it public is a user-owned infrastructure amendment, not a default.
- **PII and secrets.** The logger never logs bodies, headers (beyond the custom serializers), query strings, IPs, player/account ids or stack traces. Redaction covers top-level and nested cookies, authorization, api keys, set-cookie, email, password/pass, token, sessionToken and verificationToken with `[REDACTED]`. The error serializer emits type/code only. Metrics labels are allow-listed enums (plus the renderer-reserved `le` bucket bound), so user-controlled strings cannot become series.
- **Cardinality/DoS.** The catalog is fixed at 30 metric names and a bounded label value set; an unknown label or value throws rather than creating a series. The `/metrics` handler renders a fixed-size body and performs only three pool-gauge reads; there is no user input in the path.
- **Diagnostic ping.** The `ping` frame carries one finite number and the server echoes it; a 1 Hz per-connection limit bounds replies, and dropped pings only increment a counter. It cannot alter membership, economy, boards or broadcasts.
- **Database instrumentation.** The wrapper records duration and outcome only; it never captures SQL text, parameters or row data. Pool gauges are numeric.
- **Shutdown.** Signals are handled once; `app.close()` runs the existing hub/pool teardown. No secret is read or logged during shutdown.
- **Persistence integrity.** No schema, repository write, auth rule or persisted value changes.

## Real-time / multi-client impact

**Observability only.** No game-state authority, server rule, protocol game message, reconnect/grace behavior or cross-client value changes. All metrics are per-process aggregates: `servers_active`/`members_active` are counts of the in-memory registry; no per-server or per-user series is created, so no shared value crosses clients. The connection-lifecycle counters cover open/close/heartbeat termination; reconnection and multi-client behavior are unchanged. Every account and guest connection is counted without an identity label, so the identity-versus-no-accounts model is not reopened; there is no identity conflict. The diagnostic `ping`/`pong` pair is connection-local and carries no identity, room or world data. The server remains the only authority for shared state.

## Containerization impact

No new service, image, deployable, port, host mapping, health signal or compose service. `/metrics` is an additional HTTP route on the existing backend port 8080, alongside `GET /healthz` and `GET /ws`; the ALB is unchanged and does not route it. `compose.yaml` gains exactly three environment pass-throughs with safe defaults — backend `LOG_LEVEL: "${LOG_LEVEL:-debug}"` and `METRICS_ENABLED: "${METRICS_ENABLED:-true}"`, frontend `VITE_PERF_OVERLAY: "${VITE_PERF_OVERLAY:-false}"` — so `LOG_LEVEL=warn podman compose up`, `METRICS_ENABLED=false podman compose up` and `VITE_PERF_OVERLAY=true podman compose up` work locally; `compose.smoke.yaml`, `src/backend/Dockerfile` and `src/frontend/Dockerfile` are unchanged, and `podman compose up` remains the single local command. `curl http://localhost:8080/metrics` reaches the route through the existing loopback port mapping. The existing image `HEALTHCHECK` stays on `/healthz`. Logging remains stdout JSON captured by the existing container runtime; deployment already uses the `awslogs` driver and a 30-day CloudWatch log group, so no retention or shipper configuration is added. `LOG_LEVEL`, `METRICS_ENABLED` and `VITE_PERF_OVERLAY` are environment-based configuration with safe defaults; no settled convention in `docs/architecture/containerization.md` is reopened.

## Risks and dependencies

- **Redaction gap** → custom serializers exclude bodies/headers, redaction paths cover accidental fields, and an integration test asserts no secret value appears; code review checks every new log call.
- **Metric cardinality bug** → the registry rejects unknown labels/values; the catalog is the single source; a scrape test asserts only bounded labels.
- **Metrics endpoint accidentally public** → no Terraform/ALB change; verify command greps `infra/terraform` for `/metrics`; docs state the rule; `METRICS_ENABLED` is a kill switch.
- **Observability overhead in hot paths** → counters/gauges are in-memory map updates; no per-recipient labels; encode-once path unchanged; no sampling or JSON serialization per frame.
- **DB wrapper changes error behavior** → the wrapper rethrows the original error and preserves promise identity; tests cover resolve, reject and sync throw.
- **Shutdown hangs on open WebSockets** → `app.close()` runs the existing `@fastify/websocket` close path and hub teardown; the platform stop timeout bounds it. No new timeout is added; if the plugin does not close clients, that is a separate hardening follow-up.
- **Overlay in production bundle** → the component is rendered only when the build-time flag is exactly `'true'`; the bundle budget remains the gate; the overlay imports no Three.js.
- **Ping abuse** → 1 Hz per connection; bounded pong; no identity/state; drop counter.
- **Log volume/cost** → production enables one Fastify request/response pair per HTTP request at `info` (including the 10-second `/healthz` probe and `/metrics` scrapes) plus one lifecycle line per WebSocket connection; this is low-volume and bounded, the 30-day CloudWatch retention is unchanged, and no sampling/shipping change is made. If volume becomes material, the follow-up is an `info`-to-`warn` level or health-route log suppression, not a new stack.
- **Dependencies** — Fastify v5's built-in Pino (already installed transitively via Fastify), existing `pg` pool, existing React/Vite; no new package.

## Open questions

**Approval checkpoint.** The queue approval "Proceed with all of them, one by one" covers the existence of this feature but not the three material choices below. Recommended defaults are safe and reversible; the orchestrator should present them in `awaiting_approval` and record the user's confirmation in `status.md` before building.

1. **Q-1 — Metrics format.** Recommended **Prometheus text** (`text/plain; version=0.0.4`) because it is the de-facto scrape format and needs no dependency; alternative JSON would need a custom consumer.
2. **Q-2 — Exposure.** Recommended **internal-only on the existing port**, no ALB/Terraform route and no public access; `METRICS_ENABLED` defaults to `true` and can remove the route. Public scraping is a future user-owned infrastructure decision.
3. **Q-3 — Frontend overlay and WS RTT.** Recommended **include the dev-only overlay** behind `VITE_PERF_OVERLAY=true`, with RTT measured by additive `ping`/`pong` diagnostic frames limited to 1/s per connection. Alternatives: omit the overlay, or show frame/tier/renderer stats without RTT.

The remaining choices are builder defaults and do not need a separate user decision: Prometheus histogram buckets as listed and the renderer-reserved `le` label; log levels production `info` / development `debug` / test off with `LOG_LEVEL` override; error serializer `{type, code?}` only; CloudWatch `awslogs` + 30-day retention reused; compose pass-throughs for `LOG_LEVEL`, `METRICS_ENABLED` and `VITE_PERF_OVERLAY`; `docs/architecture/observability.md` as the documentation home; HTTP auth rate-limit drops included via the optional `onDenied` callback.

- **Q-1 — Metrics format.** Recommended **Prometheus text**. Alternatives: JSON (easier ad-hoc parsing, no ecosystem support) or both (two formats, more surface).
- **Q-2 — Exposure.** Recommended **internal only, no public route**. Alternatives: public `/metrics` behind ALB auth (new infra, user-owned) or a separate metrics port (new port, violates the no-new-port default).
- **Q-3 — Overlay/RTT.** Recommended **include dev-only overlay with ping/pong RTT**. Alternatives: overlay without RTT (no protocol addition) or no overlay (smallest scope; loses the requested dev signal).
- **Q-4 — Metric retention.** Recommended **per-process only**, reset on restart; no historical store. A future Prometheus/Grafana stack is out of scope.
- **Q-5 — Log retention/access.** Recommended **reuse stdout + existing `awslogs` with 30-day retention**; locally `podman compose logs`. No new shipper, file rotation or repository retention config.
- **Q-6 — HTTP limiter drops.** Recommended **include** `scope="http"` via the optional `onDenied` callback; the key is discarded, never logged or labeled.
- **Q-7 — Error details.** Recommended **`{type, code?}` only**, never message/stack, because messages can contain user input. A future debug-only switch would be a separate decision.
- **Q-8 — Documentation home.** Recommended **new `docs/architecture/observability.md`** plus a README `## Operations` subsection and one deployment routing sentence; no existing architecture document owns runtime observability.

## Assumptions

- One backend process; counters/gauges are in-memory and reset on restart. There is no aggregation across restarts or instances.
- Fastify v5's built-in Pino is available without adding a direct dependency; the logger is configured through Fastify's `logger` option.
- `NODE_ENV` is `production` in the deployed backend and `development` in the compose dev container (both already true in `infra/terraform/modules/ecs/main.tf` and `src/backend/Dockerfile`).
- The ALB routing table in `docs/architecture/deployment.md` is accurate: only `/ws`, `/auth*` and `/healthz` reach the backend, so `/metrics` is not public.
- `app.close()` closes WebSocket clients through the existing `@fastify/websocket` close path; the hub/pool `onClose` hooks then run. The platform's stop timeout bounds a stuck close.
- The real `WebGLRenderer.info` object is available and `autoReset` can be disabled/reset by the adapter without changing rendered output.
- `VITE_PERF_OVERLAY` is a build-time Vite variable: enabling it requires a dev/build restart, not a runtime toggle. `compose.yaml` passes `LOG_LEVEL` (default `debug`), `METRICS_ENABLED` (default `true`) and `VITE_PERF_OVERLAY` (default `false`) to the existing services.
- Metrics labels are server-controlled; the catalog allow-list is the only source of catalog label values, and `le` is renderer-generated.
- Production log volume is bounded by request traffic plus one lifecycle line per WebSocket connection; the 30-day CloudWatch retention and `awslogs` driver are unchanged, and no sampling/shipper is added.
