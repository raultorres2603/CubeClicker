# Spec — Online & Real-Time Workflow Alignment

## Summary

Reflect CubeClicker's online, real-time nature across project docs and the AI agent workflow, so every future feature request is handled with it baked in. CubeClicker is a shared, multi-client game: the backend must be WebSocket-compatible, the frontend must connect to it over WebSocket, and clients are expected to see each other's live activity (live stats, other users' clicks, connected users). Project-level statements land in `AGENTS.md` and `docs/architecture/stack.md`; the stack stays NOT DECIDED and WebSocket is captured as a protocol/architecture hard constraint only. Candidate real-time features are captured as a provisional "direction, not commitments" backlog in a new `docs/product/realtime-backlog.md`, linked from a minimally-edited `docs/product/vision.md`. Each of the four agent instruction files gains proportionate role rules — the orchestrator additionally carries the framework autonomy rule from the 2026-10-16 directive — and the relevant skill files (web-implementation SKILL + engineering principles, spec-authoring checklist, spec-review checklist, code-review quality/security/testing checklists) gain actionable real-time rules. This is a documentation/config-content feature: no application code, no dependencies, no scaffolding. It carries a sanctioned permission bootstrap (Q-1, resolved in r3 per the user directive of 2026-10-16 — quoted in § Open questions): task T0 adds five targeted `edit` allow entries (`AGENTS.md`, `docs/architecture/**`, `docs/product/**`, `.opencode/agents/*.md`, `.opencode/skills/**`) to `.opencode/agents/builder.md` via the builder's existing shell capability (the `edit` tool cannot open `.opencode/**` until T0 lands); controls: T0 is the only permission change anywhere (AC-24), reviewer diff inspection, git-revertible, no push (see § Security considerations).

## Scope

### In scope

Fifteen target files, each with a pinned content contract in `plan.md` § Pinned content contracts:

- **Project-level (2):** `AGENTS.md` (intro nature statement + § Stack WebSocket constraint); `docs/architecture/stack.md` (hard-constraint section; NOT DECIDED retained).
- **Product direction (2):** `docs/product/realtime-backlog.md` (new: provisional backlog, three named candidates + clearly-marked unconfirmed proposals + open tensions); `docs/product/vision.md` (One-liner gains "online, real-time"; exactly one added link line to the backlog).
- **Agent instruction files (4):** `.opencode/agents/orchestrator.md` (two rules: real-time awareness + framework autonomy per the 2026-10-16 directive), `.opencode/agents/planner.md`, `.opencode/agents/builder.md` (real-time rule; also the T0 bootstrap file — next bullet), `.opencode/agents/reviewer.md` (one targeted rule each unless noted).
- **Skill files (7):** `.opencode/skills/web-implementation/SKILL.md` and `references/engineering-principles.md` (real-time engineering rules); `.opencode/skills/spec-authoring/references/spec-checklist.md` and `.opencode/skills/spec-review/SKILL.md` (spec-gate real-time checks); `.opencode/skills/code-review/checklists/quality.md`, `security.md`, `testing.md` (code-gate real-time checks).

Plus the sanctioned permission bootstrap (**T0**, tasks.md): five `edit` allow entries (`AGENTS.md`, `docs/architecture/**`, `docs/product/**`, `.opencode/agents/*.md`, `.opencode/skills/**`) added to `.opencode/agents/builder.md` via shell — user-authorized by the 2026-10-16 directive (Q-1); the only permission change anywhere (AC-24).

Plus per-task build logs (`build-log-T0.md` … `-T6.md`) and the final verification log inside `docs/features/online-realtime-workflow/`.

### Explicitly out of scope

- Any application code, tests, scaffolding, dependency, or tooling change (stack NOT DECIDED).
- Any framework/library/runtime/package/product choice or named technology other than the WebSocket protocol (no library speculation anywhere).
- Implementation planning for real-time features: no architectures, message schemas, APIs, or designs — the backlog is direction only.
- Changes to any `permissions:` block or allow/deny entry in `.opencode/agents/*.md` by any change other than T0's five-entry bootstrap (the only sanctioned permission change — AC-24).
- Edits to any file outside the 15 targets and this feature directory.
- Resolving the vision "no accounts required" vs. presence/attribution conflict: flagged as an open question only (Q-6).
- Retrofitting unrelated doc prose or other feature directories (e.g., `project-glossary`).
- Scoping any new product feature.

## User stories

- As the project owner, I want the game's online/real-time nature reflected in project docs and agent instructions so future feature requests don't require relearning it.
- As the planner, I want a visible WebSocket architecture constraint and explicit real-time considerations so specs for shared/cross-client features address connection lifecycle, reconnection, multi-client behavior, and server authority by default.
- As the builder, I want real-time engineering rules so implementations don't trust client-reported state and don't leak connections.
- As the reviewer, I want real-time checks in the spec/code checklists so live/shared behavior is verified at both gates.
- As the user, I want acknowledged real-time feature candidates captured as provisional direction so they are not lost or mistaken for commitments.

## Security considerations

- Documentation/config-content change: no runtime, no user-controlled data paths, no persistence — no new attack surface in the product.
- **Permission-sensitive targets:** the feature edits `.opencode/**` and `AGENTS.md` (the workflow's own configuration). Initially no pipeline agent can edit the 15 targets **via the `edit` tool** (all four agents deny `edit: *` and the targets are outside every edit allowlist), while non-edit shell write paths (`tee`, `sed -i`, redirection) are outside the permit model — the builder's `shell: *` allow — and remain instruction-enforced. Q-1 (resolved, r3) closes the tool gap via T0: the builder adds five targeted `edit` allow entries using its existing shell capability. Effective controls: T0 is the only sanctioned permission change (AC-24); the reviewer inspects T0's diff at the code gate and every task commit is inspected against the pinned contracts; the bootstrap is user-authorized (2026-10-16 directive), git-revertible, and never pushed; the user can re-narrow permissions after acceptance.
- **Self-edit hazard:** the builder already has shell write access to repository files today (not created by this feature); T0 deliberately extends its `edit` access to the 15 targets' paths, including `.opencode/agents/*.md` — the glob covers all four agent files (orchestrator, planner, builder, reviewer), not only the builder's own permission block and instructions. This is an accepted, bounded risk under the user directive of 2026-10-16 (mechanical bootstrap operations are pipeline-applied): T0 is the only sanctioned permission change (AC-24), its scope is exactly the five pinned entries, its diff is reviewed at the code gate, and it is git-revertible with no push. **Temporal footprint:** the widened entries persist beyond this feature — unless the user re-narrows after acceptance, the builder keeps `edit` access to `AGENTS.md`, all four agent files, and all skills for future work. Flagged as a risk in `plan.md`.
- No secrets, tokens, or keys are introduced; no `.env*` edits; no dependency additions (supply chain unchanged).
- The `vision.md` edit is additive/pinned with a verbatim baseline so the reviewer can prove non-destructiveness.
