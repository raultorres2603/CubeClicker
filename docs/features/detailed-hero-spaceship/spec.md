# Spec — Detailed hero spaceship

## Summary

Enhance the right-side backdrop spaceship (`hero-ship` in `render/cosmic-backdrop.ts`) from the accepted simple seven-mesh primitive into a significantly more detailed procedural retro-futuristic craft that follows the user's reference description: a cobalt/royal-blue layered hull with light gray underside plates, dark navy trim, vivid orange accent stripes and wingtips, a dark teal framed cockpit canopy, swept delta wings with gray leading edges, small tail fins, two ribbed engine nacelles with bright orange exhaust and white-hot cores, and visible panel seams, greebles, vents and antennae. The model is built by a new testable factory, `render/spaceship-model.ts`, and mounted inside the existing camera-anchored `hero-ship` group so the accepted T16 screen composition (right of the cube, above the bottom-right upgrades panel, behind the cube) is preserved from every server slot. Everything is procedural three.js: no new dependency, loader, URL, texture, font or external asset. The feature is client-local decoration: no gameplay, engine, session, protocol, server-authority, persistence, real-time or container behavior changes. The spaceship **cursor** (`render/spaceship.ts`, customization, follow, shots, ignitions) is explicitly out of scope in this revision and is recorded as open question Q-2. The planner cannot see the attached reference image; the written description supplied with the brief is the source of truth, and Q-1 is the approval-time fidelity checkpoint.

**Scope decision.** The ship in scope is the right-side backdrop `hero-ship` (the prominent ship in the reference image). The spaceship cursor is explicitly out of scope and is listed as approval-time open question Q-2; no cursor file, constant, appearance mapping, ignition, shot or test is changed by this feature.

**Fidelity trade-off (procedural vs. external model).** The default is fully procedural three.js: layered primitives, an extruded delta wing, panel seams, greebles, emissive accents and additive exhaust can all be built and tested in code, with no dependency, loader, asset or licensing surface. Procedural work cannot match a sculpted/baked asset's organic curvature, normal/roughness maps, high-frequency rivets or painterly weathering; a GLTF/asset pipeline would be materially closer to a painted reference but needs an external asset, a loader, licensing review, a bundle-budget decision and a new asset workflow. It is **not** added silently: Q-1 records it as the fidelity checkpoint, and choosing it requires a spec revision with explicit approval.

## User stories

- As a player, the spaceship on the right reads as a detailed hero craft — layered blue/gray hull, canopy, swept wings, tail fins, twin engines with glowing exhaust and orange accents — instead of a simple toy primitive.
- As a player, the ship keeps its accepted right-side composition: it stays right of the cube and above the upgrades panel from every server slot and never covers gameplay.
- As a player who prefers reduced motion, the ship and its engine glow are static: no new idle animation, flicker or drift is introduced, and the existing bob freezes.
- As a maintainer, the detailed model lives in one testable factory with named parts, a pinned mesh/triangle budget and one disposal seam, while the cursor ship, gameplay, real-time paths and containers are untouched.
