# Spec — AWS Deploy Pipeline (Terraform infrastructure + GitHub Actions CI/CD + framework proof-of-working)

## Summary

Deploy CubeClicker from its existing container images (backend: Node.js 24 + Fastify with the `/ws` WebSocket endpoint and `GET /healthz`; frontend: static SPA served by the `prod` nginx image) to AWS, driven by a GitHub Actions pipeline, with the infrastructure defined in Terraform (HashiCorp, pinned — provider portability is an aspiration of the module layout, not a claim in these artifacts; the AWS + Terraform choice is DECIDED by this feature per the user's 2026-10-31 request). The pipeline must verify everything before deploying: every deploy is preceded by `npm ci`, lint, typecheck, unit/integration tests, the coverage gate, build, the containerized smoke tests (with Mailpit pre-started — the pinned smoke gate is structurally green only with `compose up -d mailpit` before `run --rm smoke`, verified 12/12 PASS by the r1 reviewer), and infrastructure verification (`terraform fmt -check`, `terraform validate` via containerized Podman wrappers — neither binary is installed on the host; `terraform plan` runs with real OIDC credentials in the deploy path immediately before apply; the no-credentials CI path uses fmt+validate and is stated as such rather than silently claiming a plan). The third deliverable strengthens the agentic framework so a feature is only "green to go" after a mandatory post-implementation proof-of-working loop — the builder runs the feature-appropriate verification suite (lint, typecheck, tests, `npm run coverage`, smoke or config-level equivalents) and records raw evidence in build logs, the reviewer independently reproduces it, and only then does the existing `code_review → accepted` gate pass — with no new state-machine state and no new user checkpoints for verification (autonomy per the 2026-10-16 directive quoted in `docs/features/online-realtime-workflow/spec.md` Q-1). The single deploy environment is `production` (staging is deferred to a documented additive recipe). AWS account ID, domain names, region confirmation, and remote-state assets are unknown and carried as explicit open questions with proposed defaults (region `us-east-1`; GitHub OIDC identity provider; one shared S3 state bucket with S3-native locking and per-environment state keys; `TF_STATE_BUCKET`/role-ARN repository variables).

### Raw request (verbatim, scope boundary)

> "I want you to create the different infraestructure we will need to deploy, for example, on AWS.
> We will deploy with GitHub Actions.

> Also, update our AI agentic framework we built in order to, always, after an implementation, we need to prove is working, by validating everything, being able to test and all being green, etc... So, a feature is green to go when everything works as expected.
> Does it make sense?"

## Scope

### In scope

Three coordinated deliverable clusters:

1. **Terraform infrastructure for AWS** (`infra/terraform/`): a root module composed of per-concern modules — networking (VPC, subnets, security groups), edge (internet-facing ALB with two target groups and WebSocket-upgrade passthrough for `/ws`; `idle_timeout = 90`, strictly greater than 2× the backend's 30 s heartbeat; ALB-assertable health checks: backend TG `path /healthz` matcher 200, frontend TG `path /` matcher 200), ECR (two repositories for the committed `src/backend/Dockerfile` / `src/frontend/Dockerfile` images), data (managed PostgreSQL — RDS default — reachable only from the backend containers; `use_external_database_url` toggle for an existing DB), ECS (Fargate cluster + one service per image with environment/secret injection), and CI/CD IAM (GitHub OIDC identity provider + least-privilege plan/deploy roles, deploy trust constrained to `environment:production`), plus a one-time `bootstrap/` root creating ONE shared S3 remote-state bucket (S3-native locking via `use_lockfile = true`, no DynamoDB; per-environment state keys: `env/production/terraform.tfstate` pinned literal in `backend.tf`), environment layering via `envs/production.tfvars` (`-var-file` in the deploy job), and containerized verification tooling (no host installs).
2. **GitHub Actions CI/CD** (`.github/workflows/`): `ci.yml` — the reusable verification gates (workflow-level: `contents: read`) running on every PR: `verify-app` (`npm ci` → `npm run lint` → `npm run typecheck` → `npm test` → `npm run coverage` → `npm run build`), `smoke-e2e` (`docker compose -f compose.yaml -f compose.smoke.yaml up -d mailpit` **before** `docker compose -f compose.yaml -f compose.smoke.yaml run --rm smoke` — the r1 reviewer proved the one-shot run alone fails 9/12; with Mailpit pre-started it passes 12/12), `verify-infra` (`terraform fmt -check -recursive`, `terraform init -backend=false`, `terraform validate` in the containerized wrapper — no AWS credentials needed). `deploy.yml` — on push to `main`, calls `ci.yml` via `workflow_call` (single source of truth for the gates), then: build + push both images to ECR tagged with the commit SHA (the frontend build bakes `VITE_WS_URL` from the `PUBLIC_WS_URL` repository variable via the two-line `ARG VITE_WS_URL` + `ENV VITE_WS_URL` amendment to `src/frontend/Dockerfile` (F6 route (a)) — the `ENV` bridge is required because a bare Docker `ARG` is not exported into the build container's process env, and Vite resolves the value via `process.env.VITE_WS_URL`), OIDC role assumption (`aws-actions/configure-aws-credentials`, `id-token: write` on the deploy jobs only, no long-lived keys), `terraform init -backend-config bucket=${{ vars.TF_STATE_BUCKET }} -backend-config region=${{ vars.AWS_REGION }}` + `terraform plan -var-file=envs/production.tfvars -out=tfplan` + `terraform apply` assuming the deploy role, then task-definition render + service deploy for backend and frontend with `wait-for-service-stability`. `actionlint` (containerized wrapper) green on both workflows; hygiene: full-commit-SHA pinning of third-party actions (with version comments), a `concurrency` group for the production environment, and `dependabot.yml` tracking the `github-actions` ecosystem.
3. **Agentic framework proof-of-working** (`AGENTS.md`, `.opencode/agents/{orchestrator,builder,reviewer}.md`, `.opencode/skills/orchestration-playbook/SKILL.md`, `.opencode/skills/web-implementation/SKILL.md`, `.opencode/skills/code-review/SKILL.md`): strengthen the existing `building → code_review` and `code_review → accepted` gates so the recorded raw verification evidence (including `npm run coverage` and any feature-appropriate proof — e.g. the smoke recipe for cross-service behavior, containerized `terraform fmt/validate/plan` and `actionlint` for infra/pipeline configs) is the justification for advancing, the reviewer reproduces the evidence itself, and the documentation pass gate (per `docs/architecture/documentation.md`) stays as-is. No new state; no changed verdict/report formats.

Plus the conditional builder-permission bootstrap T0 (Q-9 route (a), modeled on the `online-realtime-workflow` T0 precedent), per-task build logs (`build-log-T0.md` … `-T-final.md`) inside `docs/features/aws-deploy-pipeline/`, and the exactly-one-file `src/**` amendment (see Non-goals) — all other `src/**`, `tests/e2e/**`, `compose*` content is consumed, not modified.

### Explicitly out of scope

- Any change to application code or behavior: the only `src/**` exception this feature owns is the pinned two-line `ARG VITE_WS_URL` + `ENV VITE_WS_URL` build-arg plumb in `src/frontend/Dockerfile`'s build stage (F6 route (a); sets a default, changes no behavior — local builds produce the same image). `src/frontend/src/**`, `src/backend/**`, `tests/e2e/**`, `compose.yaml`, `compose.smoke.yaml`, `src/backend/Dockerfile` are read-only (the images remain the deployable artifacts per `docs/architecture/containerization.md`; the compose-file Mailpit one-shot fix is pinned at the workflow-step level and its upstream `npm run smoke` defect is recorded as backlog — see § Backlog notes).
- Running `terraform apply` against a real AWS account during this feature (verification boundary — see § Testing strategy and Q-8; requires user-owned account assets).
- Provider porting beyond AWS defaults: no multi-provider abstractions, no alternative-cloud modules. Provider portability is the declared aspiration of the module layout only (Terraform + AWS are the decided tools — plan D-1); a cloud port would swap resources in later features.
- DNS/Route53/custom domains/ACM certificate purchases, CloudFront in front of the ALB, multi-region deployments, cross-account bootstrapping.
- Second deploy environment: `staging` is deliberately deferred (F5 resolution — single `production` default; the additive staging recipe is documented, not shipped). No staging workflow jobs, roles, or tfvars are created by this feature.
- Changes to the local development path: `podman compose up`, hot reload, `npm run dev`, `npm run smoke` (the one-shot defect is backlog, not changed here), the existing commands.
- New state-machine states, new user checkpoints, or rewrites of agent verdict/report formats (framework strengthening only).
- Production SMTP provisioning (SES or external) — app auth email flow in production is an open question (Q-6); the pipeline provisions configuration slots, not mail identities.
- GitHub organization/settings clicks that only the user can perform (repository variables, environment protection rules, OIDC role ARN values created in AWS) — documented as an operational handoff checklist, not automated.

## User stories

- As the project owner, I want CubeClicker deployable to AWS from the images we already build, so the containerized delivery path extends to the cloud.

## Security considerations

- **Keyless CI/CD is the core security property.** All AWS authentication from GitHub Actions uses OIDC via `aws-actions/configure-aws-credentials`: the workflow's `id-token: write` exchange produces short-lived credentials scoped to a specific role. No long-lived keys exist. Trust conditions constrain the roles to the repository and (for deploy) the `production` environment; the audit (AC-15) is `git grep`-verifiable over tracked files. Plan role = read-only; deploy role = apply-scoped. The deploy role must create downstream IAM entities (ECS task roles/policies) — least-privilege is therefore bounded by explicit name prefixes pinned in plan.md, acknowledged as the risk-mitigated trade-off of using Terraform-managed execution IAM.
- **Agentic permission surface is regulated** (F3). The builder's `edit` allowlist covers neither `infra/**` nor `.github/**`; leaving that gap unregulated repeats the r1-era unpermitted-writes problem that `online-realtime-workflow` solved with its sanctioned T0. Route (a) mirrors that precedent exactly (two entries, one commit, reviewer diff inspection, AC-22 owner check); route (b) keeps the permit model intact and pins the shell-authoring controls instead. Either way the code gate verifies the route was followed and flags any `permissions:` block drift (AC-22).
- **Secrets and state.** No secret values are authored in this repository ever; database credentials are created/rotated by an AWS-managed secret store and injected into ECS via the task-definition `secrets` mechanism; SMTP credentials are user-supplied SSM SecureStrings (values set out-of-band, names pinned in the manifest). Terraform state can contain sensitive values: the state bucket is encrypted, versioned, non-public, and access is restricted to the two CI/CD roles; sensitive Terraform variables/outputs are marked `sensitive`; no state, plan, or `.terraform/` artifacts are ever committed (AC-3, AC-15); the committed provider lockfile is build reproducibility, not state.
- **Supply chain.** Every third-party action is pinned to a full commit SHA with a version comment (AC-11) and Dependabot keeps pins current (AC-14); the two verification-tool container images are pinned to stable patch/minor tags (D-13) with pull-failure → `blocked` protocol; workflow permissions default to `contents: read` with per-job elevation only; `pull_request_target` is not used; no untrusted-checkout of fork code in any workflow.
- **No `.env*` interaction.** Runtime configuration travels exclusively through environment variables/secrets in the ECS task definitions (per `docs/architecture/containerization.md`); no agent writes `.env*` files; the frontend WS target bakes at image-build time from the `PUBLIC_WS_URL` repo variable (no repository secret involved).
- **Real-time surface.** The deployed edge must preserve WebSocket upgrades (ALB target-group handling with no request-policy stripping and `idle_timeout = 90`, strictly above 2× the 30 s heartbeat); the frontend `VITE_WS_URL` production bake is resolved by the pinned Dockerfile `ARG VITE_WS_URL` + `ENV VITE_WS_URL` bridge amendment (F6/F17 route (a)) rather than left to a broken default; nothing else changes the real-time contract.
- **Third-party surface is minimized.** Actions are restricted to official scopes (`actions/*`, `aws-actions/*`, `hashicorp/*`) plus the pinned `actionlint` wrapper image (D-7), all SHA-pinned; no unvalidated third-party action is introduced.
