# Spec Review — r1

## Summary

❌ changes requested — 4 MAJOR, 5 MINOR, 2 INFO. The performance design is mostly sound: encode-once fan-out, the O(1) registry index/visitor with the defensive `servers()` snapshot, the 40 ms removal batcher with legacy single-id shape and boundary flushes, the 4 Hz absolute-total economy coalescer, and the unchanged DB writes cover the 28 ACs in principle. The four MAJOR gaps are: (1) there is **no approval checkpoint** for the user-visible Q-1/Q-2/Q-3/Q-4/Q-5 defaults, and the plan explicitly says “none blocks the build”; (2) credit results can resolve **out of order**, so the plan’s “latest observed” absolute economy frame can regress below the repository’s final totals — the plan’s concurrency note is not sufficient; (3) `hub.close()`/`discard()` does not prevent a late credit callback or a late client frame from creating a new timer or sending after shutdown, so AC-15’s no-sends/no-callbacks claim is not guaranteed; and (4) AC-18 promises a frontend end-to-end integration proof, but the T4 tasks only list separate transport/reducer/session/world tests. The MINORs are the wrong audit line for the roster `servers()` call, incomplete backend builder validation, an AC-22 “no-op” that still encodes, benchmark command/counter precision, and an unspecified smoke-burst id/order conflict.

## Notes / backlog (non-blocking)

- **Source claims verified.** `src/backend/src/game/hub.ts:333-338` is the per-recipient `send`/encode, `:351-363` is the per-member `broadcast`, `:371-379` is the scanning `locationOf`, `:412-413` is the `rosterFor` snapshot call, `:787-800` is the per-connection economy broadcast, `:866-890` is the completion credit/grant/broadcast block, and `:621-638` is the join-query block; `src/backend/src/game/servers.ts:274-276` is the defensive snapshot. The backend/frontend protocol mirrors and the reducer/session/world switches exist at the cited files. The only audit citation error is the roster `449-452` line, which is `sendSync`; the actual `rosterFor` call is `412-413` (F5).
- **The design is implementable.** The hub’s current `send`/`broadcast`/`broadcastEconomyUpdate` loops are exactly the per-recipient encode/deep-copy targets cited; `servers()` at `servers.ts:274-276` returns defensive copies; the frontend reducer/session/world switches are the correct consumption points. The new registry index/visitor, batcher, coalescer and fan-out helpers fit the existing seams.
- **The 40 ms/4 Hz targets are plausible but need the approval checkpoint.** The 30/s rate limit bounds a 40 ms window to 30 ids; a 30-id frame is well below 1024 bytes; four 25-click bursts should produce four frames (≤8) and ~13 economy frames over 3.3 s (≤16). The benchmark’s `maxRemovalFrameBytes` test uses 30 ids; the smoke’s single-click legacy shape preserves the existing check.
- **Boundary flushing is the right ordering mechanism.** The plan flushes before completion, join, rejoin and final removal; a global flush also flushes other servers’ pending groups, which only delivers earlier and does not change per-server order. Rotation correctly does not flush. The missing guarantee is shutdown (F3), not the listed boundaries.
- **The separate `economy-write-behind` feature is not present in the tree and is explicitly out of scope.** AC-23 and the non-goals keep the one-credit-per-click and completion write call sites; the coalescer must only change broadcast timing. The benchmark must keep `dbCreditsPer100Clicks = 100`.
- **The benchmark baseline for registry copies is static by design.** The baseline script cannot inject `HubDeps.registry` before T3; the spec/T2 log labels the two-copies-per-click baseline static rather than measured. It should not be reported as a measured counter.
