# Spec — Deployment Brevo Environment Placeholders (GitHub Environment → Render)

## Summary

Local development keeps delivering through Mailpit with no configuration; the deployed environments must deliver through **Brevo SMTP**. The GitHub `development` Environment today carries four SMTP variables (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_FROM`) and the `SMTP_PASS` secret; `production` carries none; the values the backend actually uses live in the Render dashboard, and the deploy workflow never reads the GitHub names. The repository owner's request is to make the deployment environments carry the Brevo configuration as GitHub environment variables/secrets, with clearly marked placeholders that the owner replaces later ("Add the placeholders on GitHub, I'll update with the values").

This feature (a) pins the deployment Brevo catalog — the seven accepted SMTP names plus two Render-wiring names (`RENDER_SERVICE_ID` variable, `RENDER_API_KEY` secret) — with the exact literal or placeholder for every value the owner must supply: all nine for `production`, and only the missing names for `development`, where the owner directed T5 to **preserve the existing values and add only what is missing** (2026-11-22) instead of overwriting them; (b) makes the GitHub Environment the **source of truth** by adding a validated, placeholder-guarded sync step to `.github/workflows/deploy.yml` that validates all nine names but writes **only the seven SMTP values** to the environment's Render service through the Render API before the deploy hook, so filling the GitHub values is sufficient for a deployment to use Brevo; (c) refuses to deploy while any value is missing or still a placeholder, so `CHANGEME` can never reach Render; and (d) documents the operator runbook (`gh` commands plus the UI for entering values), the verification path, the rollback path, and the consequence that Render-dashboard edits to those seven names are overwritten on the next deploy.

The two wiring names are pipeline-only: `RENDER_SERVICE_ID` is the URL path coordinate and `RENDER_API_KEY` is the bearer credential. Neither is ever written into the Render service's environment; `RENDER_API_KEY` lives only in the GitHub Environment secret and the runner's process environment.

The owner has approved the **auto-sync GitHub → Render** architecture and the **strict-fail** placeholder guard, and confirmed that `SMTP_USER`/`SMTP_PASS` remain GitHub Environment secrets (Q-4 and Q-5 are closed). On 2026-11-22 the owner also decided that T5 **preserves the existing `development` values and adds only the missing names**, superseding the earlier plan to overwrite them with placeholders; `production` remains all-placeholder.

## Context and current state

- **Local is already right.** `compose.yaml` passes `SMTP_HOST=mailpit`, `SMTP_PORT=1025`, empty `SMTP_USER`/`SMTP_PASS`, `SMTP_FROM=no-reply@cubeclicker.local`, `SMTP_SECURE=false` and `SMTP_CONNECTION_TIMEOUT_MS=10000`; `compose.smoke.yaml` pins the smoke backend to Mailpit. This feature changes none of it.
- **The accepted SMTP contract** (`docs/features/brevo-smtp-email-delivery/spec.md`, `README.md` § Email, `docs/architecture/deployment.md` § Secrets and variables) is unchanged: same names, same semantics (587/STARTTLS pinned, 465 implicit TLS allowed, `SMTP_USER` = Brevo SMTP login, `SMTP_PASS` = Brevo SMTP key — **not** the REST API key, `SMTP_FROM` = a Brevo-verified sender, `SMTP_CONNECTION_TIMEOUT_MS` integer 1000–120000). This feature adds no SMTP name and changes no parsing rule.
- **The catalog is documented but inert.** `docs/architecture/deployment.md` line 47 lists `SMTP_USER` among the `development` **variables** and line 50 says every SMTP value is "dashboard- or shell-supplied" (and "No new secret name is introduced"); line 51 lists `SMTP_*` among the dashboard-set `sync: false` names. (Line 52's "the workflow no longer derives or stages them" refers to `CORS_ORIGIN`/`ALLOWED_ORIGIN`/`APP_BASE_URL` and stays true.) `docs/architecture/vercel-render-neon.md` line 64 lists `SMTP_USER` among the variables and line 67 calls the SMTP names "runtime-parity catalog entries … even though only the Render service consumes them"; line 176 calls the Render SMTP values "dashboard-supplied". `README.md` line 99 says "set them on the Render service" and line 282 says the Render service "reads … from the dashboard". Those statements are the current truth and the reason the owner's request is not yet satisfied.
- **`render.yaml`** already declares all seven SMTP names with `sync: false` and no `value`; it is a correct, value-free description of the service and stays byte-identical here (the constraint "do not change `render.yaml` runtime values to secrets" is respected by not touching it).
- **The deploy job** (`.github/workflows/deploy.yml`) runs one job in the environment selected by the event and in fixed order: reject non-push CI → verify CI for a dispatch → checkout/setup/install → Neon migration (`DIRECT_DATABASE_URL`) → `POST $RENDER_DEPLOY_HOOK_URL` → 45 s wait → `/healthz` poll (180 s) → Vercel pull/build/deploy `--prod` → warm `/healthz` → deployed smoke. It has `permissions: contents: read, actions: read`, no extra action, and no step that reads `vars.SMTP_*` or `secrets.SMTP_*`.
- **The Render API** exposes `PUT /v1/services/{serviceId}/env-vars/{envVarKey}` ("Add or update a particular environment variable", bearer auth, body `{ "value": "…" }`, 200 returns the stored `{ key, value }`). It applies only to variables set directly on the service. The per-key endpoint documentation does **not** state whether the write triggers a deploy; only the bulk `PUT …/env-vars` page says changes are not deployed automatically (both fetched 2026-11-22). The design assumes the per-key write does not deploy and treats the first live run as the probe (§ Assumptions and § Deployed proof).
- **Render-wiring names do not exist yet.** No source, workflow, compose or `render.yaml` file references `RENDER_API_KEY` or `RENDER_SERVICE_ID` (planning artifacts aside), so both are new and must be created as part of this feature. `RENDER_API_KEY` is the highest-value new credential: Render documents API keys in `rnd_…` form and the key is workspace-scoped; it must never become a Render service variable.
- **Live GitHub state (names only, probe 2026-11-22).** Both `development` and `production` environments exist. `development` has `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_FROM` as variables and `SMTP_PASS` as a secret; it has no `SMTP_SECURE`, `SMTP_CONNECTION_TIMEOUT_MS`, `RENDER_SERVICE_ID` or `RENDER_API_KEY`. `production` has no variables and no secrets. `gh` is authenticated with `repo` scope; environment **write** permission is not proven by that scope and is a separate user-owned precondition (Q-12). No value was read during the probe. `SMTP_USER` must therefore be migrated from variable to secret in `development` **without changing its value**: in execution the variable is readable, so T5 reads it with `gh variable get`, pipes the value into `gh secret set` through stdin (never printed or recorded), then deletes the variable; if the variable were absent, the secret gets the `<CHANGEME-smtp-login>` placeholder. `SMTP_USER` is created as a secret in `production`. Under the 2026-11-22 owner decision, T5 preserves the other existing `development` entries (`SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, `SMTP_PASS`) and creates only `SMTP_SECURE`, `SMTP_CONNECTION_TIMEOUT_MS`, `RENDER_SERVICE_ID` and `RENDER_API_KEY`.
- **Environments.** `development` is provisioned and deploys from `main`; `production` exists as a GitHub Environment with no secrets, variables or protection rules, is reachable only by `workflow_dispatch`, and has no Render service, Vercel project or Neon branch. A production dispatch currently fails at the first missing secret (the Neon migration), and after T5 it must fail at the new Brevo guard instead.

## User stories

- As the repository owner, I want the Brevo configuration to live in the GitHub Environment so that one place holds the deployment email settings and I only replace placeholders with values.
- As the repository owner, I want to be blocked with an actionable message when a value is still a placeholder, so that a placeholder never becomes the running configuration.
- As the repository owner, I want the production entries to exist now and stay inert, so that provisioning production later is only a matter of filling values and creating assets.
- As the developer, I want `podman compose up` and Mailpit untouched, so local work never needs Brevo.
- As the reviewer, I want the guard and the sync to be unit-tested pure logic with a fake HTTP layer, so the deploy path is verifiable without live credentials.
- As the security reviewer, I want the Render API key to remain a pipeline credential — never a Render service environment variable — so a container compromise or environment dump cannot expose an account-scoped key that the runtime does not need.

## Acceptance criteria

Clause suffixes (`AC-4(a)`) identify the part a single task proves; the final verification task (T7) covers every whole AC. Commands run from the repository root. "Names only" means an output that contains variable/secret **names** and never a value.

  (c) `podman compose -f compose.yaml -f compose.smoke.yaml up -d mailpit` followed by `npm run smoke` exits `0` with every check passing, proving the backend image still builds and starts with the new deploy module present.
  Evidence: T7 build log.

- **AC-2 — The catalog and its classification are pinned.**

The synced list is `SMTP_CATALOG` only (seven entries). No other name is defined, required, validated or synced. Evidence: `render-env.test.ts` exact-array assertions (lengths 7, 2 and 9; exact key/source pairs; the sync iteration keys equal the seven `SMTP_CATALOG` keys).
  (b) The documented values are the pinned literals of § Configuration contract. For `production`, all nine are pinned: `SMTP_HOST=smtp-relay.brevo.com`, `SMTP_PORT=587`, `SMTP_SECURE=false`, `SMTP_CONNECTION_TIMEOUT_MS=10000`, `SMTP_FROM=<CHANGEME-verified-sender>`, `SMTP_USER=<CHANGEME-smtp-login>`, `SMTP_PASS=<CHANGEME-smtp-key>`, `RENDER_SERVICE_ID=<CHANGEME-render-service-id>`, `RENDER_API_KEY=<CHANGEME-render-api-key>`. Evidence: docs greps (AC-11/AC-12), the T5 names-only listings, the exact `--body` command lines recorded for the created names, the `NAME: preserved (existing)` entries for the five preserved `development` names (or the `SMTP_USER: placeholder created (variable absent)` branch), and the `SMTP_USER` migration commands (value moved in-process, never printed). - **AC-3 — Missing and placeholder values are detected by a pure function.**
  `isPlaceholder(value)` is `true` exactly when the value contains the literal `CHANGEME` (case-sensitive), and `false` for empty strings. `validateDeployEnv(env)` classifies every one of the nine `CATALOG` names as `missing` (empty or whitespace-only), `placeholder` (`isPlaceholder`) or `ok`, preserves catalog order in both lists, and returns `{ ok: true, values }` only when all nine are `ok`. With the pinned placeholder set for `development` it returns exactly `{ ok: false, missing: [], placeholders: ['SMTP_FROM', 'SMTP_USER', 'SMTP_PASS', 'RENDER_API_KEY'] }`; with an empty environment object every name is `missing`; with the all-real fixture it returns `{ ok: true }`. Evidence: `render-env.test.ts`.

- **AC-4 — The guard refuses to deploy and says what to fix.**

  (b) `--check-only` with the complete `development` fixture exits `0` and prints exactly `Deploy configuration OK: 9 value(s) present for the 'development' environment.`

- **AC-5 — The sync validates nine and writes exactly the seven SMTP names, verifying each write.**
  In default mode the CLI validates all nine names, then performs, in `SMTP_CATALOG` order, exactly one `PUT https://api.render.com/v1/services/<RENDER_SERVICE_ID>/env-vars/<KEY>` per SMTP name (seven requests), with headers `authorization: Bearer <RENDER_API_KEY>` and `content-type: application/json`, and body exactly `{"value":"<value>"}` (JSON-escaped, no extra fields, no `generateValue`). The response `value` must equal the sent value. Each success prints `SYNCED <KEY> (value verified, not shown)`; the run ends with `Synced 7 value(s) to Render service <id> for the '<env>' environment.` and exit `0`.
  (a) A non-2xx response prints `Render API error for <KEY>: HTTP <status> (<code>)` (`<code>` is the body's `code` when it parses, otherwise `unknown`), exits `1`, and stops before the next key. No response body text is printed.
  (b) A request that rejects with a timeout prints `Render API request for <KEY> timed out after 10000ms` and exits `1` (the request uses `AbortSignal.timeout(10000)`).
  (c) A request that rejects with any other transport error prints `Render API request for <KEY> failed: <sanitized>` and exits `1`; `<sanitized>` is the rejection message with every configured SMTP value, the API key and any `rnd_`-shaped token replaced by `[redacted]`, and the test feeds a message containing the sent value and a synthetic Render key shape to assert both are absent and the line is exact.
  (d) A stored value that differs from the sent value prints `Render API returned a different value for <KEY>; aborting` and exits `1`.
  (e) The sync sends exactly seven requests and never writes the two wiring names: no request body contains `RENDER_SERVICE_ID` or `RENDER_API_KEY` or their values; `RENDER_SERVICE_ID` appears only in the seven URL paths; `RENDER_API_KEY` appears only in the `authorization` header. A fake-fetch test that passes a `smtpValues` object with an extra `RENDER_API_KEY` property still produces seven calls and no wiring name in any body.
  (f) No successful or failing line contains any of the seven SMTP values or the API key; the service ID may appear in the URL and summary because it is a public identifier. Evidence: `render-env.test.ts` (fake fetch: call count, order, URL, headers, body, per-case output) and `render-env-cli.test.ts`.

- **AC-6 — Dry-run and check-only make no network calls.**

Evidence: `render-env-cli.test.ts`.

## Security considerations

- **Credential exposure.** The three secrets (`SMTP_USER`, `SMTP_PASS`, `RENDER_API_KEY`) travel only as step `env:` values and are read by the CLI from `process.env` — never from argv, a file, or a URL. The JSON body is built in-process, so no `curl` argument or shell `ps` entry can carry a value. The CLI prints key names and non-secret status text only; it never prints a response body, and the error line carries only the HTTP status and Render's machine-readable `code` (transport errors are value-redacted). GitHub masks registered secrets in logs, and no step enables shell tracing.
- **`SMTP_USER` migration at T5.** The existing variable's value is read with `gh variable get` into a shell variable and piped directly into `gh secret set` on stdin; it is never echoed, logged, written to a file or passed as a command argument, and the temporary shell variable is unset immediately. The build log records only the command lines and the `preserved (existing)` mode entry, never the value.
- **Pipeline-only wiring names.** `RENDER_API_KEY` is the Render bearer credential and `RENDER_SERVICE_ID` is the service coordinate. Neither is in the sync payload: the key is only the `authorization` header, the service ID only the URL path. `RENDER_API_KEY` is never a Render service variable, so a container compromise, crash dump or environment inspection cannot expose an account-scoped key the runtime does not need. `RENDER_API_KEY` stays only in the GitHub Environment secret (and the runner's `process.env`).
- **Placeholder safety.** `CHANGEME` is the sentinel; a value containing it is treated as unset. Documented placeholders use angle brackets (`<CHANGEME-smtp-login>`) so the extended credential guard cannot mistake them for values. The guard runs twice per deploy (preflight and again inside the sync) and is unit-tested against placeholder, missing and complete fixtures.
- **Blast radius.** The sync writes exactly seven service-level SMTP values, one key at a time, never the bulk replace endpoint, so `DATABASE_URL`, `DIRECT_DATABASE_URL`, `CORS_ORIGIN`, `ALLOWED_ORIGIN`, `APP_BASE_URL` and `SESSION_COOKIE_*` cannot be clobbered by a workflow bug. A partially failed sync cannot corrupt the running instance: Render applies saved variables on the next deploy, and the failed step stops the job before the deploy hook. The next run re-writes all seven values (idempotent).
- **Render API key scope.** A Render API key is workspace-scoped; the runbook asks for a key limited to the `development` workspace with the minimum permissions that include "Set environment variable and secret file values" (a separate key for `production` when it is provisioned), stored per environment as `RENDER_API_KEY`, rotated by the owner. A leaked key would allow environment-variable changes on the owner's services — a real risk that is documented rather than hidden.
- **Workflow permissions.** No permission or trigger change: `deploy.yml` still runs only on a successful `main` CI run or a manual production dispatch, never on `pull_request`, so a fork cannot reach the secrets.
- **Single source of truth.** Making GitHub authoritative means a Render-dashboard edit to one of the seven SMTP names is silently reverted on the next deploy. That is the requested semantics; it is documented in the runbook and the architecture docs (AC-11/AC-12) so an operator cannot be surprised.
- **No user-controlled data, no schema, no client-side secret.** The feature touches no request handling, no persistence and no frontend bundle.

### Rollback semantics (documented in the runbook)

- **A wrong value:** set the corrected value in the GitHub Environment and re-run the deploy workflow (or `workflow_dispatch` for production once provisioned). The sync rewrites all seven SMTP names, so no partial state survives.
- **A dashboard-only emergency fix:** it takes effect at the next deploy, which then overwrites it from GitHub; the runbook says so explicitly, so the fix must also be made in GitHub to persist.
- **A bad deployed revision:** Render dashboard → **Deploys** → last known-good → **Rollback**, which does not go through the workflow (and therefore is not blocked by the guard); or revert on `main` and let CI → Deploy rebuild once the GitHub values are valid.
- **The Render API key:** rotate it in Render, update the environment secret, and re-run; a revoked key fails the preflight/sync with a clear message and never reaches the running instance. It is never a Render service variable, so rotation does not touch the service environment.

### CLI contract (`src/backend/src/deploy/render-env-cli.ts`)

| Invocation | Behavior | Exit |
| --- | --- | --- |
| `--check-only` | validate all nine names; print AC-4 block or AC-4(b) line; no network | 0 / 1 |
| `--dry-run` | validate all nine; print one `DRY RUN: would set <KEY> …` line per SMTP name (seven) and the summary; no network | 0 / 1 |
| (no flag) | validate all nine; then `PUT` each of the seven SMTP names in order and verify the echo; print `SYNCED` lines and the summary | 0 / 1 |
| `--help` | usage | 0 |
| unknown option | `Unknown option: <option>` + usage | 1 |

- Inputs come from the environment: `TARGET_ENVIRONMENT` (message label, default `unknown`), `RENDER_SERVICE_ID`, `RENDER_API_KEY`, and the seven `SMTP_*` names. Nothing is read from argv, a file or stdin.
- Timeout: 10 000 ms per request (`AbortSignal.timeout(10000)`), no retries (a failed deploy is re-run; the operation is idempotent). `Retry-After` on 429/503 is not honored in this feature; the re-run path is the recovery.
- The successful sync summary is `Synced 7 value(s) to Render service <id> for the '<env>' environment.`; the dry-run summary is `DRY RUN complete: 9 value(s) validated for the '<env>' environment; 7 would be synced; no network calls made.`

### Render API contract

- `PUT https://api.render.com/v1/services/{RENDER_SERVICE_ID}/env-vars/{KEY}` with `authorization: Bearer {RENDER_API_KEY}` and `content-type: application/json`, body `{"value":"<value>"}`, for the seven SMTP keys only.
- Success: `200` with `{ "key": "<KEY>", "value": "<stored value>" }`; the CLI asserts `key === KEY` and `value === sent value`.
- Failure: any non-2xx prints `Render API error for <KEY>: HTTP <status> (<code>)`; a rejected request prints the timeout line (AC-5(b)) or the value-redacted generic line (AC-5(c)). No body text is printed.
- The call never deploys (assumed for the per-key endpoint; verified on the first live run): the existing `POST $RENDER_DEPLOY_HOOK_URL` remains the only deploy trigger.

## Assumptions

- The Render API accepts `PUT /v1/services/{serviceId}/env-vars/{key}` with a bearer token and returns the stored `{ key, value }`; a token holding the "Set environment variable and secret file values" permission is sufficient (403 `insufficient_token_scope` names the missing scopes if not).
- The per-key `PUT` documentation does not state whether the write triggers a deploy; only the bulk `PUT …/env-vars` page says changes are not deployed automatically (both fetched 2026-11-22). The design assumes no deploy, and the first live run is the probe: the Render deploy list must show no deploy between the sync and the hook. If a deploy does start, the hook queues a second deploy of the same commit; the operator records it, lets the run finish, re-runs the post-deploy verification, and a follow-up change adds a deploy-in-progress guard that skips the hook when the sync already started a deploy.
- A Render free web service has no shell, so "run `email:test` inside the deployed container" is only possible on a paid plan; the documented equivalent is a registration from the deployed frontend plus the local CLI run with the same credentials.
- GitHub Actions resolves `vars.*` and `secrets.*` against the job's `environment:`; unset names arrive as empty strings, which `validateDeployEnv` reports as missing.
- The `development` and `production` GitHub Environments both exist (2026-11-22 probe); `development` has the four SMTP variables and the `SMTP_PASS` secret listed in § Context, and `production` has none.
- `gh` is available with `repo` scope (2026-11-22 probe). Environment **write** permission is a separate user-owned precondition (Q-12), proven before T5 mutates anything by two validation-failure probes: `PUT .../environments/development/secrets/__write_permission_probe` with an empty JSON body and `POST .../environments/development/variables` with an empty JSON body. GitHub authorizes first and then rejects the missing required body with HTTP 422 (or 400), creating nothing; a 403/404 means the token lacks the write permission (classic `repo` scope, or fine-grained **Environments: Read and write**). If either probe is not 422, T5 is owner-executed: the owner runs the pinned `gh` commands (the UI may be used only to enter values) and records the names-only `gh` listings; the builder records them in `build-log-T5.md`. A UI-only listing is not verification evidence.
- A names-only listing proves presence and classification, not values; the T5 build log's exact `--body` command lines for created names and its `preserved (existing)` / migration-mode entries are the value evidence, and preserved values are not read or recorded beyond the in-process `SMTP_USER` transfer.
- The Render key format is documented as `rnd_…` (`render.com/docs/cli`, fetched 2026-11-22); the guard adds `rnd_[A-Za-z0-9_-]{20,}` alongside the `RENDER_API_KEY=` assignment pattern. `<CHANGEME-render-api-key>` and the 11-character `fixture-key` do not match either pattern.
- Node 24 supplies global `fetch` and `AbortSignal.timeout`; `@types/node@24` types both, so no dependency or `lib` change is needed.
- `tsx` (a backend devDependency) is installed by the deploy job's `npm ci`, so `npx --no-install tsx` works exactly as it does for the migration step.
- The seven SMTP names and their semantics are already accepted and unchanged; this feature only changes where the deployment values come from.
