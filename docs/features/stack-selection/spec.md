# Spec — Application Stack Selection

## Summary

Decide the CubeClicker application stack and make the decision real. `docs/architecture/stack.md` holds the split status "application stack NOT DECIDED / containerized delivery path DECIDED" and names this task as the step that resolves it ("the stack-selection task" in `AGENTS.md` and `docs/product/vision.md` § Status; user-authorized "Proceed with next steps", 2026-10-17). This feature (a) records the decided stack in `stack.md`/`AGENTS.md`/`containerization.md`, (b) resolves the concrete container conventions the containerized-workflow feature deliberately left open (Q-1: ports + env-var names, health signal, image naming, compose/Dockerfile locations, dev-mode behavior, exact local-run command), (c) authors the first-party scaffold — a minimal runnable skeleton where the backend serves a health endpoint and accepts a WebSocket connection at `/ws`, the frontend connects over WebSocket and shows connection status, both run as containers under a single `podman compose up`, and a containerized smoke test proves the path end to end (NO gameplay), (d) fills in `AGENTS.md` § Commands and resolves the flagged tension on line 32 ("Language: TypeScript (strict) per the agreed stack"), and (e) folds the carried backlog items that belong to this moment: the containerized-workflow code-r1 F1 (the TypeScript line, required) and F2 (orchestration-playbook §4 example-list asymmetry — folded here because this feature lands the container assets that make the asymmetry live). The stack recommendation below is the proposal submitted to the user at the approval checkpoint: the stack choice is user-owned, so nothing is built until it is approved. Dependency additions this feature introduces are enumerated in § Scope and are covered by that same approval.

## Stack decision (recommendation)

**Recommendation: TypeScript (strict) everywhere — backend Node.js 24 LTS + Fastify + `@fastify/websocket`; frontend React + Vite (SPA, static build); npm workspaces; Vitest; ESLint (flat config + typescript-eslint); `tsx` as the backend dev runner.**

Rationale: one language for the whole AI-native pipeline (best agent effectiveness, one toolchain, shared type-safety patterns across the protocol boundary); Node LTS + Fastify is a boring, well-documented WebSocket server path with first-class TypeScript; React + Vite gives small static bundles (vision: instant load, 60 fps, accessible, mobile-friendly) with the largest ecosystem for the future game UI; npm ships with Node (no extra host tooling) and npm workspaces fit the decided backend/frontend-container topology. The AGENTS.md:32 line ("TypeScript (strict) per the agreed stack") is resolved *by* this decision — TypeScript becomes the decided language and the line is rewritten to say so (no more implied agreement).

| Candidate | Verdict | Key trade-offs |
| --- | --- | --- |
| **TS everywhere: Node 24 + Fastify + React/Vite (recommended)** | ✅ | One language/toolchain; huge agent familiarity; WS-server and WS-client support native; images small; concurrency is event-loop-bound but ample for a clicker's multi-client scale |
| TS frontend + **Go** backend | ✗ | Excellent raw performance/single binary, but two languages split the AI pipeline, lose shared types, and contradict the TypeScript convention for no product gain at this scale |
| TS frontend + **Python (FastAPI)** backend | ✗ | Fast to write; two languages again, heavier runtime/images, no type sharing, weaker fit for long-lived connection fan-out |
| TS frontend + **Elixir/Phoenix** backend | ✗ | Best-in-class real-time primitives (channels/presence) but exotic runtime for this project's agents and ops; overkill for the known backlog |
| **Svelte** (vs React) | ✗ (alternative recorded) | Smaller bundles; materially rarer in agent training data and second-job-market patterns; React chosen for agent effectiveness; revisit only on user request |
| **pnpm / Bun / Deno** (vs npm / Node) | ✗ (alternatives recorded) | Faster installs/runtime in places; extra tooling surface, younger ecosystems, and lock-in risk for zero scaffold requirement; npm+Node is the boring default |
| **Next.js / SSR frontend** | ✗ | SSR adds server complexity and container topology for a game shell that is a static SPA; Vite SPA is smaller and simpler |

Explicit trade-offs of the recommendation: (1) Node's single-threaded model needs care if heavy per-tick simulation ever lands (not planned at this scale; worker threads remain available later); (2) React's baseline bundle is larger than Svelte's (kept in check by Vite tree-shaking and a strict "justify bundle additions" rule already in the engineering principles); (3) npm is slower than pnpm (immaterial at this size; swap is a user-owned future amendment). No deployment provider is chosen; images stay provider-neutral.

**What approval means:** the checkpoint approves this stack and the enumerated dependency set (§ Scope). If the user requests a different candidate, the spec is revised and re-approved *before* any scaffold task is dispatched; no build work happens until approval.

## Security considerations

- **No secrets anywhere:** no credentials, tokens, or keys in the repo, images, or compose; runtime config comes from environment variables with safe defaults; `.env*` stays user-owned and untouched; `.dockerignore`/`.gitignore` exclude `.env*` proactively.
- **Supply chain:** the enumerated dependency set is pinned in `plan.md` § Dependency manifest (major ranges + lockfile); `npm ci` in images; no install scripts from unknown sources; dependency additions beyond the set are ⚠️ ask-first; the lockfile is committed for reproducibility.
- **Containers:** prod stages run non-root (node `USER node`; unprivileged nginx); no privileged flags; only intentional ports (8080/5173) exposed, host-bound to `127.0.0.1` by default; deterministic image references (versioned base-image tags, digests optionally recorded); no provider lock-in.
- **WebSocket surface:** the scaffold endpoint carries no user data and no auth (local dev; loopback-bound); inbound messages are not yet processed by the scaffold (server pushes `hello` only), so untrusted-input handling obligations arrive with the first gameplay messages; future features inherit the existing untrusted-message rules.
- **User-controlled data/persistence:** none in this feature (no input surfaces, no storage).
- **Self-referential edits:** the feature edits framework files (`.opencode/**`) and root config; all pinned, baseline-diffed, git-revertible, never pushed; permission bootstrap limited to T0's six entries and reviewer-inspected.

## Testing strategy

- **Unit:** Vitest. Backend — app factory test (`/healthz` via `inject`; hello envelope shape). Frontend — connection module with an injected fake socket (status transitions, attempt cap, close-cancels-retry). Run via `npm test` (aggregated) or `npm test -w <workspace>`.
- **Integration/e2e (containerized):** `tests/e2e/smoke.mjs` inside the compose network (backend health, frontend serving, two concurrent WebSocket clients) via `podman compose … run --rm smoke`; the published-port path is checked from the host (AC-27).
- **Command transition:** `AGENTS.md` § Commands is TBD at planning time and filled by T1; scaffold ACs are verified with the newly defined commands (lint/typecheck/test/build/smoke/compose). Docs/framework ACs are inspection-verified.
- **Edge cases addressed by construction:** missing Podman (compose provider)/Node/network → `blocked` precondition; compose version lacking `--wait` → documented fallback (AC-26); hot-reload watch on non-Linux Podman Desktop (polling) documented, not defaulted; ports occupied → `strictPort` fails fast; dependency/version mismatch → blocked, never substituted.
- **Deferred coverage (explicit):** browser rendering/behavior e2e; load/soak testing; multi-instance scenarios — none required by this feature.

## Real-time considerations

- **Connection lifecycle:** the frontend connection module is the single lifecycle owner (connect → open → close → retry → teardown) per the engineering principles; the backend owns per-connection lifecycle server-side (one handler per socket; no leaking listeners).
- **Reconnection:** bounded retry with backoff and a reset on successful open (AC-23); unit-tested with a fake socket; no duplicate handlers by construction (single owner, idempotent disconnect handling).
- **Multi-client behavior:** concurrent clients are served independently; the smoke test opens two clients and asserts both receive `hello` (AC-20, AC-25) — the first concrete multi-client check in the codebase.
- **Server authority:** the scaffold's only server value (`serverTime` in `hello`) is server-generated; no shared/cross-client state exists yet — authority obligations for future values are inherited from the existing rules (backlog § Open tensions still owns the design question).
- **Identity vs. "no accounts":** not implicated — this feature adds no identity/presence surface; the tension stays flagged in `docs/product/realtime-backlog.md`, untouched.
- **Container path:** WebSocket upgrades traverse direct host port mappings (no proxy), consistent with `containerization.md`; proxy/LB handling remains deployment-time.

## Containerization impact

This feature is the container-asset authoring moment anticipated by `containerization.md`: it adds `compose.yaml` + `compose.smoke.yaml`, two Dockerfiles, pinned ports/env/health conventions (AC-5), a single-command local run documented in `README.md` and mirrored in `AGENTS.md` (AC-9, AC-12), environment-based config with safe defaults, no secrets in images, health signals per service, and the backend container exposing the WebSocket endpoint (AC-16, AC-17, AC-20). Provider neutrality is preserved: no provider selection, no provider-specific configuration; images remain runnable on any container platform. Deferred to deployment time (flagged, per `containerization.md`): proxy/LB upgrade handling, release tagging, prod runtime-config injection.

Every pinned `podman …` command form is verified in the first task that uses it (plan § Risks) — a provider divergence is a spec gap, never a reason to improvise a substitute command.

- Bind-mount file watching works on Linux build hosts (inotify); Podman Desktop hosts may need polling (documented, Q-7).
- No `.env*` files are needed: all config has compose-interpolated defaults; users may override via their own environment.
- The scaffold `hello` envelope is a scaffold-only shape; the first gameplay feature owns the real protocol schema.
- `src/shared` (shared protocol types) is deliberately not scaffolded; its path is reserved for the first feature that needs shared types (`plan.md` D-12) — no shared workspace, no premature abstraction.
- The six framework one-liners (plan.md § Pinned content contracts 13; AC-30 + AC-31) are sufficient to clear stale "undecided" guidance; the wider framework already carries container/realtime rules from the two accepted predecessor features.
