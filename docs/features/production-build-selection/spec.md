# Spec — Production Build Selection

## Summary

Production is deployed manually with `workflow_dispatch` (`environment=production`) after a CI-success preflight, but the deploy pipeline has no way to choose which successful build to ship: the checkout and the CI check use the dispatch ref, and the Render deploy hook builds the service's tracked `main` branch, so the only revision production can deploy is whatever `main` is at that moment. The request is to add a **build-selection pipeline parameter** to the production manual deploy: a dropdown of previous builds that defaults to the **latest successful build**, while the automatic development deploy keeps its existing `workflow_run.head_sha` checkout and Render hook behavior.

GitHub Actions `workflow_dispatch` `choice` options are static YAML values; GitHub has no native way to populate a dropdown from previous runs at dispatch time. This spec therefore ships the closest native design that is still a real dropdown with a default of latest: a required `choice` input named `build` whose options are `latest` plus the nine relative previous builds (`previous-1` … `previous-9`), resolved at run time from the newest successful `CI` push runs on `main`, plus an optional `build_sha` string input that pins one full 40-character lowercase SHA for an exact build. A selected build is defined as a **successful `CI` push run on `main`** (a commit SHA), not a Vercel deployment, a Render deploy or a Deploy-workflow run: the deploy pipeline rebuilds the backend and frontend from that verified source, re-runs the existing guard/catalog, and applies the fixed order (guard → schema compatibility → migration → sync → Render deploy → **Render deploy completion** → health → Vercel → smoke). The Render deploy step starts the selected commit through the API, and a completion poll waits for that deploy to reach `live` and verifies the service's current/latest deploy and commit before the health poll, Vercel deploy or smoke, so the live backend cannot still be the previous revision. A selected build that predates the current deploy/migration/smoke contract or an applied migration fails closed before any provider call. The feature sequences after `production-provisioning` (PR #4 is merged as `d10dfb1`; T6a complete; T6 complete with production live — Render `dep-dc4o1fff3r2c73c4asp0`, Vercel `dpl_2wFeBSaUSxYKkhpNtqZGFcby1Duq`, deployed smoke 8/8; T7 in progress; T8 pending), does not reopen that spec, does not add an environment, does not rename resources, keeps production manual and protected, leaves the **automatic** development path unchanged, and preserves the manual development default while aligning its Render mechanism to the API `commitId` for the dispatched SHA.

## Raw request (verbatim, scope boundary)

> "I would like to, for example, when deploying to production, being able to select a previous build. So, by default, when deploying to development on this automatic deployment we've done, it will select the latest successful build.
>
> But, when deploying to production, that will be manually, we should be able to select as a pipeline param the build we want to deploy that, by default, will be the last successful build.
>
> The selection should be as a dropdown of builds."

## Scope

### In scope

- **Production build selection:** add the `build` choice input (`latest`, `previous-1` … `previous-9`; default `latest`) and the optional `build_sha` full-SHA input to `.github/workflows/deploy.yml`; resolve the selection before checkout to one full commit SHA from the newest successful `CI` push runs on `main`; keep the existing `environment` input and its `production` default.
- **CI-success and on-main guard:** validate the **resolved** SHA (not the dispatch SHA) against a successful `CI` **push** run on `main`, and against GitHub's compare API (`ahead`/`identical`) so only a commit that is an ancestor of `main` can be deployed.
- **Same-revision deploy with a live completion proof:** check out the selected SHA, assert `HEAD` equals it, deploy that exact SHA to Render (Render API deploy-by-commit for manual dispatches), wait for that Render deploy to reach `status: live`, verify the service's current/latest deploy and commit match the selected deploy/SHA, then build and deploy Vercel from the same checkout (`--meta githubCommitSha`). The automatic `workflow_run` path keeps the Render deploy hook and its existing 45 s head start.
- **Selected-build safety gates:** fail closed before the migration or any provider when (a) the selected build's deploy guard/sync, migration runner and deployed-smoke files differ from the dispatch ref's current contract, or (b) the selected build's `src/backend/src/db/migrations/*.sql` set does not contain every migration already applied in the selected environment's `schema_migrations`. The schema gate compares names under the project's immutable-migration policy (applied migration files are never edited; new schema changes are new numbered files).
- **Fixed order and protection:** preserve guard → schema compatibility → migration → nine-name sync → Render deploy → **Render deploy completion** → `/healthz` poll → Vercel → warm → deployed smoke; production stays `workflow_dispatch`-only with the `main`-only deployment branch policy and required reviewers; the 23-name catalog (15 variables, 8 secrets), the eleven-name guard and the nine-name sync are untouched.
- **Automatic development unchanged; manual development defaults preserved with the Render API mechanism aligned:** the automatic `workflow_run` path keeps its `workflow_run.head_sha` checkout and Render hook behavior (including the pre-existing main-advance race). A manual development dispatch with the default `build=latest` still deploys `github.sha`, but its Render deploy now uses the API `commitId` for `github.sha` instead of the hook's `main` tip, so the deployed Render revision is the dispatch SHA (the Vercel build already uses the dispatch ref); a development dispatch with a non-default build selection fails closed with a clear message.
- **CI pinning and a workflow-gate harness:** update the `ci.yml` `verify-workflows` dispatch parse and add a build-selection parse that pins the exact inputs/options/defaults, resolver, guard, checkout ref, contract/schema steps, Render/Vercel steps, the 21-step deploy list and `ci.yml`'s own 11-step `verify-workflows` list. Add `tests/deploy/gate-fixtures.mjs`, which extracts the actual workflow `run` blocks for the resolver, guard, deploy-contract, schema gates, **Render creation (`Deploy Render backend`) and Render completion (`Wait for Render deploy to complete`)** (and the new CI parse) and executes them against fixtures; no reimplemented gate logic.
- **Documentation:** update `README.md`, `docs/architecture/deployment.md`, `docs/architecture/vercel-render-neon.md` and both release-identity statements in `docs/architecture/containerization.md` (lines 37 and 42); document the relative dropdown labels, the resolved-SHA/CI-run output, the lowercase full-SHA `build_sha` rule and the immutable-migration policy; propose (not apply) the `docs/features/README.md` row.
- **Evidence:** `actionlint`, the parses, the actual-block gate harness, exact-message assertions, an owner-gated live production deploy of `previous-1` followed by a `latest` restore, the `status: live` completion and current-deploy proof, a post-merge automatic development deploy proof, `/healthz` 200 and `DEPLOYED SMOKE PASS (8/8 checks)`.

### Definitions

- **Build** — a commit on `main` with a successful `CI` run whose event is `push` and whose head branch is `main`. The commit SHA is the build identity. A Vercel deployment, a Render deploy or a Deploy-workflow run is a **deploy artifact/attempt**, not a build.
- **Selected build** — the SHA resolved from `build`/`build_sha` for a production dispatch.
- **Deploy contract** — the deploy guard/sync modules, the migration runner/CLI and the deployed-smoke script that must match the dispatch ref's current versions; an old build must not run an older guard/catalog or an older smoke.
- **Deploy completion** — the selected Render deploy has reached `status: live`, and the service's current/latest deploy (`GET /services/{id}/deploys?limit=1`, `.[0].deploy`) has the selected deploy ID and commit SHA.
- **Eligible build** — a selected build that passes the CI-success/on-main guard, the deploy-contract identity gate, the schema-compatibility gate, the Render deploy completion/current-deploy gate and the deployed smoke.
- **Dropdown** — the `build` `choice` input. It is a real GitHub Actions dropdown; its labels are relative because native options are static.

## Contracts

### 1. Dispatch inputs (`.github/workflows/deploy.yml`)

```yaml
on:
  workflow_dispatch:
    inputs:
      environment:            # unchanged
        description: GitHub Environment to deploy (development or production)
        type: choice
        required: true
        default: production
        options: [production, development]
      build:
        description: Build to deploy (production only; latest = newest successful CI build on main)
        type: choice
        required: true
        default: latest
        options: [latest, previous-1, previous-2, previous-3, previous-4, previous-5, previous-6, previous-7, previous-8, previous-9]
      build_sha:
        description: Optional full 40-character lowercase commit SHA for an exact build (production only)
        type: string
        required: false
        default: ''
```

- The workflow keeps exactly the two triggers (`workflow_run`, `workflow_dispatch`), the job `if`, the `main`-only production branch policy and the environment/concurrency expressions.
- The selection inputs are **production-only**. A development dispatch with `build != latest` or a non-empty `build_sha` fails before checkout (exact message in AC-2(e)); a development dispatch with the defaults deploys `github.sha` exactly as today, with the Render mechanism aligned to the API `commitId`.
- `build_sha` is a secondary exact-pin escape hatch for an exact build; it is not the primary dropdown UX and it is validated by every gate as a selected build. It must be a full 40-character lowercase commit SHA (AC-2(d)).

### 2. Build resolution (dispatch-only, pre-checkout)

- `Resolve selected build` runs before `Checkout`, uses `gh` with `GH_TOKEN`, and writes `sha` and `source` outputs.
- Production `latest`/`previous-N`: list the newest successful `CI` push runs on `main` through the Actions API:
  `gh api "repos/$GITHUB_REPOSITORY/actions/workflows/ci.yml/runs?event=push&branch=main&status=success&per_page=100" --jq '.workflow_runs[] | [.head_sha, (.id|tostring), .created_at] | @tsv'`.
  Dedupe by `head_sha` preserving the API's newest-first order, then pick index 0 for `latest` and index N for `previous-N` with `awk -F'\t' 'NF && !seen[$1]++' | sed -n "$((index + 1))p"`.
- The resolver prints `Resolved build: <sha> (<source>)` (`latest`, `previous-N`, `pinned` or `dispatch-ref`); when the selected build came from the list it also prints `CI run: <id> <createdAt>`. The docs explain that `previous-N` labels are relative positions, not SHA labels, and that the run prints the resolved SHA and CI run.
- `build_sha` must match `^[0-9a-f]{40}$`; it is rejected with `build_sha must be a full 40-character lowercase commit SHA.` Combining `build_sha` with a non-`latest` `build` is rejected with `Set either build=previous-N or build_sha, not both.`
- An unavailable relative choice fails with `Build choice <choice> is unavailable: fewer than <N+1> successful CI builds on main.`
- The Actions API is used instead of a second `gh run list` so the T6a "exactly one `gh run list` in `deploy.yml`" invariant remains true; the one `gh run list` (the guard) keeps `--repo "$GITHUB_REPOSITORY"`.

### 3. CI-success and on-main guard (dispatch-only, pre-checkout)

`Verify CI succeeded for target commit` keeps its name and its `--repo "$GITHUB_REPOSITORY"` line, and validates the **resolved** SHA:

```bash
if ! conclusion=$(gh run list --repo "$GITHUB_REPOSITORY" --workflow CI --event push --branch main --commit "$TARGET_SHA" --limit 1 --json conclusion --jq '.[0].conclusion'); then
  echo "Unable to query CI runs for $TARGET_SHA; the token may lack actions:read" >&2
  exit 1
fi
if [ "$conclusion" != "success" ]; then
  echo "CI for $TARGET_SHA is not successful (conclusion: ${conclusion:-none}); refusing to deploy" >&2
  exit 1
fi
status=$(gh api "repos/$GITHUB_REPOSITORY/compare/$TARGET_SHA...main" --jq '.status')
case "$status" in
  ahead|identical) ;;
  *) echo "Build $TARGET_SHA is not on main (compare status: $status); refusing to deploy." >&2; exit 1 ;;
esac
echo "CI succeeded for $TARGET_SHA"
```

- `--event push --branch main` excludes pull-request CI runs for the same SHA; the compare API `ahead`/`identical` proves the SHA is an ancestor of (or equal to) `main`. A commit that is not on `main`, a failed/missing run, or a non-push run fails closed before `Checkout` and before any provider call.
- This also enforces the documented `--ref main` rule for manual dispatches: a dispatch from a non-`main` ref has no successful push run on `main` for its SHA and fails the guard. The `production` Environment's `main`-only branch policy remains the first gate.
- The step is skipped on the automatic `workflow_run` path (the job `if` and `Reject non-push CI runs` are the existing gate there).

### 4. Selected-build safety gates (dispatch-only, after checkout/install)

**4a. Deploy-contract identity.** `Check selected build deploy contract` fetches the dispatch-ref commit (`${{ github.sha }}` for a dispatch; `main` tip) and requires the selected checkout to be identical, for these files:

```
src/backend/src/deploy/render-env.ts
src/backend/src/deploy/render-env-cli.ts
src/backend/src/auth/config.ts
src/backend/src/db/migrate-cli.ts
src/backend/src/db/migrate-runner.ts
src/backend/src/db/migrate.ts
tests/e2e/deployed-smoke.mjs
```

It runs `git diff --quiet "$PIPELINE_SHA" -- <files>`; a difference fails with `Build <sha> has a different deploy/migration/smoke contract than the dispatch ref <pipeline-sha>; refusing to deploy a build that predates the current deployment contract.` It also requires `require.resolve('pg')` in the installed selected build (`Build <sha> does not include the pg dependency required by the deployment tooling; refusing to deploy.`). The selected build's **migrations SQL** are deliberately excluded: the selected build is expected to carry its own migration set, which 4b validates.

**4b. Schema compatibility under immutable migrations.** `Check selected build schema compatibility` reads `SELECT name FROM schema_migrations` through the selected environment's `DIRECT_DATABASE_URL` (treating a missing `schema_migrations` table as zero applied migrations for a first deploy) and requires every applied name to exist under the selected checkout's `src/backend/src/db/migrations/`. A missing file fails with `Build <sha> predates applied migration(s): <names>; refusing to deploy a build older than the migrated schema.` before `Migrate Neon database`, the sync, Render or Vercel. Success prints `Schema compatibility OK for <sha>: <n> migration(s) in build, <m> applied on the target branch.` The connection string is never printed. The gate compares **names** and relies on the project's **immutable-migration policy**: an applied `.sql` file is never edited; new schema changes are new numbered files. The docs record the policy; if it is ever relaxed, the gate must compare content hashes (Q-3/F11).

**4c. Why these gates exist.** Selecting an old SHA while the database schema has advanced can run old code against a newer schema; the project's migrations are forward-only and add-only, but the safe rule is conservative: only builds at or after the current migrated-schema head (and at or after the current deploy/migration/smoke contract) are eligible. An older build fails closed; an owner who genuinely needs an older backend must restore a compatible schema via the existing Neon PITR runbook as a separate operation (Q-3).

**4d. The gate harness is the durable test.** `tests/deploy/gate-fixtures.mjs` extracts the **actual** `run` blocks of `Resolve selected build`, `Verify CI succeeded for target commit`, `Check selected build deploy contract`, `Check selected build schema compatibility`, `Deploy Render backend` and `Wait for Render deploy to complete` from `.github/workflows/deploy.yml` (and the `Validate deploy build selection contract` `run` block from `.github/workflows/ci.yml`) and executes them against fixtures with a stub `gh`, a local git remote, a stub `curl` (POST/GET deploy responses, status sequences, transient failures) and a stub `pg` module. The stub `pg` directory is first on `NODE_PATH`, followed by the repo's `node_modules` for `js-yaml`/other imports, so both `require.resolve('pg')` (contract) and `require('pg')` (schema) resolve the stub. It covers the missing-`schema_migrations`-table case, every Render creation/completion status/failure path and every exact message; no `diff`/`check_missing`/resolver/render reimplementation is accepted.

### 5. Same-revision Render and Vercel deploy with a live completion proof

- `Checkout` uses `ref: ${{ steps.resolve_build.outputs.sha || github.event.workflow_run.head_sha || github.sha }}`; `Confirm selected build checkout` asserts `git rev-parse HEAD` equals the same expression and prints `Deploying build <sha> to <environment>`. A mismatch fails with `Checked-out build <actual> does not match the selected build <expected>.`
- **Render creation (manual dispatches):** `Deploy Render backend` calls
  `POST https://api.render.com/v1/services/$RENDER_SERVICE_ID/deploys`
  with `authorization: Bearer $RENDER_API_KEY` and body `{"commitId":"<TARGET_SHA>","clearCache":"do_not_clear"}`. The Trigger Deploy API reference's OpenAPI definition (`https://api-docs.render.com/reference/create-deploy`) declares `201 Created` (deploy object) and `202 Queued` (no content) responses; the deploy-hook documentation (`https://render.com/docs/deploy-hooks`) describes `202 Accepted` as a different deploy already in progress under the workspace's `Wait` policy and states the body does not include a deploy ID. The step requires HTTP 201, a `dep-…` `.id`, and `.commit.id = TARGET_SHA`; it prints `Render deploy: <deploy-id> <status> for <sha>`. HTTP 202 fails closed with `Render deploy queued behind an in-progress deploy (HTTP 202); re-run after it completes.`; a non-`dep-` ID fails with `Render deploy id <deploy-id> does not start with dep-; refusing to continue.`; a commit mismatch fails with `Render deploy commit mismatch: expected <sha>, got <commit>; refusing to continue.` The response body is never printed.
- **Render completion (manual dispatches):** `Wait for Render deploy to complete` polls
  `GET https://api.render.com/v1/services/$RENDER_SERVICE_ID/deploys/$DEPLOY_ID`
  every `RENDER_DEPLOY_POLL_INTERVAL_SECONDS` (default 10) for up to `RENDER_DEPLOY_TIMEOUT_SECONDS` (default 900). Transient 5xx/network GET failures and unreadable responses are retried until the deadline; only a terminal `build_failed`, `update_failed`, `canceled`, `pre_deploy_failed` or `deactivated`, the timeout, or a current-deploy mismatch fails closed. A terminal status fails with `Render deploy <deploy-id> ended with status <status> for <sha>; refusing to continue.`; timeout fails with `Render deploy <deploy-id> did not reach live within <timeout>s (last status: <status>); refusing to continue.` After `live`, it reads `GET /v1/services/{id}/deploys?limit=1` (the latest deploy, `.[0].deploy`, with bounded `curl` retries), requires `.[0].deploy.id = <deploy-id>` and `.[0].deploy.commit.id = TARGET_SHA`, prints `Render current deploy: <id> <commit>` and `Render deploy live: <deploy-id> for <sha>`. A mismatch fails with `Render service current deploy <current-id> (<current-commit>) does not match the selected deploy <deploy-id> (<sha>); refusing to continue.` The old 45 s “head start cannot pass against the old instance” claim is false and is removed. The harness executes the actual block with a short timeout/poll override to prove the timeout path.
- **Render (automatic `workflow_run`):** the existing `curl -fsS -X POST "$RENDER_DEPLOY_HOOK_URL"` stays, and the same `Wait for Render deploy to complete` step's automatic branch keeps the existing 45 s head start because the hook does not provide a deploy ID to poll. The automatic path's existing behavior and its narrow main-advance race are unchanged; the completion/current-deploy proof is for manual selected builds. The hook is never used for a selected old build.
- **Vercel:** `Build Vercel frontend` and `Deploy Vercel frontend` run from the selected checkout; the deploy adds `--meta githubCommitSha="$TARGET_SHA"` and prints `Vercel deployment: <url> for <sha>`. `vercel pull`/`build`/`deploy --prod` keep their existing semantics and environment values. The selected build re-reads the current GitHub Environment configuration; it does not restore historical environment values.
- **Same-SHA evidence:** the resolver line, the checkout line, the Render response `.commit.id`, the completion `status: live` + current-deploy ID/commit and the Vercel deployment metadata/line all carry the same full SHA. If the Vercel projection omits custom metadata, the build log records `Vercel metadata projection: unavailable` plus the Vercel deployment ID and the checkout/Render evidence (AC-4(d)). No provider step uses `github.sha` when a selected build is active (except the automatic `workflow_run` path, where `github.sha`/`head_sha` is the selected build).

### 6. Automatic development path (unchanged) and manual development alignment

- **Automatic:** trigger `workflow_run` of `CI` `completed` on `main`; job `if` exactly `github.event_name == 'workflow_dispatch' || (github.event.workflow_run.conclusion == 'success' && github.event.workflow_run.head_branch == 'main')`; `Reject non-push CI runs` unchanged. The resolver, guard, deploy-contract and schema-compatibility steps are skipped; the checkout uses `workflow_run.head_sha`; the Render hook is used; the completion step's automatic branch keeps the 45 s head start; Vercel builds the same checkout; warm + deployed smoke unchanged. The only additions are the universal `Confirm selected build checkout` assertion and the Vercel `--meta`/line; both are observational and carry the same head SHA.
- **Manual development:** a dispatch with the default `build=latest` resolves `github.sha` (`dispatch-ref`) and deploys it; the Render API `commitId` now deploys that SHA instead of the hook's `main` tip, so Render and Vercel use the dispatch SHA. This is an explicit, intentional mechanism change (the old hook could deploy a newer `main` than the Vercel build); it preserves the manual development default and the trigger choices. A non-default selection fails closed.

## User stories

- As the repository owner, I want a production deploy dropdown of previous builds defaulting to the latest successful build, so I can redeploy a known-good revision without a throwaway revert commit.
- As the repository owner, I want the selected build to reach the Render backend and the Vercel frontend as the same commit, with the Render deploy proven `live` and current before health/Vercel/smoke, so a production deploy cannot mix revisions or pass against the old instance.
- As the security reviewer, I want every selected SHA to pass the CI-success guard, the on-`main` check, the deploy-contract identity gate and the schema-compatibility gate, so a build selection cannot bypass CI or run old code against a newer schema.
- As the security reviewer, I want the production protection gate and the 23-name catalog unchanged, so the new parameter cannot widen the credential or deployment surface.
- As the operator, I want the automatic development deploy unchanged and the manual development default preserved while its Render mechanism is aligned, so the new production UX does not silently change the development path.
- As the maintainer, I want the dropdown/resolution/guard/deploy contract and the actual gate blocks pinned by executed fixtures and CI parses, so a future workflow edit cannot silently weaken build selection.

## Security considerations

- **User-controlled inputs.** `build` is a closed `choice`; `environment` is a closed `choice`; `build_sha` is strictly `^[0-9a-f]{40}$` and validated before any `gh`, git or provider call. No input is interpolated into a shell command, JSON body or SQL query without validation; the Render body uses the validated hex SHA.
- **No guard bypass.** Every production dispatch validates the resolved SHA against a successful `CI` **push** run on `main` and the compare API (`ahead`/`identical`). The automatic path keeps the `workflow_run` success gate. A missing/failed/non-push/non-`main` run stops before checkout. The `production` Environment's branch policy and required reviewers remain.
- **Same guard/catalog.** The deploy-contract identity gate requires the selected build's guard/sync (`render-env.ts`, `render-env-cli.ts`, `auth/config.ts`), migration runner/CLI (`migrate-cli.ts`, `migrate-runner.ts`, `migrate.ts`) and deployed smoke to be byte-identical to the dispatch ref's current versions, so a selected old build cannot run a weaker guard or an older smoke. The selected build's migration SQL is applied by the current runner; the schema gate proves its migration set contains every applied migration under the immutable-migration policy.
- **Live revision proof.** A manual selected-build deploy is not considered successful at the Render response; the workflow polls the deploy to `status: live` and verifies the service's current/latest deploy ID and commit. The health poll, Vercel deploy and smoke run only after that proof, closing the false-positive path where Render keeps the old instance serving.
- **Schema safety.** The selected build must contain every applied migration; an old backend cannot run against a newer schema. Forward-only migrations are never undone by this feature. The operator cannot override the gate (Q-3); a real schema rollback is the separate Neon PITR runbook. The immutable-migration policy is the basis for the name-only comparison; a policy relaxation requires content hashes.
- **Secret handling.** `RENDER_API_KEY` is sent only in the `authorization` header; `RENDER_DEPLOY_HOOK_URL` is used only on the automatic path; `DIRECT_DATABASE_URL` is passed as step `env:` to the schema check and migration and never printed. The Render response body is parsed for `id/status/commit.id` and never printed; `pg` errors print only `error.message`, never the connection string. No step enables shell tracing; GitHub masks registered secrets; build logs record names/IDs/statuses/short SHAs only.
- **Protection.** The production job still pauses for the `production` Environment reviewer; the build input is visible in the run metadata. The branch policy allows only `main`; the compare gate proves the selected SHA is on `main`. A production dispatch cannot be triggered by a `push`.
- **Rollback/promotion semantics.** `vercel promote`/`vercel rollback` and Render dashboard rollback are per-provider, immediate and do not re-run the guard/migration/sync/smoke; they can leave the backend and frontend on different revisions and can restore old artifacts. The coordinated recovery path is a build-selection deploy of the known-good SHA. The selected build re-reads current environment values and does not restore stale configuration; if an old environment value is required, it must be restored explicitly in the GitHub Environment, re-deployed, and re-validated.
- **Supply chain.** No new action or npm dependency; the pinned actionlint and existing action SHAs stay. `js-yaml`/`pg` come from the locked tree. The Render API is called with the existing `${RENDER_API_KEY}`.
- **No user data or identity change.** This is pipeline/runbook configuration; the auth model, sessions, game state and WebSocket protocol are unchanged. No "no accounts" conflict arises.

## Real-time impact

- A selected-build deploy restarts the single Render instance and replaces the Vercel production deployment. Every WebSocket closes; clients reconnect on the unchanged bounded policy (10 attempts, 500 ms → 5 s backoff), and in-memory rooms reset. This is the existing deploy behavior, not a new failure mode.
- The completion poll and current-deploy check prove the selected Render deploy is the one serving before the health poll/smoke; the old instance can keep serving during the build, but the workflow does not declare success until the selected deploy is `live` and current. During the provider's short old/new overlap, a client still attached to the old instance may see a different room registry until its socket closes and it reconnects; the selected frontend and backend are deployed from the same SHA, so the protocol and client/server contract match.
- A selected previous build is a normal backend restart plus a frontend deployment of the same revision; it does not restore old in-memory rooms (they are not persisted). No cross-client state moves to Postgres or Vercel.
- No identity or "no accounts" question is reopened: build selection is operator configuration, not a user identity.

## Containerization impact

- No new image, Dockerfile stage, compose service, port, volume, build argument, health signal or WebSocket endpoint. The Render production service builds the selected commit's `src/backend/Dockerfile` with `dockerContext .` through the Render API `commitId`; Vercel builds the selected checkout's `src/frontend` static SPA. The images remain provider-neutral; `compose.yaml`, `compose.smoke.yaml`, `podman compose up` and the local/smoke images are unchanged.
- Configuration remains environment-based: the selected build reads the current GitHub Environment values, and secrets are injected at run time. The release identity is the selected commit SHA for a manual production dispatch, the dispatch SHA (`github.sha`) for a manual development dispatch and `workflow_run.head_sha` for the automatic path, matching the container conventions; both release-identity statements in `docs/architecture/containerization.md` are updated.
- `GET /healthz` remains the health signal (Render has no platform health check), `/ws` stays on port 8080, and Render still terminates TLS/passes WebSocket upgrades. No container convention is reopened.

## Open questions

- **Q-1 (owner) — Dropdown design (requires owner acceptance at the approval checkpoint).** Default/shipped: static relative choices `latest`, `previous-1` … `previous-9`, plus the optional `build_sha` exact pin. The relative labels identify positions, not SHAs or dates; the run prints `Resolved build: <sha> (<source>)` and `CI run: <id> <createdAt>` after selection, and `build_sha` is the exact selector. A generated list of real recent SHA/date labels (option B) would need a scheduled workflow or bot that commits the updated `deploy.yml` to `main`, adding automation writes, a workflow-file update path and drift risk; an external dispatch UI (option C) leaves native GitHub; GitHub re-run/promote/rollback (option D) is per-provider and uncoordinated. The owner must accept Q-1 before building; the default A is native, reviewable and write-free.
- **Q-2 (owner) — What "previous" means.** Default: previous **successful CI build on `main`** relative to the newest successful build, not the previous production deploy. Deployment history includes failed/partial runs and per-provider rollbacks, so it is not a clean build list. If the owner wants deployment-history semantics, a follow-up would query Deploy runs and define the eligibility rule; the shipped default is CI-build order.
- **Q-3 (owner) — Old-build eligibility and immutable migrations.** Default: fail closed when the selected build predates an applied migration or the current deploy/migration/smoke contract, under the immutable-migration policy (applied files never edited; new changes are new numbered files). An owner override would allow old code against a newer schema (or an older guard/smoke); the safe alternative is the existing Neon PITR runbook to restore a compatible schema, then deploy. The owner may request an explicit override, but it needs a separate risk acceptance; relaxing the immutable policy requires content hashes.
- **Q-4 (owner) — Selection scope.** Default: production only. Manual development keeps `github.sha` and its defaults, with the Render API mechanism aligned; a development dispatch with a non-default selection fails closed. Extending selection to development is a small follow-up but changes the development path, so it is not shipped silently.
- **Q-5 (owner) — Dropdown depth.** Default: 10 options (`latest` + `previous-9`). More options are a one-line YAML change but keep relative labels; the `build_sha` escape hatch covers exact older builds. The owner may choose a different depth before build.
