# Spec Review — r1

## Summary

❌ **changes requested** — The feature artifacts are unusually strong: every raw-request ask except one maps to a binary-testable AC (21 numbered ACs, all mapped to tasks, all with named evidence files), the three.js decision is stated with a criterion table, an ask-first trace, and a T1 hard gate; the DAG is acyclic, `[P]` batches are file-disjoint, and the real-time/container impact is explicitly handled as a non-goal + additive-only. But three contradictions inside the artifact set will surface mid-build as verification failures: (F1) the two headline camera animations from the request — the intro flight to the cube and the travel pull-away — are pinned in § UX behavior but appear in **no acceptance criterion**, so the build gate's per-AC table and the code gate can never verify them; (F2) T7 (starfield) consumes `STAR_COUNT`, which plan § Interfaces exports from T5's `effects.ts`, while T7 `depends_on` lists only T2 and is DAG-batched **in parallel with T5** — a guaranteed import-time dead end in that batch; (F3) plan § UI interfaces pins an `aria-live` faces-destroyed counter while AC-14 pins the phase region as "*the only* live region" — T14's own pinned markup fails T14's own AC. All three are planner-fixable; no user input is needed beyond the already-flagged Q-1 checkpoint.
