# Spec — Cube Game Frontend (first playable 3D experience)

## Summary

Deliver the first playable CubeClicker frontend: a futuristic 3D cube in a galaxy/starfield backdrop (black with stars), entered via an intro camera flight; the player clicks mini-cubes tiling the big cube's six faces, each clicked mini-cube explodes away; the view rotates through space (drag or keyboard) to reach other faces; a face disappears when its last mini-cube is gone; when all six faces are gone, a galaxy-travel transition arrives at a new cube with a different material/colour style. Session stats (clicks and faces destroyed) display live. The feature is frontend-only with local client state: no backend integration, no multiplayer/sync, no persistence, no economy — those are explicit non-goals with documented hook-in points for future features. Game logic lives in pure, DOM-free modules (testable under Vitest in the existing node environment); three.js (new dependency, pending the user checkpoint) renders through a thin adapter behind interfaces.

## Scope

### In scope

- Frontend workspace (`src/frontend`): new `game/**` (pure logic), `render/**` (three.js adapter), `input/**` (event mapping), `ui/**` (React components) modules; `App.tsx` rewritten as the game shell; `App.test.tsx` rewritten for the new shell.
- Two new frontend dependencies: `three` (runtime) and `@types/three` (dev) — the flagged user-checkpoint decision (§ 3D rendering library decision); lockfile regenerated by npm.
- `docs/product/glossary.md`: new canonical terms **mini-cube**, **face**, **cube level** (same change that introduces them).
- Pinned UX: intro + skip, click/explode, pointer+keyboard rotation, keyboard selection cursor, face destruction, all-faces-gone travel to the next styled cube, live stats HUD, reduced-motion profile, touch/mobile support.
- Testing: pure-logic unit tests, node-level integration tests (real three.js scene graph), React SSR shell tests; coverage ≥ 80 per workspace via `npm run coverage`.

### Explicitly out of scope

- Any backend work, WebSocket usage in gameplay, shared/cross-client state, identity/accounts, reconnection — `src/frontend/src/ws/connection.ts` stays untouched and unreferenced by the game.
- Persistence (no save/localStorage; refresh restarts a fresh session), offline/idle progress, points/economy/upgrades/prestige.
- Audio, browser-automation e2e, CI changes, container/Dockerfile/compose changes, new tooling or DOM test environments.
- Gameplay difficulty scaling across cube levels — later cubes differ by visual style only.

## UX behavior (pinned)

Subsections below define behavior; § Acceptance criteria turns each into a binary-testable obligation. All numeric values are pinned in § Pinned constants.

### Loading, intro, and skip

On load the galaxy starfield is visible immediately; the camera performs an intro flight from far out to the gameplay distance in front of the cube. During `intro`, gameplay input (mini-cube clicks, rotation) is ignored. The intro ends after `INTRO_DURATION_MS` or immediately on a skip event (any pointer tap — a gesture below `TAP_DRAG_THRESHOLD_PX` — or any key press; pointer drags during `intro` are ignored); on end, phase becomes `playing`. A visible skip hint is shown ("Click or press any key to skip").

### Cube, mini-cubes, and styles

A cube level has 6 faces; each face is a `GRID_SIZE`×`GRID_SIZE` grid of clickable mini-cubes (default 5×5 = 25 per face, 150 per cube level). Mini-cube ids are `face:row:col` (rows/cols 0-based). Each cube level uses one style from the pinned styles list (5 styles, distinct materials/colours, cycled in order); the cube body/faces render in the style's `cubeColor`, mini-cubes in `miniCubeColor`, highlights/accents in `accentColor`.

### Click and explosion

A click/tap (or keyboard confirm) on a remaining mini-cube during `playing`: removes it from the board state immediately (repeat clicks on the same id are no-ops), increments `clicks` by exactly 1 at dispatch time (real-time), and triggers the explosion: the mini-cube's instance is hidden and a particle burst (`EXPLOSION_PARTICLE_COUNT` fragments) plays for `EXPLOSION_DURATION_MS`, after which the burst is removed. Other mini-cubes remain clickable throughout. A pointer click/tap is gated to the current front face: it explodes only when the pick hits a mini-cube on the front face; hits on other (partially visible) faces are ignored — no explosion, no rotation, no stat change (keyboard confirm is inherently front-face-only via the selection cursor).

### Rotation and face navigation

Pointer: a drag over the canvas beyond `TAP_DRAG_THRESHOLD_PX` commits exactly one 90° rotation step about the drag's dominant axis (one step per gesture); drags below the threshold are taps (no rotation). Keyboard: ArrowLeft/ArrowRight = one yaw step, ArrowUp/ArrowDown = one pitch step. Steps animate over `ROTATION_DURATION_MS` and always settle on exact 90° multiples (yaw mod 4, pitch clamped to ±1 quarter-turn so the top/bottom faces can be faced; pitch allows 0 (side faces) and ±1 (top/bottom)). At most one rotation step is queued while a step animates; further dispatches during the animation are ignored. The facing ("front") face is derived from the orientation and determines where clicks land (pointer picks are front-face-gated — see § Click and explosion).

### Keyboard selection cursor

A visible highlight cursor is anchored to the front face's grid. W/A/S/D move it up/left/down/right (clamped to the grid). Enter/Space explodes the highlighted mini-cube with exactly the same effects as a click (same stat increment, same intents). Whenever the cursor's target is gone (exploded, face cleared) or the orientation changes, the cursor re-anchors deterministically to the nearest remaining mini-cube on the front face (grid distance, then lowest row, then lowest column); if none remain, the cursor is absent.

### Face destruction

When a face's last mini-cube is cleared: `facesDestroyed` increments by exactly 1 at that moment; the face's plate fades out over `FACE_FADE_MS` and its geometry/instances are removed and disposed; remaining faces stay playable. If the destroyed face was the front face and other faces remain, the view auto-rotates (one step at a time, re-evaluated after each step) toward the nearest face that still has mini-cubes — deterministic order: fewest steps from the current orientation, then FACE_IDS order.

### All faces gone → travel → next cube level

When the sixth face is destroyed, phase becomes `travel` after the face fade completes. The travel transition shows a galaxy streak (starfield hyper-streak mode + camera pull-away) for `TRAVEL_DURATION_MS`, then: `levelIndex` advances, a fresh board is built, the next style is applied (style id differs from the previous; cycling in list order), orientation and cursor reset to the default front-facing state, stats carry over unchanged, phase returns to `playing`. No input is accepted during `travel`.

### Stats HUD

The HUD displays, live and always visible: `Clicks: N` (increments per exploded mini-cube, at dispatch time), `Faces destroyed: N` (cumulative across cube levels), and `Cube N` (1-based level indicator). HUD values come from the session snapshot; the snapshot's object identity is stable until a value changes (React-safe subscription contract).

### Reduced motion

When the motion source reports `prefers-reduced-motion: reduce` (at start and on live change): intro and travel collapse to `REDUCED_INTRO_TRAVEL_MS` with no camera fly-through/streak; rotation steps are instant; explosions remove mini-cubes instantly with no particle burst; face fades use `REDUCED_FACE_FADE_MS`. Gameplay (clicks, rotation, keyboard cursor, stats, level progression) remains fully functional.

## 3D rendering library decision

**Decision: three.js, imported directly (tree-shaken named imports), behind a thin rendering adapter — no React-3D bridge.** The adapter (`render/**`) consumes engine intents/snapshots; all game logic lives in `game/**` pure modules, so the library sits at the leaf of the dependency graph. Candidate comparison:

| Criterion | A. three.js (direct) — **chosen** | B. @react-three/fiber + drei | C. hand-rolled WebGL / CSS 3D |
| --- | --- | --- | --- |
| 60 fps capability | Full control of the rAF loop, instancing (`InstancedMesh`) for mini-cubes, points-based starfield/particles | Equivalent rendering, plus reconciler/`useFrame` overhead on every frame | Raw WebGL: possible but all lighting/particles/materials hand-built; CSS 3D cannot deliver materials/particles/camera flights credibly |
| Small bundle | Tree-shaken core only (measured ~120–135 KB gz for a minimal scene in 0.181; budget ≤ 350 KB gz total) | three + fiber + zustand/scheduler/its-fine (~+20–25 KB gz; drei more) | WebGL: smallest bundle but disproportionate build cost; CSS 3D: ~0 KB but wrong visual ceiling |
| Accessibility | DOM layer (HUD, skip, status regions, focus ring) is ours either way; keyboard model is pure logic — identical across A/B; CSS 3D would give native buttons but cannot meet materials/particles/transition asks | Same DOM layer as A | CSS 3D wins on native semantics; not decisive vs the visual requirements |
| Testability | Node-testable scene graph (Object3D/Mesh/Points/InstancedMesh construct fine without a GL context); only `WebGLRenderer` construction is GL-bound (mocked in one test); logic fully pure | Needs `@react-three/test-renderer` (extra dep) or reconciler-level testing; per-frame logic still imperative | Raw GL shaders untestable in node; CSS 3D would force DOM-environment testing (new dependency + config) |
| Dependency surface / risk | One mature MIT library + its `@types/three`; stable API; React-version independent | Peers pin React `>=19 <19.4`; larger transitive tree; version coupling | Zero new runtime deps, but large ongoing implementation risk |

**Rationale:** the game loop is imperative (camera flights, per-frame rotation interpolation, particle systems, star streak), which is exactly where a declarative React-3D bridge adds cost without benefit; direct three.js gives the smallest bundle, the fewest dependencies, and the strongest node-testability story (real scene-graph objects assertable in the existing test setup). **Checkpoint flag:** this adds two new dependencies — AGENTS.md § Boundaries marks dependencies as ⚠️ Ask first — so the user must approve `three` + `@types/three` before building (spec Q-1; the orchestrator carries this to the approval checkpoint). Versions: `three@^0.186.1` (latest 0.186 line), `@types/three@^0.186.0` (version-aligned; three ships no bundled types). No addons (`three/addons/*`) are used; named imports only.

| Principle | How this feature applies |
| --- | --- |
| Instant fun | Load lands directly in the game (no accounts, no menus); intro is short (2.5 s) and skippable; first click possible within seconds. |

## User stories

- As a player, I want to see the cube appear through an intro flight in a starry galaxy, so that entering the game feels immersive but not slow.
- As a player, I want every mini-cube click to explode satisfyingly and update my stats instantly, so clicking feels responsive and rewarding.
- As a player, I want to rotate the cube (mouse, touch, or keyboard) to reach and clear every face, so I can keep playing until the cube is gone.
- As a keyboard-only player, I want to navigate and explode mini-cubes without a pointer, so the game is fully playable without a mouse.
- As a player who prefers reduced motion, I want short/instant transitions, so I can play without discomfort.
- As a mobile player, I want tap-to-explode and drag-to-rotate to work perfectly, so the game feels native on my phone.
- As the project owner, I want the game logic in pure, tested modules at the 80% coverage bar, so the feature is solid and extensible for future real-time and economy work.

## Non-goals

- No backend integration of any kind: no WebSocket usage in gameplay, no shared/cross-client state, no identity/accounts, no reconnection handling; the existing `ws/connection.ts` scaffold stays untouched and is not referenced by the game (future real-time features own wiring it).
- No persistence: no save, no localStorage/sessionStorage, no cookies; a reload starts a fresh session.
- No economy: no points, upgrades, prestige, idle/offline progress; no placeholder economy code.
- No gameplay progression beyond visual style: later cube levels have identical structure (same grid) and differ by style only.
- No audio, no settings menu, no pause menu, no leaderboards.
- No new dependencies beyond `three` + `@types/three` (in particular: no R3F/drei, no physics/animation/tween libraries, no jsdom/happy-dom/RTL, no browser-automation).
- No changes to the backend workspace, container assets, smoke test, CI, ESLint/TS configs, `index.html`, or `main.tsx`.
- No coverage-config changes (no new exclusions, no threshold changes); no bounded-exception usage unless justified per the project rule (≤ 1 per task, in-test comment, reviewer-approved).

- ⚠️ Ask first: any dependency beyond the two sanctioned (`three`, `@types/three` — the user checkpoint Q-1 covers exactly these two); any coverage exclusion or threshold change; any change to a shared/container/config file outside a task's `files_owned`; any use of `three/addons` (unplanned feature surface); deviations from the pinned constants that would change an AC.
- 🚫 Never: add deps beyond the sanctioned two; weaken assertions (banned matchers, snapshot-only, assertion-free, useless tests) or exclude production code from coverage; touch `.env*`, secrets, backend/container files, `main.tsx`, `ws/connection.ts`, `index.html`, or configs; use `import *`/namespace imports from `three`; read browser globals inside `game/**`; push; change the pinned constants or ACs unilaterally.

## Security considerations

- **Dependency addition (supply chain):** exactly two new frontend deps — `three` (MIT, the de-facto standard 3D library, latest 0.186 line) and `@types/three` (dev-only, DefinitelyTyped, version-aligned). Both are locked via the repo lockfile (`npm install` only). This is the feature's flagged ⚠️ Ask-first checkpoint (Q-1); the builder does not add anything else. Supply-chain exposure is limited further by using named imports only and no `three/addons` code.
- **No secrets, no user data, no storage:** the feature has no network calls, no persistence, no cookies, no user input beyond pointer/keyboard events; nothing outside the session's memory is written. No `.env*` files are touched.
- **Rendering safety:** the canvas renders only procedurally generated geometry (no external assets, no textures, no model files → no loader/CORS attack surface); no `innerHTML`/`dangerouslySetInnerHTML`; all DOM text is static copy; React escapes the numeric stats by construction.
- **Resource bounds as robustness:** star count, particle count and pool size, and drawable counts are pinned constants (AC-16) — animations cannot grow memory without bound; `dispose()` releases GL/scene resources (AC-15), so repeated level transitions do not leak.
- **Test integrity as a control:** the coverage bar and concrete-assertion rule (AC-17) protect regressions in the pure logic that future server-authority work will depend on; no exclusion gaming; `game/**` DOM-freedom keeps logic testable and auditable.
- **Real-time impact — explicitly none in this feature:** no shared or cross-client state is created; connection lifecycle, reconnection, multi-client behavior, and server authority are out of scope (state above in § Non-goals and the hook-in notes in Q-7). Nothing here may be treated as authoritative game state outside the client session.
- **Containerization impact — additive only:** dependency manifest + lockfile change, absorbed by the existing image build (`npm ci`); no new services/images/ports/env/health; rebuild note already documented (`podman compose up --build`); the containerized smoke test is unchanged (AC-21).

## Testing strategy

- **Unit (Vitest, node environment, existing setup):** every `game/**` module — the pure core (board, rotation, progression, effects, engine) and the session with its injected environment — plus input mapping and `ui/theme.ts` tested in isolation with injected clock/scheduler/random/motion values; deterministic (fake timers, seeded fakes), concrete expected values, no banned matchers, no useless tests.
- **Integration (same node environment — no DOM is needed and none is added):** render-layer modules against **real three.js objects** (Object3D/Mesh/InstancedMesh/Points/Raycaster construct fine without a GL context): `cube-view`, `starfield`, `particles`, `scene`, `picking` assert real scene-graph state (counts, positions, visibility, disposal) and camera ray hits; `session` composes engine + scene + input through one fake boundary per environment concern (fake canvas, fake renderer adapter, fake scheduler, fake motion/visibility sources); React components get SSR render tests (`App.test.tsx`, `Hud.test.tsx`, `GameCanvas.test.tsx`) asserting exact static markup per phase. The only mocked module is `three`'s `WebGLRenderer` in `webgl.test.ts` (GL context is the one thing node cannot provide); the existing `connection.test.ts`/`App.tsx`-era tests are replaced/updated as part of this feature.
- **E2E / container:** no browser automation in this feature (out of scope — no browser dependency is added); `npm run smoke` remains the unchanged container regression check and is run at the final gate where the environment allows. The container path exercises the built SPA only structurally, which is honest evidence scaled to its reach.
- **Coverage:** `npm run coverage` — thresholds ≥ 80% statements/branches/functions/lines per workspace (frontend workspace pre-gate: `npm run coverage --workspace @cubeclicker/frontend`); config exclusions unchanged (only `src/main.tsx` + test patterns). Known honest residual: thin React effect bodies (session subscribe/attach wiring in `App.tsx`/`GameCanvas.tsx`) and the real GL context creation are not executed by tests; this residual is small and documented in the build logs — the aggregate must still clear 80. If measurement shows a metric cannot clear 80 honestly, the task reports `blocked` (no carve-outs, no exclusions, no threshold changes).
- **Verification commands:** `npm ci`, `npm run lint`, `npm run typecheck --workspace @cubeclicker/frontend`, `npm test --workspace @cubeclicker/frontend`, `npm run coverage --workspace @cubeclicker/frontend`, final gate `npm run coverage`, `npm run build`, optional `npm run smoke`.
- **FPS honesty:** 60 fps is pursued structurally (AC-15/AC-16: rAF loop, hidden-tab pause, instancing, bounded drawables, disposal) and is not an automated pixel/benchmark AC; a manual browser pass is recorded in the final build log where an environment allows it (steps listed), explicitly marked unexecuted otherwise.

## Open questions

- **Q-1 — New dependency approval (user checkpoint).** `three@^0.186.1` + `@types/three@^0.186.0` require the user's ⚠️ Ask-first approval. **Recommended: approve both** — rationale in § 3D rendering library decision; alternatives (R3F, hand-rolled) rejected there. If declined, the feature cannot deliver the requested materials/transitions; the fallback candidate (CSS 3D, evaluated and rejected above for its visual ceiling) would need a spec revision.
- **Q-2 — Mini-cube grid size.** Pinned `GRID_SIZE = 5` (25/face, 150/cube ≈ a 1–2 min level). **Recommended: keep 5**; alternatives 4 (snappier, 96/cube) or 6 (216/cube) are one-constant changes.
- **Q-3 — Rotation control feel.** Pinned: drag ≥ 40 px commits one 90° step; snap-to-face on settle; no free-orbit/momentum; queue-one during animation; arrows = one step. **Recommended: keep** (predictable, motion-sickness-friendly); alternatives (continuous orbit with snap, corner rotate buttons) rejected for ambiguity/complexity.
- **Q-4 — Transition pacing.** Pinned: intro 2.5 s skippable; travel 2.5 s; rotation 300 ms; explosion 350 ms; face fade 400 ms. **Recommended: keep**; pacing tweaks are constant changes, never AC changes without a spec revision.
- **Q-5 — HUD extras.** Beyond the requested clicks + faces destroyed, the HUD also shows `Cube N` (level feedback). **Recommended: keep** (cheap, clarifies the travel transition); user may drop it.
- **Q-6 — Auto-rotate after a front-face clear.** Pinned: auto-rotate to the nearest face that still has mini-cubes. **Recommended: keep** (keeps play flowing); alternative (leave orientation so the player sees the hole) is fine too.
- **Q-7 — Future real-time and economy hook-in (direction only).** When live stats arrive, clicks would be emitted as events to the server and shared counters would be server-authoritative; identity vs "no accounts" remains the tension flagged in `docs/product/realtime-backlog.md` § Open tensions. Economy (points/upgrades) would consume the same seam: the engine already emits one domain event per exploded mini-cube and owns the stats counters, so a future economy feature can derive currency from those counts (or a future real-time layer can forward the events) without changing this feature's rules. Not resolved here. **Recommended: address in the real-time feature's spec and the first economy feature's spec**, not now.
- **Q-8 — DOM test environment for interactive UI tests.** Current design keeps logic in tested pure modules and accepts a small React-effect residual. **Recommended: defer** jsdom/RTL (new deps, repo convention is DOM-free); revisit only if UI-wiring regressions appear.
- **Q-9 — Audio.** Not requested. **Recommended: out** (non-goal); add via a future feature if wanted.

## Assumptions

- The project bar from `docs/features/testing-criteria/spec.md` governs: unit + integration tests, concrete assertions, no banned matchers, ≥ 80% × four metrics per workspace via `npm run coverage`, exclusions unchanged.
- three.js `0.186.x` core constructs scene-graph objects without a DOM/GL context in node (used by the integration tier); only `WebGLRenderer` construction is mocked. If a specific import proves DOM-bound at import time, the builder imports granularly and records the deviation — tests must still exercise real three.js objects.
- The node Vitest environment can import `.css` files (Vitest stubs CSS by default); if not, the builder moves styles to `index.html`-linked CSS without changing the ACs' observable outcomes, or adjusts the import site — recorded in the build log.
- `@types/three` tracks three's 0.186 line; if npm resolves a mismatch, align both within the 0.186 line and record it.
- Stats are session-local and truthful by construction (no network, single client); counting semantics are per exploded mini-cube and per cleared face, cumulative across cube levels.
- The intro/travel cinematic is camera/scene work only — it never blocks input beyond the gated phases in AC-2/AC-10.
- The user checkpoint for Q-1 is the only mandatory approval; Q-2…Q-9 carry recommended defaults and do not block building.
