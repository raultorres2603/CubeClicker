# Spec — Frontend Delivery Hardening

## Summary

CubeClicker's frontend is currently one JavaScript chunk. The verified P-04 audit measured `src/frontend/dist/assets/index-qRRPF0W.js` at **982,591 bytes raw / 271,171 bytes gzip**, with Three.js at **662,772 bytes raw / 131,382 bytes gzip** (≈48% of that gzip payload); the current `adaptive-render-budget-v2` build is **≈983.50 kB raw / 273.10 kB gzip** (`assets/index-Dn5pY2q7.js`). The fresh post-split T3 build measured entry `assets/index-Cu7lmcVH.js`, initial `[index, react]` **95,903 B gzip**, three `assets/three-4rmoIDEa.js` **154,323 B gzip**, and total **273,854 B gzip**; the audit's 131,382 B was the **unminified** `three.module.js`, not the minified production chunk, so the user-approved r3 three ceiling is **165,000 B** while initial stays 150,000 B and total stays 300,000 B. Three.js is statically reachable from `App → createGameSession → render/scene` and from the customization preview, so every visitor downloads the 3D engine before seeing the auth/menu; the production nginx (`src/frontend/nginx.conf`) has no gzip, no immutable caching for hashed assets, and no explicit no-cache for `index.html`. This feature hardens the frontend delivery path — audit findings **P-04** (code splitting) and **P-06** (nginx delivery) — by (1) moving the Three.js game runtime and the customization preview behind dynamic imports so the auth/menu entry graph is Three-free, with explicit loading/error/retry states while preserving the accepted gate-close intro timing; (2) adding a reproducible bundle-size gate that fails the existing `npm run build` (and therefore CI and the Docker build stage) when the measured gzip budget is exceeded; (3) enabling gzip and the correct cache headers in the existing nginx container; and (4) proving the built image's headers and chunk graph in the containerized smoke test. The gate-deferred attach behavior accepted in `adaptive-render-budget-v2` is preserved, not redone.

## User stories

- As a player on a phone or slow connection, I want the auth/menu to load without downloading the Three.js engine, so the first interaction is fast.
- As a player, I want a clear loading state after I choose how to enter, and a retry if the game runtime or customization preview fails to load.
- As a returning player, I want hashed build assets cached for a year while the app shell revalidates, so deploys are picked up without stale JS.
- As a maintainer, I want a build-time bundle budget that fails CI when a dependency or import graph regression puts Three.js back in the initial load.
- As a reviewer, I want the production nginx headers and served chunk graph proven by the containerized smoke test, not just asserted in a config file.

## Acceptance criteria

### Initial load and code splitting (P-04)

- **AC-1 — The auth/menu entry graph excludes Three.js.** On a fresh `npm run build`, `dist/bundle-report.json` reports an `initial.files` list that does not contain the `three` chunk's `file`; the `index.html` entry's static `imports` closure in `dist/.vite/manifest.json` contains no chunk whose `name` is `three` and no file matching `assets/three-`; the built `index.html` contains no `<link rel="modulepreload">` or `<link rel="preload" as="script">` whose `href` contains `/assets/three-`. Evidence: `docs/features/frontend-delivery-hardening/build-log-T3.md` (fresh report + manifest excerpt), `bundle-budget.test.ts` (initial-closure unit test), and the smoke `/bundle-report.json` check.
- **AC-2 — Gate-close loading, error, and retry for the game runtime.** While `gateState.view === 'menu'`, `session.attach` is not called and no environment dynamic import occurs. After `Play as guest` or a verified login, `GameCanvas` renders an element with `role="status"` whose text is exactly `Loading the game…` until the session reports `ready`; in the normal gate path the session calls the environment loader once and starts exactly one attach cycle, and `ready` removes the status. If the loader rejects, the session reports `error`, `GameCanvas` renders `role="alert"` with the text `The game could not be loaded.` and a button named `Try again`; clicking it calls `session.attach(canvas)` again (a second loader attempt), and a resolved retry removes the alert. The `<canvas>` element and its SSR markup remain byte-identical in every state. In a StrictMode-like mount → unmount → remount, the first loader is cancelled by the attach-generation token, only the second load starts (two loader calls, one start), and the status is `ready` once it resolves. Evidence: `session.test.ts` (status transitions with an injected deferred loader and the StrictMode-shaped cancellation), `GameCanvas.runtime.test.tsx`, `App.test.tsx` (attach counts and ordering).
- **AC-3 — Attach/dispose semantics and the gate-close intro clock are preserved.** With an injected `SessionEnvironment`, `attach` remains synchronous and the accepted `adaptive-render-budget-v2` evidence stays valid: attach is idempotent; no renderer, listener, frame or transport connect exists before attach; `dispose()` during a pending load creates nothing and a later resolution is ignored; `attach → dispose → attach` creates one fresh cycle (attach 2 / dispose 1); hidden-at-attach schedules no frame; transport subscriptions are registered before the single connect. The intro clock stays anchored at gate close: the session never calls `engine.advance` while the loader is pending, and the start body sets the frame baseline to the runtime-start time, so the loader's elapsed time is never passed to `engine.advance`. With a fake-clock environment returned by a deferred loader, an attach request at `t0`, loader resolution at `t0 + N`, and first frame at `t0 + N + 16` yields the same intro progress as an immediate loader whose first frame is 16 ms after attach (`16 / introMs`), never `(N + 16) / introMs`; the intro begins at progress 0 and the load is skipped, not consumed. Evidence: the existing `session.test.ts`, `GameCanvas.test.tsx`, and `App.test.tsx` suites plus the new status/loader and intro-clock cases.
- **AC-4 — The customization preview is deferred.** The customization panel and `render/preview` are not in the initial entry graph. Opening the customization toggle after `welcome` lazy-loads `SpaceshipCustomizationPanel`, shows `role="status"` with the text `Loading customization…` until loaded, then renders the existing panel (the same `.customization-panel` and `Open lootbox` control). On load rejection it shows `role="alert"` with `Customization could not be loaded.` and a `Try again` button; clicking it triggers a second import attempt. Evidence: `DeferredSpaceshipCustomizationPanel.test.tsx`, `App.test.tsx` async customization tests, and the AC-1 build graph.

### Bundle budget (P-04)

- **AC-5 — The build fails on a bundle-budget violation.** `src/frontend/package.json` runs `vite build && node scripts/check-bundle-budget.mjs`. The script reads `dist/.vite/manifest.json`, measures every JS file with gzip level 6, writes `dist/bundle-report.json`, prints every chunk's raw/gzip size and the totals, and exits `1` when any of the following holds: `initial.gzipBytes > 150000`; `three.gzipBytes > 165000`; `total.gzipBytes > 300000`; no chunk named `three` exists; `three.file` is in `initial.files`. It exits `0` when all pass. The root `npm run build` inherits the exit code, so CI's existing `verify-app` Build step and the frontend Docker `build` stage fail on a violation. Evidence: `bundle-budget.test.ts` (synthetic manifests for each violation), `build-log-T3.md` (fresh measured bytes and report), and the CI/Docker build commands already pinned in the repository.
- **AC-6 — The budget is grounded in a fresh build.** The approved ceilings are **initial ≤ 150,000 B gzip, three ≤ 165,000 B gzip, total ≤ 300,000 B gzip** (the three ceiling was raised from 140,000 B by the r3 user decision). The fresh post-split T3 build measured entry `assets/index-Cu7lmcVH.js`, `initial.files = ["assets/index-Cu7lmcVH.js", "assets/react-BYqCGoBQ.js"]` at **95,903 B gzip**, `three = assets/three-4rmoIDEa.js` at **154,323 B gzip**, and total **273,854 B gzip**. Root cause of the original miss: the audit's 131,382 B was the **unminified** `three.module.js`; minification removes the whitespace and long identifiers that gzip exploits, so the minified production Three chunk compresses to 154,323 B despite a smaller raw size (609,337 B vs 662,772 B). T3 records in `build-log-T3.md` the exact `npm run build` output and the `dist/bundle-report.json` values for `initial.gzipBytes`, `three.gzipBytes`, and `total.gzipBytes`; that fresh post-split measurement is the authoritative number. If a future fresh measurement exceeds a ceiling, the builder stops and reports `blocked`; the ceiling is not raised without an orchestrator-approved spec revision. Evidence: the build log and the report.

### nginx delivery (P-06)

- **AC-7 — gzip and the cache-header matrix.** `src/frontend/nginx.conf` contains `gzip on;`, `gzip_comp_level 6;`, `gzip_min_length 128;`, `gzip_vary on;`, and a `gzip_types` list containing `application/javascript`, `text/javascript`, `text/css`, `application/json`, `application/manifest+json`, and `image/svg+xml`. It contains a `location /assets/` block with `try_files $uri =404;` and `add_header Cache-Control "public, max-age=31536000, immutable";`; a `location = /index.html` block with `add_header Cache-Control "no-cache";`; and the existing `location /` SPA fallback (`try_files $uri /index.html;`) with `add_header Cache-Control "no-cache";`. Evidence: `nginx-config.test.ts` static assertions and the AC-8 smoke headers.
- **AC-8 — Brotli is gzip-only and documented.** The `nginxinc/nginx-unprivileged:1.27-alpine` base image does not include `ngx_brotli`; the config enables no `brotli` directive. `docs/architecture/containerization.md` states that delivery is gzip-only, why brotli is not enabled (a custom nginx build would be required), and that a custom build is out of scope. Evidence: the T4 `nginx -V` probe in `build-log-T4.md` (no `ngx_brotli` match), the `nginx-config.test.ts` absence assertion, and the doc grep.

## Boundaries

- ✅ Always: keep the auth/menu entry free of Three.js; keep the game runtime and preview behind dynamic imports; keep the canvas element mounted and its SSR markup byte-identical; preserve gate-deferred attach, attach/dispose idempotence, transport subscribe-before-connect, the auth call order, and the gate-close intro timing (the loader elapsed is skipped, never consumed); use the existing Vite/npm/Vitest stack; record raw command output and measured byte values in build logs; keep `compose.yaml`, `podman compose up`, and the dev Vite frontend unchanged; run lint, typecheck, tests, the coverage command, the build, and `npm run smoke` before reporting done.

- 🚫 Never: load Three.js before the gate closes; weaken the initial-graph, gzip, or cache-header assertions; add `!important` or wildcard/snapshot-only tests; serve `index.html` with an immutable cache policy; commit source maps, secrets, or a report containing them; edit `.env*`; `git push`; edit outside the task's `files_owned`.

## Security considerations

- **No user-controlled data reaches the build, budget, or nginx layers.** Dynamic import specifiers are static source strings; there is no URL- or user-driven chunk loading. The budget script reads local build files only.
- **No secrets in the bundle or report.** `bundle-report.json` contains chunk names, file names, raw/gzip byte counts, and budget constants only; no source maps, environment values, or credentials are emitted. The report is served read-only like any static asset.
- **Dependency surface unchanged.** No package is added; the budget script uses Node built-ins (`node:fs`, `node:path`, `node:zlib`, `node:url`), and the smoke uses `node:http`/`node:https`/`node:zlib`.
- **Cache safety.** Hashed `/assets/*` may be immutable; `index.html` and SPA fallback routes revalidate (`no-cache`) so a deploy cannot leave clients on an old shell. Missing `/assets/*` paths return 404 and never the shell.
- **Load-failure discipline.** A failed game-runtime or preview chunk load is contained by the component's error state and a user-triggered retry; it cannot execute unverified code or bypass the auth gate. The gate remains terminal; the fallback does not reopen or reorder the auth flow.
- **Persistence integrity.** No persistence, storage, or schema is added or read.

## Real-time / multi-client

Explicitly **none**. No shared or cross-client state, protocol message, server rule, reconnection contract, or server-authoritative value changes. The only timing difference is client-local: the first WebSocket connection opens after the game-runtime chunk loads rather than at the instant the gate closes; the accepted subscribe-before-connect order, detached retry, reconnect/grace behavior, and multi-client semantics are byte-for-byte unchanged. No identity/account conflict is introduced (guest and account flows are untouched). The WebSocket endpoint (`/ws`) and its container exposure are unchanged.

## Assumptions

- **A-1** — Vite 7 supports `build.manifest`, function-form `output.manualChunks`, and the manifest fields (`isEntry`, `imports`, `dynamicImports`, `file`, `name`) used by the budget script.
- **A-2** — Naming the manual chunk `three` produces a manifest chunk with `name === 'three'` and a stable `/assets/three-<hash>.js` file name; the budget script fails loudly if that is not true.
