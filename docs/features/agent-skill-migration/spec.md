# Spec — Agent Skill Migration & Repository-State Repair

## Summary
The repository's agent skill pipeline is half-migrated and currently broken. Six project-owned pipeline skills (`orchestration-playbook`, `spec-authoring`, `spec-review`, `task-decomposition`, `web-implementation`, `code-review`) are deleted from `.opencode/skills/` in the working tree (the deletion is uncommitted and the content is intact at `HEAD`). Separately, `.agents/skills/` holds 31 imported skill packs — 13 `threejs-*` packs committed in `5801294`, plus 18 untracked packs (UI, Superpowers, OpenAI docs) and a modified-but-uncommitted `skills-lock.json` — none of which is referenced anywhere. The four agent allow-lists still name the deleted pipeline skills; `AGENTS.md:31` still describes `.opencode/` as the only skill home; `docs/architecture/documentation.md` cites a now-missing playbook file; and `docs/features/README.md` omits `coin-economy`, `spending-upgrades`, and `idle-accrual`.

This feature repairs the state without changing application behavior or the four-agent workflow: restore the six pipeline skills from `HEAD`, commit-track the imported packs and lockfile, adopt and document a two-location canonical split (project skills in `.opencode/skills/`, imported packs in `.agents/skills/`), curate per-agent allow-lists with explicit exclusions, reconcile the live docs and feature index, and leave every feature artifact committed. Raw request gist: "Proceed with all of them, one by one" — this is the first item, the repository-state repair.

## User stories
- As the maintainer, I want the six pipeline skills restored verbatim so the orchestrator, planner, builder, and reviewer can load their procedures again.
- As a pipeline agent, I want my `skill` permission block to encode exactly the skills I need, with a wildcard deny first and explicit allows after it, so no excluded pack can be loaded and no allowed skill is accidentally denied.
- As a builder, I want the version-matched three.js packs and the engineering-process packs (TDD, systematic debugging, verification, review reception) available on demand.
- As a reviewer, I want every allow-list rule, documentation path, feature-index row, and feature artifact to be mechanically verifiable from a clean committed state.
- As a reader, I want one architecture document that inventories both skill locations, states ownership and precedence, and gives every imported pack a disposition and reason.
- As a maintainer, I want the feature index to show the real state of `coin-economy`, `spending-upgrades`, and `idle-accrual` so the next pipeline run resumes from truth.

## Non-goals
- Rewriting the four-agent workflow, its states, gates, verdict formats, or delegation model.
- Authoring new skills beyond restoring the existing six pipeline skills.
- Deleting any imported pack, including the excluded and unassigned ones; deletion is a separate user decision.
- Hand-editing vendored pack content or changing the `skills-lock.json` schema/version; pack updates go through the installer and a future change.
- Running the skills installer, fetching from the network, or re-installing packs as part of this feature.
- Editing application code, tests, dependencies, container assets, ports, environment configuration, or deployment.
- Implementing the performance optimizations or the feature-idea inventory that follow this repair in the user's "one by one" request.
- Retroactively rewriting historical feature artifacts (`spec.md`, `build-log-*.md`, `reviews/*.md`) of other features that mention the old skill paths.
- Editing another feature's `status.md`, including the stale `coin-economy` frontmatter timestamp.

## Boundaries
- ✅ Always: restore pipeline skills verbatim from `HEAD`; stage and commit only the task's `files_owned` paths plus its declared `commits_also` bookkeeping paths; keep project skills and imported packs in their decided locations; verify every allow-list rule, effect, and order; record raw command output in the build log; leave the tree clean after T4 and T5; preserve the four-agent pipeline.
- ⚠️ Ask first: deleting any imported pack; changing `skills-lock.json` beyond committing its existing working-tree modification; editing agent permissions beyond `skill` allow entries; changing `opencode.jsonc`; editing another feature's `status.md`; adding an ESLint ignore for vendored packs.
- 🚫 Never: edit `src/**`, `tests/**`, container assets, or application config; rewrite vendored skill content; `git push`; run `git clean` or a worktree-wide `git checkout` that could lose the untracked packs; edit `.env*`; commit secrets; change the four agents' roles or the state machine; edit `docs/features/README.md`, `status.md`, `tasks.md`, `spec.md`, `plan.md`, or `reviews/**` as the builder (the builder stages/commits the declared bookkeeping paths without editing them).

## Security considerations
- **Third-party content.** The imported packs are vendored third-party instructions, and some contain scripts (`brainstorming/scripts/`, `systematic-debugging/find-polluter.sh`, `openai-docs/scripts/`). They are tracked for provenance but not executed automatically; only allow-listed skills are advertised to agents, and the excluded packs are not loadable by the pipeline.
- **Supply chain.** `skills-lock.json` pins each pack's source and `computedHash`. This feature commits the already-installed tree and lockfile; it does not fetch, install, or modify pack content. The 13 pre-existing entries are compared entry-by-entry to `BASE_SHA`, and the lockfile diff must have zero deletions. Any future pack update must go through the installer and a reviewed change.
- **Secrets.** The T1 credential scan covers `.env*` files, private-key blocks, provider token prefixes, credential assignments, and the named environment variables; any match blocks the task. The scan result is recorded in `build-log-T1.md`.
- **Permission surface.** Agent edits are limited to `skill` permission rules and a one-line advisory-precedence note. The rule order and effects are verified structurally and by last-match evaluation. T2 additionally compares every agent's **non-skill** permission entries to `BASE_SHA` and fails on any change, so no shell, edit, question, or subagent permission can be widened unnoticed. The builder stages `.agents/skills/` and `skills-lock.json` with git commands because its edit allow-list does not cover those vendored paths.
- **Bookkeeping commits.** The builder stages/commits planner-, reviewer-, and orchestrator-authored artifacts without editing them. The staged path list is explicit, and a clean `git status` check prevents unrelated files from riding along.
- **No user data.** The change touches no authentication, persistence, network, or cross-client state, so there is no new user-controlled-data or persistence-integrity surface.

## Testing strategy
- **Unit (content-level).** Static assertions executed by the builder, not new runtime tests: the 18 pipeline-skill files match `HEAD`; the 31 imported directories, 31 lockfile entries, and 13 pre-existing entries match `BASE_SHA`; the allow-list parser checks the exact rule sequence plus last-match semantics for every known ID; every allowed ID resolves to exactly one `SKILL.md`; no duplicate ID exists; the skills inventory/disposition tables cover all 31 IDs and all 14 non-allowed reasons; every live `.opencode/skills/...` reference resolves; the three feature-index rows are exact, dated from their status loop logs, chronologically placed, and additive-only. These are the unit-level checks for a content/configuration change with no application code.
- **Integration (system-level).** Static resolution is the authoritative gate: discovery from both locations is proven by the file/ID/allow-list checks. A best-effort `opencode run --format json --agent builder` smoke is supplementary only; whether it passes, fails, or is unavailable, it never substitutes for the static result (AC-13).
- **E2E.** None. The feature adds no service, image, port, route, container, or WebSocket behavior; `npm run smoke` is intentionally not required because there is no container/runtime change to prove.
- **Regression gates.** `npm run lint`, `npm run typecheck`, `npm test`, `npm run coverage`, and `npm run build` must stay green in T4. The change adds no application code; coverage thresholds remain ≥ 80 statements/branches/functions/lines per workspace, unchanged. Raw output goes in `build-log-T4.md`.
- **Bookkeeping.** T4 commits `spec.md`, `plan.md`, `tasks.md`, `reviews/**`, `status.md`, and the T3 README edit before code review, then records its commit stat audit in a second T4 evidence commit. T5 commits the pre-applied acceptance `status.md`/README row, task board, and code-review artifact; no edits occur after T5. Both tasks end with an empty `git status --porcelain`; raw output goes in `build-log-T4.md` and `build-log-T5.md`. T5's final README diff check covers the three AC-10 rows plus the single accepted row and compares the README date to the acceptance loop-log date.
- **Verification commands.** The exact commands are pinned in `tasks.md` T1–T5. Historical `docs/features/**` references are excluded from the live-link check (AC-9).

## Open questions
- **Q-1 (canonical location).** Recommended and planned: keep project-owned pipeline skills in `.opencode/skills/` (restore from `HEAD`; higher precedence, edited like code) and keep imported packs in `.agents/skills/` (upstream-managed, tracked with `skills-lock.json`). Alternative: move the six pipeline skills into `.agents/skills/` and update every allow-list. The alternative mixes project content into an installer-managed directory and adds no benefit; the recommended split is the default unless the user objects.
- **Q-2 (excluded/unassigned packs).** Recommended: track all 31 packs so nothing is lost, but allow-list only the curated subset; keep the excluded and unassigned packs in the repository for explicit user invocation and future review. Deletion is deferred and requires a separate user decision.
- **Q-3 (binding vs advisory).** Recommended: `AGENTS.md`, the agent prompts, the six project skills, and `docs/architecture/*` are binding; imported packs are advisory. Where an imported pack conflicts (human-partner escalation, `docs/superpowers/plans/` save paths, own stack mandates, inline/subagent execution methods, or namespaced references such as `superpowers:test-driven-development`), the project pipeline wins; namespaced references resolve to the local allow-listed ID when one exists and are otherwise ignored, and a subagent that would need to ask the user reports `blocked` to the orchestrator instead.
- **Q-4 (`coin-economy` date).** Its `status.md` frontmatter says `updated: 2026-10-28`, but its latest loop-log entry is `2026-10-30` (code review r1). Recommended: the README row uses `2026-10-30` to reflect actual last activity; the orchestrator may refresh the status frontmatter on the next `coin-economy` transition. This feature does not edit another feature's status file.
- **Q-5 (skill-load smoke).** Recommended: static resolution is authoritative; the `opencode run --format json` smoke is supplementary only and is never the acceptance basis. This avoids treating a repeated string or an environment-dependent model session as proof of discovery.
- **Q-6 (UI fix packs).** Recommended: allow `fixing-accessibility` and `fixing-motion-performance` on the builder only, because the project already enforces an accessibility baseline and a 60 fps interaction target. `baseline-ui` is **excluded** (its stack mandates conflict with the decided stack, per the plan's excluded table); the remaining design/authoring packs (`component-canvas`, `create-canvas`, `create-design-md`, `improve-ui`, `ui-skills-root`, `fixing-metadata`) and `brainstorming` are **unassigned**.
- **Q-7 (`writing-plans` conflict).** Recommended: allow `writing-plans` on the planner as an advisory aid for file structure, task right-sizing, step granularity, and self-review only; its `docs/superpowers/plans/` save path, plan header, execution handoff, and sub-skill references do not apply. CubeClicker's `spec.md`/`plan.md`/`tasks.md` templates remain binding.
- **Q-8 (orchestrator prompt vs edit permission).** The orchestrator's frontmatter grants edit access to `status.md`, `tasks.md`, and `docs/features/README.md`, while its prompt says it must not use read/write tools directly. This feature relies on the existing permission model and the established `docs-on-feature-acceptance` policy (the same model used by prior accepted features); reconciling the prompt text is a future workflow change and is out of scope here. No permission is widened.
